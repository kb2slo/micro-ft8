# Micro-FT8 test plan (kb2slo fork)

A ledger, not a manual: what automation checks, what it cannot see, and which field checks are still owed.
How a field check is asked for and closed is under **Pending** below; when the ledger changes, in
[AGENTS.md](../AGENTS.md) (**Test plan matches the work too**). Git history records every check that passed.

## Automated

An agent runs these itself before saying work is done. `tools/check.sh` runs every one but the decode
benchmark (`--changed` for only those a change can affect, `--list` to see which), and CI's steps call
the same script. No hardware.

## What automation cannot see

A green run is not coverage of these:

- **What any screen paints.** No test runs a `draw_*` function. Screen and MENU *navigation* are host-tested;
  whether a MENU row's label matches what it does is checked only by eye.
- **The main loop and slot timing.** Slot alignment, decode deadlines, TX start latency.
- **Decode tuning on the air.** The recall harness pins the firmware's settings given a WAV. `golden_rx` uses its own candidate and LDPC limits, so a tuning change moves none of its output. Whether a busier candidate list still finishes inside the guard is the decode benchmark, on a board.
- **The board slot cycle.** The scenario stepper injects decodes and takes whatever autoseq has pending. It does not run the head check before the trigger, IgnoreList, or arming. Those stay board code.
- **Every hardware path.** USB host and UAC audio, CAT, display, GPS, RTC, SD, flash, WiFi, the sidekick's
  HTTP server and button.

## Pending

Field checks owed on shipped work. Only someone with the hardware can run these: the maintainer, or a
contributor with a P4, a QMX and a sidekick. Add one when a change touches a
field-only path, naming the change and the exact check. **Drop it when the check passes.**

- **Asking someone to run a check → put the check itself in chat, never just its row's name.** For each owed row being asked for, give its numbered steps and expected results, and first how to get the build onto the device (the flash or `desk_push.py` command). "Run the O1a row in TEST_PLAN" sends them to a file in the middle of a bench session. Ask for a result per step. **Label each step with its number in the row, as text ("Step 5:"), never as a Markdown numbered list:** a list renumbers from its first item, so asking for steps 2, 5, 6 and 7 displays 2, 3, 4, 5, and their answers then map to the wrong steps.
- The person who ran it reports a pass **for every step** → drop the row in the **same turn**. The commit that drops it names the build that passed. A summary "it passed", or a step with no result, keeps the row: say which step is still open. A failure keeps the row and becomes a fix.

proven, and not counted as owed. Move one into the table when a check is planned.

- **The radio bar's push on a QMX without `AI`** (`radio_control_set_push()`). The bar should still read when the drawer opens, since `AI2;` is answered `?;` and ignored; never run. Firmware 1_04_003 accepts `AI2;` and passed the bench 2026-10-24 ([radio.md](architecture/radio.md)).
- **The Not decoding state** (`decode_failed`, `main.cpp`; [main_board.md](architecture/main_board.md), internal RAM). It needs the decoder to fail to start, which the RAM budget now prevents; the failure it reports happened once, on a build 14.6 KB over.
- **CAT lost mid-transmission keeps the radio bar on Transmitting with its Stop** (`radioBarState()`, decided 2026-10-25; host-tested). Losing CAT while keyed is not reproducible on the bench without risking the radio, so the bar's switch to CAT lost when the transmission ends is unchecked on a device.

The wire flag and the JSON are tested; the skip is not reached on the bench. Powering the QMX off takes its audio too, so no decode is applied and the trigger never reaches `tx_start()` (tried 2026-10-24); the other cause, SWR protection, needs `SR;` (QMX 1_04_004 or later, the bench radio runs 1_04_003). Check it on a radio with that firmware.
