# Micro-FT8 test plan (kb2slo fork)

A ledger, not a manual: what automation checks, what it cannot see, and which field checks are still owed.
How a field check is asked for and closed is under **Pending** below; when the ledger changes, in
[AGENTS.md](../AGENTS.md) (**Test plan matches the work too**). Git history records every check that passed.

## Automated

An agent runs these itself before saying work is done. `tools/check.sh` runs every one but the decode
benchmark (`--changed` for only those a change can affect, `--list` to see which), and CI's steps call
the same script. No hardware.

## What automation cannot see

A green run is not coverage of these:

- **What any screen paints.** No test runs a `draw_*` function. Screen and MENU *navigation* are host-tested;
  whether a MENU row's label matches what it does is checked only by eye.
- **The main loop and slot timing.** Slot alignment, decode deadlines, TX start latency.
- **Decode tuning on the air.** The recall harness pins the firmware's settings given a WAV. `golden_rx` uses its own candidate and LDPC limits, so a tuning change moves none of its output. Whether a busier candidate list still finishes inside the guard is the decode benchmark, on a board.
- **The board slot cycle.** The scenario stepper injects decodes and takes whatever autoseq has pending. It does not run the head check before the trigger or arming. Those stay board code.
- **Every hardware path.** USB host and UAC audio, CAT, display, GPS, RTC, SD, flash, WiFi, the sidekick's
  HTTP server and button.

## Pending

Field checks owed on shipped work. Only someone with the hardware can run these: the maintainer, or a
contributor with a P4, a QMX and a sidekick. Add one when a change touches a
field-only path, naming the change and the exact check. **Drop it when the check passes.**

- **Asking someone to run a check → put the check itself in chat, never just its row's name.** For each owed row being asked for, give its numbered steps and expected results, and first how to get the build onto the device (the flash or `desk_push.py` command). "Run the O1a row in TEST_PLAN" sends them to a file in the middle of a bench session. Ask for a result per step. **Label each step with its number in the row, as text ("Step 5:"), never as a Markdown numbered list:** a list renumbers from its first item, so asking for steps 2, 5, 6 and 7 displays 2, 3, 4, 5, and their answers then map to the wrong steps.
- **Before step 1, confirm what the bench runs:** the P4 build (`App version` in its boot log), the sidekick firmware (Settings, **Firmware**) and the web app (Settings, **App:**). An agent reads all three itself, from the station ([AGENTS.md](../AGENTS.md), **Read the station before asking about it**). A board keeps whatever was last flashed or pushed to it, from any machine and any branch, and a web app that does not match its sidekick firmware can fail silently. The pass records all three. After testing a branch on the bench, put `main` back (the web app from `/update`, **Install**) or say what is left on it.
- The person who ran it reports a pass **for every step** → drop the row in the **same turn**. The commit that drops it names the build that passed. A summary "it passed", or a step with no result, keeps the row: say which step is still open. A failure keeps the row and becomes a fix.

### Unverified, no check planned

Shipped code that has never run on hardware, with no check scheduled. Listed so it is not mistaken for
proven, and not counted as owed. Move one into the table when a check is planned.

- **The USB host patch for a channel error with no buffer executing** (`components/usb/src/hcd_dwc.c`; [main_board.md](architecture/main_board.md), **USB host stack**). It stops the `_buffer_parse` assertion that rebooted the P4 on 1 QMX power-off in 7 on usb 1.1.0; on 1.6.0 its warning did not fire in 20 power-offs (2026-11-01), so no run has shown it taking effect. No check can trigger it on demand: if `Channel error with no buffer executing, ignored` ever appears in a log, that run proves it.
- **The radio bar's push on a QMX without `AI`** (`radio_control_set_push()`). The bar should still read when the drawer opens, since `AI2;` is answered `?;` and ignored; never run. Firmware 1_04_003 accepts `AI2;` and passed the bench 2026-10-24 ([radio.md](architecture/radio.md)).
- **The Not decoding state** (`decode_failed`, `main.cpp`; [main_board.md](architecture/main_board.md), internal RAM). It needs the decoder to fail to start, which the RAM budget now prevents; the failure it reports happened once, on a build 14.6 KB over.
- **CAT lost mid-transmission keeps the radio bar on Transmitting with its Stop** (`radioBarState()`, decided 2026-10-25; host-tested). Losing CAT while keyed is not reproducible on the bench without risking the radio, so the bar's switch to CAT lost when the transmission ends is unchecked on a device.
- **Not keyed on the radio bar** (`tx_scheduler_hud_not_keyed_reason()`, `porta_emit_tx_not_keyed()`; [webapp.md](architecture/webapp.md), **The radio bar**). The wire flag and the JSON, including the sidekick's relay of it (`host_test_event_state`), are tested; the skip is not reached on the bench. Powering the QMX off takes its audio too, so no decode is applied and the trigger never reaches `tx_start()` (tried 2026-10-24); the other cause, SWR protection, needs `SR;` (QMX 1_04_004 or later, the bench radio runs 1_04_003). Check it on a radio with that firmware.
- **Field Day follows the CQ type** (2026-10-14; [autoseq.md](architecture/autoseq.md)). Host scenarios pin the sequences; no Field Day station is on the air to work until Winter Field Day (January) or ARRL Field Day (June).
- **Port A v2, a slot retuned partway through** (decodes from one slot under two headers, the same time, each
  under the frequency it was heard on). Not reproduced on the bench (2026-09-28, several tries): a decode lands
  on the new band only if the switch comes within a second or two of the slot start and the station is strong,
  or on the old band only if the switch comes after about 11 s and the rest still decodes. Covered by
  `host_test_dial_history` (a retune 3 s into a slot), the decode-batching test (a retuned slot as two batches
  that keep every decode) and the preview. No error appeared in the tries.
- **Android.** Nothing has been checked on an Android phone, including whether `micro-ft8.local` resolves over mDNS (on the sidekick's AP with mobile data on, and on a home router). It should work on Android 12+. Low priority at this project's scale: not every client gets tested.
- **The P4 drops a late or duplicate HL2 packet** (`poe_p4/main/hl2_transport.cpp`, the stream loop): its place was already zero-filled, so writing it would push the slot's timeline late by a packet (2.6 ms). The sequence tracker that decides it is host-tested (`host_test_hl2_proto`), and `tools/test_hl2_record.py` tests the recorder's same rule; the P4's use of it is not. A direct cable does not reorder packets, so no bench run reaches it; a run whose HL2 status log shows `late` above 0 with decodes still on time would.
- **Sidekick HTTP socket count.** `max_open_sockets = 10` in both servers (`sidekick/main/wifi_prov.c`) was
  chosen without an on-device heap reading.
