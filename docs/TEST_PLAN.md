# micro-FT8 test plan (kb2slo fork)

A ledger, not a manual: what automation checks, what it cannot see, and which field checks are still owed.
How a field check is asked for and closed is under **Pending** below; when the ledger changes, in
[AGENTS.md](../AGENTS.md) (**Test plan matches the work too**). Git history records every check that passed.

An agent runs these itself before saying work is done. `tools/check.sh` runs every one but the decode
benchmark (`--changed` for only those a change can affect, `--list` to see which), and CI's steps call

## What automation cannot see

A green run is not coverage of these:

- **What any screen paints.** No test runs a `draw_*` function. Screen and MENU *navigation* are host-tested;
  whether a MENU row's label matches what it does is checked only by eye.
- **The main loop and slot timing.** Slot alignment, decode deadlines, TX start latency.
- **Decode tuning on the air.** The recall harness pins the firmware's settings given a WAV. `golden_rx` uses its own candidate and LDPC limits, so a tuning change moves none of its output. Whether a busier candidate list still finishes inside the guard is the decode benchmark, on a board.
- **The board slot cycle.** The scenario stepper injects decodes and takes whatever autoseq has pending. It does not run the head check before the trigger or arming. Those stay board code.
- **Every hardware path.** USB host and UAC audio, CAT, display, GPS, RTC, SD, flash, WiFi, the sidekick's
  HTTP server and button.

## Pending

Field checks owed on shipped work. Only someone with the hardware can run these: the maintainer, or a
contributor with a P4, a QMX and a sidekick. Add one when a change touches a
field-only path, naming the change and the exact check. **Drop it when the check passes.**

- **Asking someone to run a check → put the check itself in chat, never just its row's name.** For each owed row being asked for, give its numbered steps and expected results, and first how to get the build onto the device (the flash or `install_firmware.py` command; the sidekick's image carries the web app, and `install_app.py` pushes an app alone onto a sidekick that is not on a release). "Run the O1a row in TEST_PLAN" sends them to a file in the middle of a bench session. Ask for a result per step. **Label each step with its number in the row, as text ("Step 5:"), never as a Markdown numbered list:** a list renumbers from its first item, so asking for steps 2, 5, 6 and 7 displays 2, 3, 4, 5, and their answers then map to the wrong steps.
- **Before step 1, confirm what the bench runs:** the P4 build (`host_fw_version` in `/api/config`), the sidekick's build and its web app (Settings › Software update, **Sidekick and app**: one version for both), and an app pushed from the bench if there is one (the same page, **App, pushed from the bench**). An agent reads all three itself, from the station ([AGENTS.md](../AGENTS.md), **Read the station before asking about it**). A board keeps whatever was last flashed or pushed to it, from any machine and any branch. The sidekick's image carries the web app ([sidekick.md](architecture/sidekick.md), **Web root**), so one version says both, unless an app was pushed onto it from the bench, which has its own line and build id (`<sha> <date> <time>`) and which any firmware change ends ([sidekick.md](architecture/sidekick.md), **The bench push**). The pass records all three, and a pushed app's build id when there is one. After testing a branch on the bench, put `main` back (flash a build of it, or `python3 webapp/tools/install_firmware.py --both` from one) or say what is left on it.
- The person who ran it reports a pass **for every step** → drop the row in the **same turn**. The commit that drops it names the build that passed. A summary "it passed", or a step with no result, keeps the row: say which step is still open. A failure keeps the row and becomes a fix.
- **Working for the maintainer, a change to this file alone goes straight to `main` when what it records is already on `main`,** with no pull request, the way a roadmap-only change does ([maintainer/roadmap.md](maintainer/roadmap.md), **Roadmap intake**, direct to `main`): results recorded, a passed row dropped, a step's instructions corrected. ### Unverified, no check planned

Shipped code that has never run on hardware, with no check scheduled. Listed so it is not mistaken for
proven, and not counted as owed. Move one into the table when a check is planned.

The stop decision is host-tested; on the radio it is not tested: the operator will not key a QMX into an open antenna to prove it (2026-11-20). A known mismatch at Tune's 25%, such as a 200 Ω resistor or four 50 Ω loads in parallel, would test it without that risk.

The row's words are host-tested; on a phone not tested: on a home network the phone reaches QRZ and the station through the same WiFi, so one cannot be cut without the other (operator, 2026-11-20).

Its code has run only on a workstation, as the relay for a real sync (2026-11-19: 84 of the station's 147 QSOs found at QRZ, 8 of the other 63 sent and found there by the next run).
