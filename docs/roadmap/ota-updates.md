# OTA updates (epic ukk6)

After the first install, every firmware update, for every board, happens over the air from the web app. Rows: [v697](#v697), [hstv](#hstv), [yme5](#yme5), [gemx](#gemx), [jmch](#jmch), [knwx](#knwx) ([ROADMAP.md](../ROADMAP.md)).

## Goal

* **First install is from the public site:** the Web Serial flasher on the downloads page writes a full merged image over USB, and recovery uses the same path ([sidekick.md](../architecture/sidekick.md), **First install**; [main_board.md](../architecture/main_board.md), **Two USB-C ports**).
* **Every update after that is OTA,** for both boards. Noticing an update, the prompt, the download and the install all happen in the web app.

## Constraints

* **No TLS and no signing on the device.** Trust comes from the browser's HTTPS fetch of the manifest, as for the app bundle ([system.md](../architecture/system.md), **The inversion** and **Why not signing**).
* **An update starts only by an operator's action in the app,** never remotely and never by itself (maintainer, 2026-11-12). The operator is asked to switch the radio off first and back on when it is done.
* **One update, as the operator sees it** (maintainer, 2026-11-12). The app, the main board and the sidekick are parts of it, named in its progress and in a failure, and nowhere else offered or described apart.
* **The main board has no network.** Its image reaches it over Port A.

## Decided

* **The sidekick downloads images itself** (§ **Download**), not the phone: one path, not two (**Why not**).
* **The operator is asked to switch the radio off for a firmware update, and nothing checks.** One left connected may need switching off and on afterwards; that is all a check would prevent, and two attempts at one cost more than it is worth ([main_board.md](../architecture/main_board.md), **Firmware updates**).
* **Nothing transmits during any step of an update** (maintainer, 2026-11-12, at the bench: a CQ went out through a 79 s transfer). From the tap to the end the main board holds transmit off and ends its queue; it goes on receiving, and the operator starts again afterwards. This replaces "nothing is stopped" (2026-11-10).
* **The boards update together** (maintainer, 2026-11-12). **Update** is offered only when a main board is linked and the sidekick has internet, and takes every part that differs to the published build; nothing is offered for part of a station, and a sidekick with no main board is not updated over the air at all (USB is the way out). Two boards cannot be made atomic, since each installs and restarts by itself: the main board goes first, so its failure changes nothing, and if the sidekick's then fails, the next **Update** finishes it. The app enforces this; the sidekick still takes a one-board request, which is how `install_firmware.py` sends a bench build.
* **The `FW_*` messages are frozen across `PORTA_PROTO_VERSION` bumps,** so any two builds can always carry an update between them.
* **Two channels, stable and dev.** Stable is a `v*` tag, cut by hand, semver; dev is every firmware build CI publishes from `main`, numbered by `main`'s commit count. A version carries its commit after a `+` (`0.1.0+ab12cd3`, `b1234+ab12cd3`); a local build reports its SHA alone, at a tagged commit too, so a bench build is never taken for a release. The boards compare versions as opaque strings, so none of this changes them.
* **A station's channel is read from its main board's version,** with no stored setting: semver is stable, anything else dev. Within a channel only a newer build is offered; a part running something from outside the channel (a bench build) is offered the channel's build.
* **An operator switches channel from Settings,** to an older build included: Settings names the station's channel and offers the other ("Switch to Stable (0.1.0)"), which is the one Update against the other channel's manifest, whatever its build number, the review saying when that build is older. The main board updates first, so a switch that fails halfway already reads as the new channel and the next Update finishes it.
* **Each channel has its own manifest file,** owned by one CI job, so no job rewrites part of another's. The stable one records its commit's build number, which orders versions across the channels, and names the app built at the tag: stable publishes the app and both boards as one version.
* **A stable tag goes only on a commit whose dev build was published:** both boards' dated OTA images for it are on the mirror. `cut_release.py` refuses first, and the tag's CI job refuses before it publishes, so a tag pushed by hand cannot pass. A stable release is then code that could be run as a dev build first.
* **A field result is recorded by commit, and counts for every build of that commit:** local, dev or stable. No check needs a build from CI, but the stable channel's own, which runs on real tags.
* **The first stable tag, `v0.1.0`, is the first beta, and ends pre-alpha.** A beta is a named build for testers. It does not promise that an update keeps settings or a log, in either direction: that starts at 1.0 ([n75z](release-1-0.md#n75z)), so until then an older build may meet files a newer one wrote.
* **When both boards need updating, the main board goes first,** while the sidekick still speaks its protocol; the frozen messages make that safe.
* **A main-board image counts as good** once the Port A handshake with the sidekick completes after its restart; otherwise the bootloader rolls back. The update is reported done only when the version the board then reports equals the manifest's.
* **The web app is part of the sidekick's image** (maintainer, 2026-11-15): one artifact that updates, confirms and rolls back together, and a first install that needs no internet ([sidekick.md](../architecture/sidekick.md), **Web root**).
* **A bench push replaces the image's app only on the image it was pushed onto, and never on a release,** so any firmware change returns a station to its image's app ([sidekick.md](../architecture/sidekick.md), **The bench push**).
* **The sidekick has no filesystem** (built by [jmch](#jmch)): two firmware slots and its settings in NVS. The station's data is the main board's.
* **An app change reaches a dev station as a sidekick update.** The cost is accepted until it bites (**Later**).

## Design

Facts it rests on, checked 2026-11-10: the release host serves `/download/manifest.json` over plain HTTP as well as HTTPS, with no redirect; each build reports a version (`PROJECT_VER`, `tools/git_version.cmake`), its channel's from CI and its git SHA from a local build ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **An image carries its version**), the P4's included, and the manifest's `ota` entry carries it ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Public Cloudflare mirror**); `porta_proto.h` reserves `PORTA_MSG_FW_BEGIN`/`FW_CHUNK`/`FW_END` (`0x10`–`0x12`), unused; the sidekick already has two 3 MB OTA slots and rollback (`sidekick/partitions.csv`, `esp_ota_mark_app_valid_cancel_rollback()` in `sidekick/main/main.c`); a P4 flashed before the two-slot partition table has one `factory` slot and answers `FW_BEGIN` with `NO_SLOT` until it is flashed over USB once.

Left for [jmch](#jmch). Facts it rests on, checked 2026-11-15: the slots are 0x300000 each and `web` 0x1E0000 (`sidekick/partitions.csv`); an image with the app is 1,288,160 bytes; no sidekick code holds a partition's offset (the slots are found by `esp_ota_get_next_update_partition()` and `esp_ota_get_running_partition()`, `web` by its label; only `tools/merge_sidekick_bin.sh` holds offsets); a page from 0.1.0 that finds no `app` entry in the stable manifest plans firmware only (its `FwUpdates.stableApp()`), and one that finds an entry relays that bundle to a sidekick whose bundle API still answers; of 371 commits on `main` in the month to 2026-11-15, 42 touched only the app and 108 touched firmware, which is the cost **Decided** accepts for an app change reaching a dev station as a sidekick update. **The merged USB image erases NVS,** which the design had the other way: `merge_bin` writes one file from 0x0 and fills the gap between the table (0x8000) and `otadata` (0xF000) with 0xFF, and NVS lies in that gap (0x9000); a merge of the current build has 0x9000 to 0xEFFF all 0xFF, and the downloads page writes the whole file at 0x0 (`webapp/downloads.html`, `writeFlash()`, whose `eraseAll: false` spares only what lies beyond the file). So "boots still joined and paired" needs the flasher to write the pieces at their own offsets.

* **Recovery:** `/update`, a seed page served from the image, starts a firmware update to the published build. It needs the sidekick on WiFi; on its own access point the way out is USB. The trial does not see an app that fails to load, which is why `/update` stays.
* **The table:** `ota_0` at 0x20000 and `ota_1` at 0x410000, 0x3F0000 (4,032 KB) each, and no `web`; `nvs` stays at 0x9000. One USB flash per sidekick. The firmware finds its partitions at run time, so a sidekick on the old table keeps taking images over the air while they fit its 3 MB slot.
* **Open, for [jmch](#jmch):** how a USB flash keeps NVS, given the merged image above: the downloads page's flasher writing the pieces at their own offsets, the merge leaving the gap out, or both. Its entry names neither `webapp/downloads.html` nor `tools/merge_sidekick_bin.sh` yet.
* **A switch to a release from before the app shipped in the image** (0.1.0) leaves the sidekick with no app of its own ([webapp.md](../architecture/webapp.md), **Settings › Software update**, switching channel). Nothing guards it; a release that carries its app ends it.

### Later

* **A dev manifest that leaves the main board's entry alone** when a commit did not change its image, if app-only updates prove costly: every board whose version differs is offered, so an app change reflashes the main board too.
* **A window on `FW_CHUNK`,** if [hstv](#hstv)'s measured transfer time is too long.

## Why not

* **The phone relays the image,** as it does the app bundle: it works in AP mode wherever the phone has signal, but the whole image sits in the browser as a Blob (Safari cannot stream a request body), and iOS suspends the page if the screen locks mid-upload.
* **IP over Port A** (PPP, NAPT on the sidekick, lwIP and HTTP on the main board): a redesign of Port A that costs RAM on the main board and runs slower than raw chunks on the same wire, and it would let a main board download for itself, the unattended-update trigger for reopening signing. Reopen if a main board needs the network for something continuous that cannot be handed down over Port A.
* **The P4 on its own Ethernet:** not a path this project uses ([main_board.md](../architecture/main_board.md)).
* **TLS on the sidekick:** not needed while the host serves plain HTTP. Reopen if the host ever forces HTTPS; measure the handshake's heap cost first, since the sidekick has no PSRAM.
* **The sidekick downloads the app bundle and switches it in after the firmware confirms:** a downloader, staging and a second copy to roll back to, all of which the bootloader gives an app inside the image.
* **A data partition on the sidekick,** for the app or for a park and summit store: with the app in the image it would exist for the store alone, and the station's data is the main board's ([activator-mode.md](activator-mode.md), **Decided**).
* **App-only publishes sent to dev stations through the bench push,** to spare them a sidekick update: it keeps the phone's relay and its publishing, and each published app would have to name the one firmware build it goes with.
