| w859 | <a id="w859"></a>The app says when it does not match the sidekick's firmware | A web app and sidekick firmware from different builds can fail silently. On the 2026-10-30 bench a branch's app asked for `/api/state`, the firmware answered 404, the event poll threw on every tick, and Operate stayed empty while the station decoded about 23 messages a slot; band changes still worked, so nothing looked broken. | zxv4 | <a id="zxv4"></a>Sidekick: a configurable host name (`micro-ft8.local`) | Raised while building the AP name and password: a custom AP name loses the hint the default SSID `micro-ft8.local` gives about the URL. | I32 | <a id="I32"></a>P4: keep the QSO log in a database, not daily `.adi` files | Each QSO is one ADIF line in a day file on the P4's LittleFS. No record has an ID, and the browser reads the log a day file at a time over Port A. So edit and delete ([I31](#I31)) and adding a partner reference after logging (row [w5nj](../ROADMAP.md#w5nj)) mean rewriting a file, and worked-before (the New filter, A5's dupe cue) means pulling the whole log into the browser. A database on the P4, with record IDs, answers these where the log lives; ADIF stays the export, and query results travel as [syb2](#syb2)'s JSON. **Open:** the engine and its RAM (PSRAM is off and internal RAM is spent, [main_board.md](../architecture/main_board.md)); power loss mid-write; the queries; whether the browser still caches; ADIF import. **Done-when:** an RFC accepted or rejected. |
| syb2 | <a id="syb2"></a>Port A: a data channel past 255 bytes, streamed to the web app | Each message is one frame of positional binary, 255 bytes at most, so a log field means five edits and a flash of both boards, and the QSO row (221 bytes) has no room for A5's partner reference ([logging.md](../architecture/logging.md), **The four-place field chain**). **Direction (operator, 2026-10-24):** control, config and events stay typed binary; a data channel carries JSON and bulk text such as ADIF, which the sidekick streams to the web app unparsed; a fragmentation layer above the unchanged 255-byte, I2C-mappable frame lifts the cap; the protocol revs freely while pre-stable. First use: the log. **For the RFC:** the fragment header (routing without parsing); what the sidekick buffers versus streams; JSON per record or the stored ADIF; the browser-to-P4 direction (import, edits); what holds the web app to the P4's names. **Done-when:** an RFC accepted or rejected. |

| I38 | <a id="I38"></a>Max-decode main board: Raspberry Pi Zero 2 W running `jt9` | From [RFC 0006](../rfcs/0006-decode-performance.md). | I40 | <a id="I40"></a>Encoder conformance against WSJT-X's `ft8code` | **Intake 2026-09-23**, the TX-side counterpart of [RFC 0006](../rfcs/0006-decode-performance.md)'s `jt9` truth. `ft8code` (installed with WSJT-X, e.g. `/usr/local/wsjtx/ft8code`) prints the reference 77-bit payload, 14-bit CRC, 83 parity bits and message type (`i3.n3`) for any message. | I41 | <a id="I41"></a>Sidekick: preserve recent decodes across a client reconnect gap | Operator-requested. | f4kb | <a id="f4kb"></a>Report our receptions to PSKReporter | Our decodes as spots, as WSJT-X does.
