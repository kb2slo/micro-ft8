# Web app architecture

The web app (`webapp/app/`) is the station's only UI on the headless P4, served by the sidekick ([sidekick.md](sidekick.md)) and run in the phone's browser. System context: [system.md](system.md).

## Screens

**Operate / QSOs / Tools / Settings** are four tabs, switched only from the tab bar (`app.html`, `#tabbar`), with no swipe between them and no title row above them (operator decisions 2026-10-25): the title row held only the title, a pairing badge and the Settings gear, and its height went to the decodes. Not paired shows as a radio bar state and a dot on the Settings tab (**The radio bar**).

**Every action reports where the operator is looking.** Operate has no status line and no banners (operator decision 2026-10-25): what an action changes shows where it changed (the radio bar, a row, the queue), progress and "ok" are not reported, and a failure's reason is a toast at the bottom for 6 s, above the tab bar and Operate's pinned bottom (`failMsg()`, `showToast()`; the Undo after a reply is the same toast). A lost link is the radio bar's No contact state (**The radio bar**). A newer app build is offered on Settings' App line, with Reload (`checkAppStale()`). Settings (a line stuck to the top of its tab) and the Station sheet (a line under its fixed header) each carry progress, results and failures while open. Settings has no Save button for the station: each field writes its own key when it changes (blur or Enter for text, a pick for a menu, a tick for a band), and a refusal puts the reason on that line and reloads the field to what the station holds. The sidekick's own network keeps its Save, since saving restarts it. An action's result is never replaced by the form reload that follows it.

* **Operate** pins its status above the decodes and its controls below them, so only the decode list scrolls (**Operate's pinned regions** below): the slot bar on top; the queue (**The CQ row** below) and the radio bar (**The radio bar** below, with band and frequency in its drawer) at the bottom.
* **Grow by destination, never by feature.** QRZ is not a screen: per-callsign data expands on the row it belongs to. One shared expand-on-tap component, used on decode, queue and QSO rows, shows **offline-derived** facts at once (DXCC and zones from the prefix, distance and bearing from grid arithmetic) and **online-enriched** ones (QRZ bio, photo) when reachable, failing legibly when not.
* **QSOs is one continuous list** with day dividers ("Today", "Sep 13"), not a day-file picker. The main board keeps one ADIF file per UTC day; the list loads the current day on open and older days as the operator scrolls (`FILE_LIST`/`FILE_READ`), because Port A's budget cannot carry the whole log on every open. A line under the toolbar shows the main board's log storage, "N MB free of M MB", from the live `storage_total_kb` / `storage_used_kb` config lines; it is hidden while the board has not said, and red under 10% free.
* **The callsign card's QSO history comes from the QSOs loaded so far** (`qsoHistoryFor()`), so a QSO on a day not yet loaded is missing from it. Row I32 would answer it from the P4.

### The CQ row

The queue's last row, always present (`app.html`, `#opCqRow`), above the radio bar: the queued CQ, which is an ordinary queue entry with its own tries ([autoseq.md](autoseq.md), **Tries**), drawn here rather than among the QSO rows. It sits below the scrolling QSO rows, not inside them, so a long queue neither hides it nor loses rows to it. The queue's other rows read `queue`, the CQ row too, from the same `QUEUE_ENTRY` stream (`renderCqRow()`; the CQ is the entry whose call is `CQ`).

* **Call CQ** (`POST /api/cq`) when no CQ is queued. It keys the transmitter in one tap, as Reply does; the main board picks the parity and the tries, and both show once the CQ is queued.
* **Once queued:** the parity, **Even ⇄** or **Odd ⇄**, which a tap moves to the other period (`POST /api/queue/parity`, for a strong station nearby); the count, `2/6 tries`, which opens the tries stepper (**Tries on a queue row** below); and **×**, which ends the CQ, stopping one on the air in the same press (`POST /api/queue/cancel`; the P4 stops a cancelled entry that is on the air, [autoseq.md](autoseq.md), **The slot cycle**).
* **Arrangement:** the Sends text over the status line on the left, the controls on the right, then a gear (`#cqSettingsBtn`, labelled "CQ settings").
* **The Sends text** mirrors autoseq's `generate_cq_text_into()` (`components/autoseq/autoseq.cpp`): the type's prefix (`CQ`, `CQ SOTA`, `CQ POTA`, `CQ QRP`, `CQ FD`) plus the call and the grid's first four characters, or the free-text field verbatim for a Free-text CQ. Tapping it, or the gear, opens the Station sheet (**The Station sheet** below).
* **The status line** reads "Not calling"; "Calling · even/odd slots" when the CQ is queued and the queue holds no other station; or "Waits for the queue · even/odd slots" once a real QSO is active, since every live QSO outranks a CQ ([autoseq.md](autoseq.md)).
* **Stop, during our own CQ, ends the CQ too.** The radio bar's Stop reads **Stop CQ** while the CQ is what's on the air, and posts `/api/tx/cancel` then the CQ's `/api/queue/cancel`; during a QSO message it reads **Stop TX** and only cancels that transmission. Which one is decided from the text on the air (`txIsOurCq()`: it starts with `CQ `, or is a Free text CQ's `free_text`), never from the queue: the CQ stays queued behind a QSO that answers it, while our report is what transmits. Otherwise the CQ stayed queued and the next one went out a cycle later regardless of the operator's tap.

### Tries on a queue row

Every queue row's count is a button, `2/6 tries` (tries sent of the limit, [autoseq.md](autoseq.md), **Tries**), reading `· custom` when the entry has a count of its own. A tap opens the tries stepper (`#opTriesEdit`), static markup under the CQ row for the reason the CQ row is static: the QSO rows are rebuilt on every poll.

* **The stepper** is `[−] n [+]`: − and + repeat while held (`holdRepeat()`: after 450 ms, every 100 ms), and the count is not typed (operator decision 2026-10-14). Buttons carry `touch-action: manipulation`, so quick taps do not zoom the page on iOS. It names the entry and what its count bounds ("K9ABC · tries at each step", "CQ · tries in all") with the tries already sent, and steps 1–20 for a QSO, 1–99 for the CQ. A change applies on its own about a second after the last tap (`POST /api/queue/tries`, "`<entry_id> <tries>`"), since an Operate control takes effect when touched ([RFC 0009](../rfcs/0009-operate-station-surface.md) §4). **Use default** sends 0, and the entry follows the Station sheet's Tries again.
* **A count at or below the tries already sent ends the entry**, so the stepper does not send it on its own: it says so ("2 already sent: this ends this step, after the try on the air if there is one.") and waits for **End it**.
* **Done** closes it, and so does the entry ending.
* **The CQ decode color** (`--good-hot`, `.c-cq`) is `#007a00` in light mode, `#4ade80` in dark. The light value was `#00c800` (about 2.3:1 on white), which fails WCAG's 4.5:1 text-contrast minimum.

### Operate's pinned regions

Operate keeps its status on top and its controls at the bottom, and only the decode list scrolls ([RFC 0009](../rfcs/0009-operate-station-surface.md) §3.14). Decodes are the scarce resource on a phone, and every control touched mid-QSO stays in thumb reach however long the list grows on a busy band (operator, 2026-10-24).

* **Why they sit outside the Operate panel.** Each tab is its own scrollport (`#viewTrack > section`), and the three tabs slide on a track moved by a CSS transform, so neither a sticky nor a fixed element inside a panel stays on screen. The top region (`#opTop`) sits at the top of `#viewport`, outside the track, and shows on every tab (operator decision 2026-10-26: "am I on the air, and is RF going out" matters on QSOs and Tools too, and a row that stays put keeps tabs from jumping); every panel starts below it (`--optop-h`). The bottom one (`#opDock`) is a fixed sibling of the tab bar, hidden off Operate (`body.on-operate`), and `#view-operate` alone ends above it (`--dock-h`). `layoutDock()` measures both and the tab bar. The map and SWR sweep pages are separate pages and have no slot bar. A hidden region reports 0 and the last height is kept, so leaving Operate does not resize the panel and clamp its scroll.
* **Top, on every tab:** the slot bar, with a tag at its left for the parity of the slot now, **E** or **O**. The bar is 18 px whether or not we transmit, so the row never changes height. It fills over the slot, with a cursor at the TX offset; red while we transmit, with the readout inside it (`txReadout()`: "4.9 W · SWR 1.30" from the TX HUD event, "Tune · …", "— W" before the first reading, "Write blocked"); amber while TX is halted, or with "0.0 W · no RF" when a keyed transmission still reads 0 W 1.5 s in, past its first tone and meter reply: the radio is keyed and sending nothing, and the SWR it reports then means nothing (operator decision 2026-10-26). At an activation, one line under it (**Activation progress** below). The decode count and the CAT, Audio and Link checks are in the drawer's status line.
* **The Decodes bar** (`#dvBar`) is sticky at the top of the scrolling list.
* **Bottom, top to bottom:** the QSO rows, one line each (call, `n/N tries`, state, ×), about two showing before they scroll in place, with no label and no empty line; rows scrolled out of sight show as a fade and a count at that edge, "+2 more ▾" below and "1 above ▴" above (`renderQueueMore()`, operator request 2026-10-25), which take no taps; the CQ row; the tries stepper while open; the radio bar; the drawer while open, below the bar.
* **Measured** in the browser at 402 × 874 pt, the iPhone 17 Pro's screen, on 2026-10-26, with no title row or status line: the decode list under the Decodes bar is 512 pt closed with two QSOs and an activation line (the canvas drew about 510). With the drawer open it loses about 190 pt (the canvas's drawer was about 150; this one adds the radio's line). On the phone, Safari's own bars take more; the layout passed the operator's phone check on 2026-10-26, unmeasured there.

### The radio bar

The bottom row of Operate (`#opRadioBar`): the band and frequency, a sub-line, and on the right a label, or **Stop** while something is on the air. It shows one state, highest first (`radioBarState()`, host-tested by `webapp/tests/test_radio_bar.js`), each with a glyph as well as a tint:

1. **On the air** (red): the band and frequency, and under them "Sending" with the message and the offset. Power and SWR are in the slot bar (**Operate's pinned regions**). **Stop CQ**, **Stop TX** or **Stop Tune** takes the label's place and is its own tap target, never the drawer toggle (`#rbStop`; **The CQ row** says what each stops). Tune reads "Tuning".
   - **CAT lost while on the air keeps this state** (decided 2026-10-25), so Stop stays under the operator's thumb; the sub-line ends "· CAT lost". The state ends with the TX HUD event's falling edge, or 3 s after the last event (`expireStaleTxHud()`), and the bar then shows CAT lost.
2. **A transmission that did not go**, with no Stop since nothing is on the air: **SWR protection tripped** (red: "Stopped, not sent · K9ABC tries next slot"); **Stopped: SWR tripped twice** (red: "CQ ended · queue cleared · check the antenna"), kept until the next transmission starts, since the main board stays stopped until the operator calls CQ, replies or tunes ([radio.md](radio.md), **SWR protection trips on a QMX**); **TX aborted** for another reason (red); **Not keyed** (amber: "Not counted: <reason>"), a TX HUD event with its `nk` flag when CAT was not ready or SWR protection held the slot. `noteTxHud()` counts tripped transmissions in a row as the main board does: once per transmission, and a clean one resets the count.
3. **No contact with the station** (red), then **Not paired** (amber: "Not paired · press the sidekick's button"; this phone can watch but not transmit or change anything, and the Settings tab carries a dot; `paired()` is whether a token is stored, so one the sidekick rejects shows at once), when nothing has answered for 30 s (`linkLost()`): the sidekick not reaching the main board and the browser not reaching the sidekick look the same from here, so it does not guess which, and the drawer says what to check. It clears with the next answer. Then **a radio problem**, from `radioChipState()`: **Found · syncing** (the device is there, CAT and audio are not both up) and **Radio moved** (the radio reports a frequency, mode or split other than the one the main board set) amber; **CAT lost** (CAT was up this session and stopped) and **Not decoding** (the main board's decoder could not start) red; **No radio** and **Unknown USB** (a device that is not the QMX) grey. The label becomes the way to the actions: "Review ›", "Radio ›".
4. **Ready**, quiet: "QMX ready", and at an activation "· 3 refs · 0000Z 3h12m", the time to 0000Z, when a POTA activation's day starts over.

**The drawer** (`#opDrawer`) opens from the bar's chevron, body or label (`setDrawerOpen()`) and asks the radio for its state. It opens below the bar, so the bar rides up to the top of the open section, and it slides open and closed (its one grid row animates from 0fr to 1fr in .25 s, with no motion under the system's reduce-motion setting; operator request 2026-10-25). While closed it is `inert`, out of the tab order and VoiceOver. Open, the bar turns blue, the chevron fills and points down, and the label reads **Close**. A band is two taps (operator decision 2026-10-25). Top to bottom:

* **A problem state's note and actions first:** **Put it back** and **Use it** when the radio moved, **Retry now** when CAT is lost, **Retune VFO** when not decoding.
* **The band grid and the frequency row** (**Band and frequency** below).
* **The status line:** the CAT, Audio and Link checks, the decodes in the last 5 minutes, and **Station ›** (the Station sheet).
* **What the radio said:** in Ready, one line (the device, its firmware, what it reports) with **Retune VFO** and **Tune**; in a problem state, its rows.

The rest of radio state:

* **Found shows at plug-in.** The main board announces the device when the USB host first sees it, not when CDC opens about 11 s later (`qmx_transport.cpp`, `track_usb_presence()` and the descriptor callback): `USB_STATUS` attach, with VID/PID `0` when the device is there but not yet named. An attach whose device leaves before CDC opens is cleared by the same task, since no CDC disconnect comes.
* **Read-back.** `POST /api/radio/read` sends the `RADIO_READ` action; the main board sends `IF;` (`radio_control_query_state()`) and the parsed reply (frequency, TX/RX, mode, split) rides in the config snapshot as `radio_hz`, `radio_tx`, `radio_mode`, `radio_split`, with `want_hz`, what the station means the VFO to be. A sync asks too. Never during a transmission or Tune, and never polled: the page reads when the drawer opens, and the radio pushes the rest (next bullet). The `IF;` layout parsed is the Kenwood TS-480 one the QMX follows (`components/radio_control/cat_reply_parser.cpp`); it is host-tested but unchecked against a real QMX (TEST_PLAN, Pending).
* **Pushed state.** The main board sends `AI2;` once per connection (`sync_vfo()`, with the `VN;` read), and the QMX then sends `IF;` unprompted whenever its frequency, mode, TX or split changes. `cat_reply_parser` counts each `IF;` that differs from the one before (`if_changes`); `porta_p4_radio_push_tick()` sees the count move and sends one `RADIO_STATE` event (`PORTA_EVT_RADIO_STATE`, at most one per 100 ms) with what the radio last said. The sidekick serves it in `/api/events` as `"d":7` (`hz`, `tx`, `md`, `sp`), and the page puts it where the poll would (`applyRadioPush()`), so the bar follows a knob turn at once; the next poll carries the same values. The tick holds back during a sync and 150 ms after, because the radio answers each command we send with its state and those are not its own doing. The drawer-open read stays for firmware that does not answer `AI2;` (it replies `?;`, which the parser ignores). There is no `AI0;`: the P4 has no clean stop to send it from, and a QMX power cycle clears `AI2;`. Host-tested by `host_test_cat_reply_parser`, `host_test_porta_proto` and `webapp/tests/test_radio_push.js`; the sync gating and the radio itself are field-only (TEST_PLAN, Pending).
* **Firmware version.** The main board asks `VN;` once per connection (after the first sync) and the parser keeps the answer until the radio goes; it rides in the config snapshot as `radio_fw`, and the drawer shows it ("FW" on Ready's line, "Radio firmware" in a problem state's rows). A QMX answers `VN1_04_003QMX;` (the release and the model run together, read on the bench 2026-10-24), shown as `1.04.003 (QMX)`.
* **Actions.** **Retune VFO** (**Put it back** when the radio moved) is the old Connect: sync the Station band, Digi, VFO A. **Use it** saves the radio's frequency as that band's frequency. **Tune** sends a carrier, with power and SWR large on the bar and in the drawer while it is on. **Retry now** when CAT is lost is the same sync, refused while CAT is down.

### Decode rows and tap to reply

Each decode row is two lines, about 51 pt. The first is the message at 1.05rem, with the → ME badge kept whole, and the SNR in bold mono right-justified at its end. The second is one mono line: DT, the place (a link to the map at the station's grid, cut short with … when long) and the distance at the right. The grid itself is on the station's card, and so is the bearing, which Settings' **Show the bearing on decode rows** (this phone only, off by default) adds to the row (operator requests 2026-10-25 and 26: DT is acted on more than the grid). Nothing shares the message's line but the SNR, so it does not wrap: measured at 402 pt with "-24 dB" on every row, every FT8 message shape tried fits, where beside a fixed 172 px number column 13 of the same 16 wrapped. Two cases still wrap, their badges going to the next line: a compound call to us (`KB2SLO <PJ4/K1ABC> RR73 → ME`), and a long message carrying both activation badges. A decode's audio offset is not on the row: the station's card lists it beside each decode heard this session (decided 2026-10-25: it is a detail of one station, and the card is where a station's details are). The slot header is one line: band and frequency, then the slot's span without the date, and its age ("14:02:30–45z · 6s ago", `fmtSlotTime()`). It sticks under the Decodes bar while its slot is on screen (each slot is its own `.dslot` box, so the header lets go when the slot ends), so the slot being read keeps its time in view.

**Rows never move under a finger** (operator request 2026-10-25). A new slot arrives at the top, and a tap that landed as the list shifted would reply to a different station. So a redraw waits while a finger is on the list, for 600 ms after it lifts (the tap's click comes after the lift), and while the list still coasts from a flick (`decodeRedrawHeld()`), then runs once. A redraw the operator's own reply asks for (Sending…) runs at once.

* **Tap a row to reply.** There is no Reply button. A row replies when its message is replyable (`isReplyableDecode()`: a CQ, or a closing 73 or RR73) on a slot still open for a reply (`slotReplyOpen()`), and no reply from it is sending or queued (`decodeRowReplyable()`). Such a row ends in a blue › and is a button for assistive technology, labelled "Reply to <call>: <message>". Its callsign and grid links keep their own taps (`decodeTapAction()`), with hit areas padded without moving the text. A row that is not replyable has quieter text and no ›; a message to us keeps its colour and badge. One listener on `#opDecodeRows` serves every row, so a row rebuilt by a poll keeps its tap. A tap meets the same refusals as before: a slot that aged out, and a decode heard on another frequency (**Band and frequency**). Host-tested by `webapp/tests/test_decode_tap.js`.
* **Feedback** (`sendReply()`). The row says **Sending…** at once; the sidekick holds the POST until the main board accepts or refuses, about a second. Accepted, the row is tinted, with a **Queued** badge after the message in place of the ›, and a dashed placeholder for the sender's call stands in the queue until a `QUEUE_ENTRY` for the same call arrives (matched on the call, no protocol change); a call already queued is highlighted instead. A refusal, or no entry within 10 s, removes the placeholder and shows the reason under the row with **Retry**. The row is tappable again once the queue entry goes away. State is `replyState`, reconciled by `reconcileReplies()` on each queue render and once a second.
* **The queue in the decodes** (operator request 2026-10-26). A decode that names a station in our queue (never our CQ entry, `queuedCalls()`) says what it means for that QSO (`queueInvolvement()`): the station is calling **CQ again**, **Working** someone else, **Done with** someone else (73 or RR73), or **Called by** someone else. The row gets an accent bar at its left edge, that station's call in bold, and the phrase on its second line in place of the place; no filter hides it, and it sorts right after messages to us (`decodeViewOf()`'s `involves`). A message to us from a queued station is already red with → ME and gets nothing more. Each queue row repeats the newest such phrase, with its age, while that slot is under two slot lengths old (`queueLastHeard()`, "Working W1XYZ · 6s", or "→ you"); within a slot, what the station sent outranks someone else calling it. WSJT-X gives this its own pane; on a phone it is a mark on rows already shown. Settings' **Mark decodes about stations in the queue** (this phone only, on by default) turns all of it off: the marks, the filter pass-through and order, and the queue rows' cue. Host-tested by `webapp/tests/test_queue_cues.js` and `test_decode_view.js`.
* **Undo.** An accepted reply to a call not already queued shows a toast, "Queued K4XYZ · Undo", for 5 s. **Undo** cancels that entry (`POST /api/queue/cancel`); an entry not in the queue yet is cancelled when it arrives, or forgotten if none comes within 10 s. A call that was already queued gets no Undo, since cancelling would end the QSO that was there.

### Decode sort and filter

The Decodes bar (`#dvBar`), sticky at the top of the list: the label and one non-wrapping row of same-shape pills, filled when active. **Sort** opens its four choices: Default (the order `decodeSortCmp()` stored: decodes to us, replyable lines with CQs strongest first, the rest, recent partners), Strongest (SNR), Nearest or Farthest (distance from the Station grid, for DX); it applies within each slot and slots stay newest first, because replies go to the newest slot and the 15 s rhythm stays readable. A decode with no known grid sorts last under Nearest and Farthest. **Filters** combine: **Replyable** keeps the lines a tap replies to by `isReplyableDecode()` (a CQ, or a closing 73 or RR73), whatever the clock says, and POTA/SOTA (`CQ POTA`, `CQ SOTA`). There is no distance filter: Nearest and Farthest already order by distance, and a filter hid every decode with no known grid. A message to us stays on top and is never filtered, and a decode naming a station in our queue comes next and is never filtered either (**Decode rows and tap to reply**). The choice is kept per browser (`localStorage`, a per-viewer convenience), and "N/M" (shown of all) sits right-aligned in the row while any decodes are on screen. Applied when a slot is drawn (`decodeViewOf()`), so changing it re-sorts what is on screen; host-tested by `webapp/tests/test_decode_view.js`. A New filter waits on row `I32`: the app knows only the log it has loaded.

### Activation cues on decodes

Only while the station has references (`act_refs`, Station sheet). `refreshOpLog()` loads today's UTC day file (`YYYYMMDD.adi`) itself every `LOG_REFRESH_MS` while Operate is showing, into `opLog.rows` (the Log tab's list is separate), and primes `callinfo.js`'s activator-spot cache. A decode whose sender is in the log on this band and mode, at one of our current references (`dupeIndex()`; an n-fer record counts for each reference), gets a grey **Worked** flag. A cue, never a block: a tap still replies. A decode whose sender is a spotted FT8 activator (`CallInfo.activeSpotFor()`, online only) gets a badge with their reference: **P2P** for a POTA spot when we are at a park, **S2S** for a SOTA spot when we are at a summit, else the plain program. A decode's mode comes from its slot length. Host-tested by `webapp/tests/test_activation_cues.js`.

### Activation progress

Only while the station has references: a line under the slot bar with each reference's count of today's QSOs (`opLog.rows`, the day file the cues above read) against its target, ✓ once reached (`activationCounts()`, `renderActLine()`). A QSO counts for every reference on its record, so an n-fer counts for each. A park counts calls unique by band and mode, to 10; a summit counts different calls, to 4 (SOTA's "four different stations"). The countdown to 0000Z is on the radio bar's Ready line. Host-tested by `webapp/tests/test_activation_cues.js`.

### Band and frequency

In the radio bar's drawer (**The radio bar** above), so a band is two taps: open the drawer, tap the band.

* **The band grid** (`#opBandGrid`) shows `active_bands`, one button of at least 44 px per band. Up to seven bands share one row with columns equal to the count (`grid-template-columns: repeat(N, 1fr)`, `buildDockBandGrid()`); more than seven wrap to a second row on their own, so no band is ever a swipe away.
* **A tap changes band at once** (`changeBand()`), asking first only when a QSO is queued or our own transmission is on the air ("ends your QSO with K9ABC and stops the transmission on the air," `confirmRetune()`), then cancelling both (`cancelQsosAndTx()`) and writing the band's standard frequency and `band_sel` in one PUT; the drawer closes. A "no" leaves the grid as it was and the drawer open — it never shows the new band until the write actually lands.
* **A band tap always lands on the band's standard frequency** (`standardKhz()`, the app's table), never the last frequency typed there (operator decision 2026-09-28), including a tap on the band already selected; one already at its standard sends nothing. A typed or nudged frequency therefore holds only until the next band tap. Keeping chosen frequencies is row `y9js`.
* **The frequency row** (`#opFreqRow`): **−**, the operating frequency in MHz, **+**, **Set**. The field shows the frequency except while it is being edited (`syncFreqInput()`), so a poll never overwrites a typed value. There is no Standard button: a tap on the band already selected returns to its standard.
  - A typed value under 1000 is MHz, otherwise kHz, kept to 0.1 kHz (the station file stores tenths).
  - **Set**, Enter and the keyboard's ✓ / Done apply it, and a change that goes ahead closes the drawer; a refusal or a declined confirmation leaves it open with the typed value. Escape puts the frequency back. **On iOS, Done sends no key event** (operator request 2026-09-28), only closing the keyboard, so an edit committed with no tap just before it applies; a tap (Set, −, +, anywhere) reaches the page first and its own handler decides instead.
  - **Set**, **−** and **+** (1 kHz) write the operating band's own key (`band<N>`, or `ft4_band<N>` under FT4) with one `putConfigLine()` PUT; − and + leave the drawer open.
  - **A value in another active band always asks first** ("Change band to 20m? 14.080 MHz is on 20m.", plus what it would end; operator decision 2026-09-28), then cancels like `changeBand()` and sends that band's key and `band_sel` in one PUT, frequency first. A non-standard value, such as the calling frequency SOTA's FT8 advice asks for ([RFC 0008](../rfcs/0008-activator-mode.md) §3), holds until the next band tap; saving one to return to is row `y9js`.
  - A value outside every Region 2 amateur band, or on a band not in `active_bands`, is refused client-side (`bandForKhz()`) with the reason, in a dialog. The band edges (kHz, ITU Radio Regulations Article 5) are a sanity check, not a licence check; 60 m is one range spanning the US channels and the WRC-15 allocation:

    | Band | 160 | 80 | 60 | 40 | 30 | 20 | 17 | 15 | 12 | 10 | 6 | 2 |
    |---|---|---|---|---|---|---|---|---|---|---|---|---|
    | From | 1800 | 3500 | 5330 | 7000 | 10100 | 14000 | 18068 | 21000 | 24890 | 28000 | 50000 | 144000 |
    | To | 2000 | 4000 | 5407 | 7300 | 10150 | 14350 | 18168 | 21450 | 24990 | 29700 | 54000 | 148000 |

  - **A same-band change mid-QSO is treated like a band change** (operator decision 2026-09-28): the same confirmation, then the queued QSOs end and a transmission on the air stops before the new frequency is written. The partner is listening on the old frequency. Stopping the TX first also matters because a frequency the VFO cannot reach mid-TX is still saved, and nothing retunes the radio when the TX ends, so the bar would show a frequency the radio is not on. With nothing to end, no cancel is sent: a cancel also blocks a TX armed for the current slot.
* **Reply refuses a decode heard on another frequency** (`replyFrequencyMismatch()`; operator request 2026-09-28). A reply goes out on the frequency the radio is on now, so after a band or frequency change a decode from before it gets a dialog ("K1ABC was heard on 7.074 MHz, and the radio is on 14.074 MHz now…") and nothing is queued. The decode's own frequency comes from the main board (next bullet); the radio's now is the bar's. If either is unknown, the reply goes ahead.
* **The main board names each decode's slot and frequency** (Port A v2, [sidekick.md](sidekick.md), **Port A**). The app used to label a slot by what was current when its decodes arrived, a second or two after the slot ended, so headers missed the slot grid and a band change in that gap mislabelled a slot. Now each decode carries the slot it was recorded in (`si`, `sl`) and the dial frequency at the middle of its own signal (`fq`). The app groups decodes by slot (a new slot starts a new batch; SLOT_STATE's parity is only the fallback for a v1 host) and, within a slot, by frequency: a slot retuned partway through reads as two batches with the same time, each under the frequency its decodes were heard on, and nothing is dropped (operator decisions 2026-09-28). **A slot is timed at its end**, on the :00/:15/:30/:45 grid (7.5 s for FT4), so a batch that has just arrived reads "0 s ago", and its header shows its span, `2026-09-28 19:03:30–45z` (`fmtSlotSpan()`), so a WSJT-X-style start reads true too; its band is named from its frequency. **Reply is offered by the clock, not by position in the list** (`slotReplyOpen()`): only on a slot that ended less than two slot lengths ago, the current and previous slot (30 s on FT8, 15 s on FT4). Decodes shown after the app sat idle, restored from its cache or caught up from the sidekick, carry their real slot time and are not replyable however high they sit, and a tab that stayed open redraws the moment it is visible again. A station still calling reappears with its own button, and the main board remembers only its last 64 decodes for a reply, two or three slots on a busy band (operator decisions 2026-09-28). **A reload adds no second copy:** it restores the shown slots from the cache and then reads the sidekick's event ring from its start, so a decode already shown (the same id and text, and the same slot when the host names it) is skipped (`decodeAlreadyShown()`). The text is part of the match because the main board numbers decodes from 1 at each boot. The QSO log is untouched by any of this. Covered by `webapp/tests/test_decode_batching.js`.
* **The main board refuses a frequency write that does not reach the radio.** `station_key_names_operating_band()` (`components/station/station.cpp`, host-tested) answers whether a CONFIG key names the band actually being operated — `band_sel`, or that band's own frequency key under the active protocol. `porta_host_config_set()` calls it where it already tested for `band_sel`, and refuses with `station_vfo_refusal()`'s text: "band saved, VFO not moved (TX active)" for `band_sel`, "frequency saved, …" for a frequency key, or "… (CAT not ready)". A write to any other band's frequency, or to `active_bands`, stays silent on a sync miss, same as before. The refused value is still saved: the refusal says the radio did not move, not that nothing changed. So after any refused write the app re-reads the station, and the bar shows what it holds; a refusal of a drawer action also shows in a dialog, since the operator is looking at the drawer (`putConfigLine()`). With CAT down, the P4 retunes to the saved frequency when the radio reconnects.
* **Settings keeps only which bands appear** (`active_bands`, `buildBandRows()`). `band_sel` and the per-band frequency rows are in the radio drawer, not Settings; Settings no longer sends either key, which also ends the mid-TX `band_sel` refusal that could hit every Settings save (§2.1 of [RFC 0009](../rfcs/0009-operate-station-surface.md), now moot since Settings can no longer trigger it).

### The Station sheet

A full-screen overlay (`#stationSheet`, same slide-up mechanics as Who hears me's list, `#pskrList`), opened from the CQ row's gear and the radio drawer's **Station ›**, and never open at the same time as that list — each `open*()` closes the other first. Like Settings there is no Save button: **each control writes its own key the moment it changes**, with one `putConfigLine()` PUT, which reloads the whole station either way — a success brings the CQ row's Sends text and the dock line back in sync with what actually landed, and a refusal (shown in a dialog, since the operator is looking at this sheet, not the status line) reloads the control back to what the station still holds.

* **Calling CQ:**
  - A **Sends** preview, `cqSendsText()`, the same function the CQ row's own preview uses.
  - **Type** (`cq_type`, 0–5: CQ, SOTA, POTA, QRP, FD, FreeText).
  - **One free-text field, shown only for FD and FreeText,** writing `free_text` for both (`setStationSheetForm()`): the label switches between "FD exchange" and "CQ message", and only FreeText caps it at 13 characters (`maxlength`, removed for FD, which has no such limit). Since both types write the same key, switching from one to the other leaves the previous type's text sitting in the field until a new CQ actually goes out under the new type.
  - **Grid**, with a client-side format check (`gridFormatOk()`) matching `normalize_grid_maidenhead()` exactly (`components/station/station.cpp`): 4, 6 or 8 characters, field `A`–`R`, square `0`–`9`, subsquare `A`–`X`, extension `0`–`9`. A malformed grid is refused in a dialog and never sent — the firmware itself only silently *keeps the old value* on a bad write (`StationKey::Grid` in `station_parse()`) rather than reporting a refusal, so without this check a typo would read as accepted while the grid never changed. A note under the field always says the CQ carries the first four characters, plus the same compact location badge a decode or QSO row shows for a grid (`CallInfo.shortLocation()`, `callinfo.js` — "TX·US"), so typing a grid gives the same "is this where I think it is" check the operator already gets on someone else's. **Set from GPS** reuses the `geo.html` handoff (**A non-secure origin** below); its return route is `#stationsheet`, which `applyHashRoute()` opens straight to this sheet.
* **QSOs:** **Tries** (`tries`, 1–20, the same stepper control as a queue row's count, written about 0.8 s after the last change: how many times each QSO message goes out, and how many CQs Call CQ sends, [autoseq.md](autoseq.md), **Tries**) and TX offset (`offset`, `offset_src`).
* **Activation:** a program+reference list (`act_refs`, e.g. `POTA:US-1234,SOTA:W7O/CC-001`) with an Add row and an × per reference (RFC 0008 §4.2, §4.3 "Typed references, offline"). The program is inferred from the reference itself — a `/` means SOTA, otherwise POTA — and a reference containing `,` or `:` (the list's own delimiters) is refused client-side before it is ever sent, since it could never round-trip. Format-only: there is no store, nearby list, map, or verified/unverified badge yet, since nothing exists to check a reference against until A3's reference store ships (row `I18`). `components/station/station.cpp`'s `normalize_act_refs()` is the actual source of truth — it drops a malformed token on its own rather than rejecting the whole write, and is what a manual Station.txt edit or a future add-screen (A3) is also held to. **Adding the first reference (empty → non-empty `act_refs`) switches `cq_type` to `CQ POTA` or `CQ SOTA` on its own** (SOTA if any SOTA reference is present, a mixed activation defaults to SOTA), in `porta_host_config_set()` (RFC 0008 §4.4). Only that one transition derives it — adding or removing a reference afterward never overrides a manual Type change made through this same sheet.
* **Footer:** the call, read-only, with a note that it is changed in Settings — the call is the licence identity, not something changed mid-QSO.
* **Not in the sheet:** Call CQ and an entry's own count (the queue's rows) and band/frequency (the radio drawer) — each control has one home.
* **Settings does not carry these keys** (`cq_type`, `free_text`, `grid`, `tries`, `offset`, `offset_src`): its `FIELDS` array no longer lists them, and each Settings field writes only its own key (§2.1 of [RFC 0009](../rfcs/0009-operate-station-surface.md)). `free_text` is the Free text CQ's message and, with Type FD, our Field Day exchange ([autoseq.md](autoseq.md), **Field Day follows the CQ type**); there is no separate CQ free-text key.
* **Not yet in the sheet:** the grid check against a station's references (row `I18`, RFC 0008 A3).

### Decisions a reference app would make differently

Surveyed 2026-09-14: WSJT-X, FT8CN, iFTx and the standalone touchscreen builds.

| Not imported | Why |
| --- | --- |
| Waterfall | Its control job in every reference app is picking the TX offset, and `resolve_tx_offset()` already does that without asking: Random re-rolls 500–2500 Hz per transmission, which decorrelates us from the stale gaps every operator taps. Spectrum data would also blow Port A's budget. Reopen if field operation shows repeated collisions re-rolling does not avoid. |
| Mode control (Listen / Call / Exchange) | Autoseq's priority queue already sequences: every live QSO outranks a CQ, so the operator calls CQ and replies take priority. A mode control would add an error state that does not exist. |
| A single "current QSO" panel | The queue holds up to `AUTOSEQ_MAX_QUEUE` (30) concurrent QSOs, active and inactive ([autoseq.md](autoseq.md)); one panel would misrepresent it. The queue is a first-class region, and at 30 rows it simply scrolls. |
| A view per feature | Too much for a phone, and mid-QSO tab-switching runs against a 15-second clock. |
| Modifier-key interactions | There are no modifiers on a phone. |

Borrowed deliberately: FT8CN's lesson that the operator must see **which slot a tap lands in** (the countdown sits beside the tap target); iFTx's **worked-before colouring** on CQ rows; and WSJT-X's two information needs, "everything on the band" and "what concerns me", kept as **emphasis within one stream**, not two panes.

## A non-secure origin

`http://micro-ft8.local` is not a secure context, and that is a design choice, not an oversight: the alternative is a certificate for a name that resolves on one LAN. Measured 2026-09-21 in Chromium (Safari gates these APIs on secure contexts the same way); the last row follows from the spec rather than a measurement:

| API | Here |
| --- | --- |
| `localStorage`, IndexedDB, `fetch` to HTTPS | work |
| Cache API, Service Worker | **absent** |
| `navigator.geolocation` | property present, **call refused** (feature detection lies) |
| Web Serial, Web Bluetooth, Web Push | absent |

**So "cache it in the browser for offline" does not exist on this origin.** Anything that must work offline is served by the sidekick from its `web` partition, or it is not available offline.

**Grid from the phone's location** therefore needs a real secure context: `webapp/geo.html` on the release host (HTTPS). The app does a **top-level navigation** there, the page calls `navigator.geolocation`, and it redirects back with the grid. An HTTPS iframe does not work: secure-context checks walk the whole ancestor chain. Reached from the Station sheet's **Set from GPS** and the map's locate button; both confirm before overwriting an existing grid. The sidekick is not a party to the exchange. Leaving needs internet, which the phone often lacks on the sidekick's AP ([system.md](system.md), **Connectivity**), and a navigation that cannot load strands the operator on Safari's spinner or error page with nothing of ours running. So both leave only after a 4-second `no-store` fetch reaches the host (`geo_handoff.js`), and otherwise stay and say there is no internet. **Not yet built: row rrsp** — a service worker on the release host that makes `geo.html` work with no network; with it, that check would refuse a hand-off that works, so the row replaces it.

## Tools

What the operator consults *instead of* looking at the radio. **The test for a Tools card: if it expands an existing row, it is not a Tools card** — a worked-before flag, a DXCC name or a QRZ bio stays on its row. Cards are questions the operator asks, not vendors we integrate.

**Every card declares a tier and degrades visibly:**

* **Offline-derived** — computed from data the app already has; works on a summit with cellular off.
* **Online-optional** — offline-derived, enriched when reachable; complete without the enrichment.
* **Online-required** — meaningless without the internet, and says so when it cannot reach its source.

**A card never shows a stale value as a current one.** A four-hour-old K-index shown as now is worse than an empty card, because the operator makes a band decision on it: stale data carries its age or is not shown.

**Sources** are called directly when they send CORS, and a Worker route is added only when they do not ([system.md](system.md), **Third-party services**). Payload size is part of the choice: a phone on cellular must not pay for a large file to show one number.

* **Space weather** (`app.html`): NOAA SWPC's small current-value endpoints (10.7 cm flux, X-ray flare class, solar wind speed and Bz/Bt, the R/S/G scales) and the planetary K-index, whose `a_running` supplies the A-index. Not hamqsl.com: no CORS and no JSON, and its per-band verdict is an undocumented formula (row B80 adds it through a Worker). Not NOAA's aurora file (922 KB) or sunspot history (no small endpoint).
* **POTA and SOTA** (`map.html`): `api.pota.app` activator spots and `api-db2.sota.org.uk/api/spots/{n}/all/all`, both CORS-open. SOTA's API terms restrict AI-authored clients without prior approval; the operator chose to build against it anyway (2026-09-21).
* **Not in Tools:** self-spotting to POTA/SOTA — an authenticated outward write is a different risk class from a read-only card.

### Who hears me

Stations that reported hearing our call, from PSKReporter's live MQTT feed. Online-required. **The map is the main view** (operator, 2026-10-08): a PSKReporter layer on `map.html` (**The map**, below). Tools has a card with a status, a count, **Open list** and **Show on map** (`map.html?layer=psk`, which opens with the layer on). The design, and the history query still to come for gaps, is [RFC 0013](../rfcs/0013-pskreporter.md).

* **Three files.**
  - `pskr_core.js` holds the logic: packets, spots, gaps. Host-tested by `webapp/tests/test_pskr_core.js`.
  - `pskr_live.js` is the listener `app.html` and `map.html` share: the socket, reconnects and the stored copy. Tested with a fake socket and clock by `webapp/tests/test_pskr_live.js`.
  - Each page names the call, says when it wants to listen, and draws.
* **The browser subscribes to our own call only:** `wss://mqtt.pskreporter.info:1886`, topic `pskr/filter/v2/+/+/<CALL>/#`, never the whole feed (operator, 2026-10-07). WebSockets are not subject to CORS, so no Worker route is involved.
  - The feed writes a `/` in a call as `.` (`F5OYA/P` is `F5OYA.P`, seen 2026-10-08).
  - A spot whose sender is not our call is dropped even when the topic matched.
* **A hand-written MQTT 3.1.1 client.** It connects, subscribes at QoS 0, receives, and pings every 30 s.
  - The broker drops a client that is silent for about 90 s (keepalive 60).
  - A socket that has heard nothing for 75 s is treated as gone. That is how a phone that locked notices on waking.
  - A refused or dropped connection backs off from 15 s to 5 minutes.
* **When it listens:**
  - For 15 minutes after any transmission `app.html` saw (a TX HUD event on the air), on whichever page is open.
  - While Tools or the list is on screen, or while the map's layer is on.
  - Why 15 minutes: a transmission's spots reached the feed up to 561 s after it (median 92 s; 2026-10-07, 20 m FT8). The map sees no TX events, so a transmission made while only the map is open is not recorded.
* **The feed keeps no history.** It publishes at QoS 0, so even a persistent session holds nothing for a client that is away (measured 2026-10-07). A spot that arrives while no page is listening is lost.
* **One stored copy, both pages.** `localStorage` key `microft8_pskr_v1` holds one call's newest 5,000 spots for 24 hours, plus the listening and transmitting ranges.
  - A page loads it on start and saves it every couple of seconds while listening, and on leaving.
  - Two tabs open at once each take the other's new spots when it saves (the `storage` event).
  - A different call in Settings starts fresh. A per-phone convenience, never the record.
* **Gaps are shown, not hidden.** Where a spot of ours could have arrived (a transmission through 15 minutes after it) and no page was subscribed for a minute or more, an italic **Not listening 14:10–14:25z** row sits in the list. A quiet stretch never reads as nobody hearing us.
* **The summary** (the Tools card and the list) covers the last hour: how many distinct stations, the bands they heard us on, and the farthest of them with its distance. The farthest call is tappable.
* **The list** is a full-screen sub-page over Tools (`#pskrList`, the same overlay mechanics as Settings). Its rows are built only while it is open.
  - **One row per receiver and band:** its newest report (SNR, age) and how many it sent (×3). One row per report would let a single far station fill the top of a distance sort.
  - **Filter by band** (chips for the bands in the stored spots, and All).
  - **Sort by Time** (newest first), **Distance** (farthest first) or **dB** (loudest first). A row with no grid or no SNR sorts last. The field sorted by is shown in bold.
  - **Not listening** rows show only in the Time sort, since they are about time.
  - Up to 200 rows. The band and sort are kept on the phone (`microft8_pskr_list_v1`).
* **Tapping a receiver,** in the list or on the map, opens its call card, after adding the receiver's grid from the spot to the shared callsign-grid cache (`learnGrid()`, `callinfo.js`).
* **Every call card shows what PSKReporter has of that station hearing us** (`callinfo.js`, `opts.heardUs`, from `PskrCore.heardBy()`): a **PSKReporter: heard you** section, a line per band with its newest SNR, age and report count. It appears only when there are such reports, on any card: a decode, a QSO, a map pin. A station with no cached grid gets the locator from its report.

## The SWR sweep

`swr.html`, reached from Tools ([radio.md](radio.md), **The SWR sweep on the main board**): tune an antenna in the field. The bands ticked are swept by the main board through the QMX, one short carrier per point; the page plots what comes back. The CAT sequence and what the radio refuses: [radio.md](radio.md) (**QMX SWR Tune over CAT**); the wire: [sidekick.md](sidekick.md) (**Port A**, v4).

* **The plan is the page's.** `bands.js` (shared with `app.html`, which used to hold the table inline) gives the band edges; `swr_core.js` turns the ticked bands into `(lo, hi, step)` ranges, about 10 to 20 points a band (the step table is there), **Fine** halves every step. The ranges go to `POST /api/swr/start`. The host's three numbers (800 ms a point, 200 points, 12 ranges) are read from `swr_sweep.h` by `webapp/tests/test_swr_core.js`, so the estimate and the refusal cannot drift from the firmware. 2 m is left out: its edges do not fit the wire's 16-bit kHz.
* **Bands default to `active_bands`.** The ticked boxes open as Settings has them (`defaultBands()`), and only bands a QMX could have are offered.
* **The estimate and the countdown.** "About 1:14 (93 points)" before a run; while it runs the page counts the points still to do at the rate measured so far (the estimate until two have arrived), and a band the radio reports it lacks leaves the count.
* **One plot** (`plotModel()`, drawn as SVG): frequency across the swept bands only, each as wide as its span with a floor so a 50 kHz band is not a sliver, a vertical line at every band boundary; SWR from 1 to 6 with a dashed line at 2. **No point is drawn where there is no measurement, and the line breaks there.** A reading above 6 sits on the top edge as a red triangle. A band the radio does not have is labelled **not swept**, so a missing band never reads as a pass. Each band's minimum is named, and a table under the plot gives each band's lowest SWR, where, and the share of points at or below 2.
* **The previous run** is kept in `localStorage` (`microft8_swr_prev_v1`, readings only) and drawn faintly behind the next: run, adjust the wire, run again. A per-phone convenience, never the record.
* **Landscape is recommended, not required.** A page cannot force an orientation (iOS Safari has no `screen.orientation.lock()`), so in portrait a line says "Rotate your phone for a wider plot" and the plot draws at the width it has. Rotating re-lays out the readings already held; it never restarts a sweep (tested).
* **Starting asks first** when it would end something: the host refuses over a queued CQ or QSO, a transmission or Tune, and the page then asks in the words of a band change ("A sweep ends your QSO with K9ABC, your CQ. Receive is also interrupted while it runs. Continue?"), ends them through the existing endpoints (`/api/tx/cancel`, `/api/queue/cancel`, `/api/radio/tune`) and starts again. **Stop** is `/api/tx/cancel`.
* **Events are polled**, so a phone that sleeps through a sweep misses points; they are shown as missing, never as zero. The page polls every 400 ms while a sweep runs.
* **Run against a simulator:** `python3 tools/serve_webapp_local.py --sim` serves the page with `sim_station` behind it, which runs the real sweep against a fake QMX that reads like a 40 m end-fed half-wave (bands 40 to 10 m; 160, 80, 60 and 6 m refused).

## The map

`map.html`, reached from Tools: a full-screen map with independent layers (QSOs, decodes, POTA/SOTA spots) over a bundled basemap. **Only QSOs is on when the map opens**; every other layer starts off, and a layer that starts off fetches nothing until it is tapped on (operator decision 2026-10-08).

* **The PSKReporter layer** (**Who hears me**, above) puts one pink diamond on each receiver's newest spot within the "Over the last" window, with a path from our grid. While the layer is on, the page listens too. The note counts the stations and says when PSKReporter is unreachable.

* **A vector basemap, not tiles.** Natural Earth 110m files (land, countries, lakes, US states, places; public domain) are bundled in `webapp/app/` and served by the sidekick, so the map works offline. Tiles cannot be cached on this origin, so a tile map would be blank exactly where the radio must work; and what the map shows (grid squares, station pins, great-circle paths) gains nothing from roads or imagery. Coordinates are rounded to 2 decimal places (~1 km), and each file stays under the 512 KB per-file limit.
* **Hand-rolled canvas, no framework.** Equirectangular projection with **one scale for both axes, cropping rather than distorting**: the base scale is `max(w/360, h/180)`, so the view always fills the canvas, like CSS `background-size: cover`, and never zooms out past it. Pan by drag, zoom by pinch (anchored at the midpoint) or wheel; longitude wraps at the antimeridian. Great-circle paths use spherical interpolation and split where they cross the antimeridian.

## Build

`webapp/app/` holds the hand-edited sources; what Pages serves and the sidekick installs is their build, `webapp/dist/app/`, produced by `webapp/tools/build.py`. Pages, CI's Host tests and `desk_push.py` all run it, so what is tested is what ships. `desk_push.py --usb` installs the same build with no network: `webapp/tools/usb_push.py` packs it into a LittleFS image (the firmware's block size, `name_max` 64 and 512 KB file cap) and `esptool` writes it to the `web` partition. It replaces the whole filesystem and leaves NVS alone; the next boot re-hydrates the seed pages. Needs `pip install littlefs-python`. Neither the output nor its manifest is committed: a committed manifest had to be regenerated by hand after every edit, and it was forgotten twice.

In order, the build:

1. copies the sources;
2. stamps the build id (`<short sha>[-dirty] <UTC date>`, dirty meaning `webapp/app/` has uncommitted changes) over `app.html`'s one `__APP_BUILD__`. Settings' **App** line shows it beside the FNV-1a self-hash, and an unbuilt page shows `source`;
3. minifies every `.html` and `.js` (`minify.mjs`: html-minifier-terser and terser, versions pinned in `webapp/tools/package-lock.json`);
4. compile-checks every script with `node:vm`, compacts the JSON data files, and writes `manifest.json` from the output;
5. fails if a file exceeds the sidekick's 512 KB per-file limit or the bundle exceeds 800 KB.

**Minification is conservative on purpose.** Top-level names are never renamed: the pages share globals across files (`CallInfo` from `callinfo.js`, `MicroFT8Pairing` from the sidekick's `/pairing.js`), and a readable top-level name is what makes an error on a device traceable to the source. Whitespace collapses to one space, never to none. A file the minifier would grow ships as it is. The first build took the bundle from 637 KB to 469 KB (73%).

**The 800 KB budget** comes from the `web` partition (1,920 KB). An install stages a second copy of the bundle before renaming it into place ([sidekick.md](sidekick.md), **Installing the app bundle**), and the reference store's proposed cap is 256 KB ([RFC 0008](../rfcs/0008-activator-mode.md) §4.2): 2 × 800 + 256 leaves 64 KB for the bootstrap pages and LittleFS overhead. Raising the budget means shrinking the store cap.

**Previewing:** `tools/serve_webapp_local.py` serves the sources at `/app/`; with `--dist` it serves the last build there instead, which is how a minifier problem shows up before a push. Without `--sim` there is no sidekick behind it, so the pages load and render but no API call succeeds; a bench check still needs `desk_push.py`. `--sim` proxies `/api/` to `host_mock/sim_station`, which plays `host_mock/test_qso.json` (or `--scenario`) on a real 15 s clock (`--scale` divides that wait) and serves the same event JSON the sidekick does. Open `http://127.0.0.1:8787/app/app.html`. The simulator's pairing window stays open, so the page pairs without a button press. That is a scripted station, not a radio: USB, CAT, and audio timing are not what it exercises.
