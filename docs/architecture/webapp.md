# Web app architecture

The web app (`webapp/app/`) is the station's only UI on the headless P4, served by the sidekick ([sidekick.md](sidekick.md)) and run in the phone's browser. System context: [system.md](system.md).

## Screens

**Operate / QSOs / Tools / Settings** are four tabs, switched from the tab bar (`app.html`, `#tabbar`), with no swipe between them and no title row above them (operator decisions 2026-10-25). **A shortcut may land on a tab where it saves a step toward something the operator is already reaching for** (operator decision 2026-11-11); there are two: the slot bar's row, tapped on any tab, goes to Operate (**Operate's pinned regions**), and the CQ row's gear and the drawer's **Station ›** go to Settings' Station page (**Settings › Station**). The title row held only the title, a pairing badge and the Settings gear, and its height went to the decodes. Not paired shows as a radio bar state and a dot on the Settings tab (**The radio bar**).

**Every action reports where the operator is looking.** Operate has no status line and no banners (operator decision 2026-10-25): what an action changes shows where it changed (the radio bar, a row, the queue), progress and "ok" are not reported, and a failure's reason is a toast at the bottom for 6 s, above the tab bar and Operate's pinned bottom (`failMsg()`, `showToast()`; the Undo after a reply is the same toast). A lost link is the radio bar's No contact state (**The radio bar**). A newer app build is offered in Settings › Software update, with Reload (`checkAppStale()`). Settings has no status line either (operator decision 2026-11-11: the line sat over Settings' menu and every page, repeating "ok"); `setMsg()` is gone, and `failMsg()` is the toast alone, which shows over Who hears me's list too. Settings has no Save button for the station: each field writes its own key when it changes (blur or Enter for text, a pick for a menu, a tap for a band), and a refusal is a toast with the reason, the field reloaded to what the station holds. The sidekick's own network keeps its Save, since saving restarts it. What stays a message beside its control: the sidekick actions' own lines (`#netMsg`, `#apMsg`, `#tokMsg`, `#resetMsg`, `#updMsg`), and Set from GPS's progress, under the Grid field (**Settings › Station**). A log download or clear that fails is a toast; it used to write to Settings' line, unseen from QSOs.

* **Operate** pins its status above the decodes and its controls below them, so only the decode list scrolls (**Operate's pinned regions** below): the slot bar on top; the queue (**The CQ row** below) and the radio bar (**The radio bar** below, with band and frequency in its drawer) at the bottom.
* **Grow by destination, never by feature.** QRZ is not a screen: per-callsign data expands on the row it belongs to. One shared expand-on-tap component, used on decode, queue and QSO rows, shows **offline-derived** facts at once (DXCC and zones from the prefix, distance and bearing from grid arithmetic) and **online-enriched** ones (QRZ bio, photo) when reachable, failing legibly when not.
* **QSOs is one continuous list** with day dividers ("Today", "Sep 13"), not a day-file picker. The main board keeps one ADIF file per UTC day; the list loads the current day on open and older days as the operator scrolls (`FILE_LIST`/`FILE_READ`), because Port A's budget cannot carry the whole log on every open. **A new QSO shows at once:** the main board writes it as our RR73, RRR or 73 starts, so a TX event turning active with such a message (`txLogsQso()`) reads today's file 0.5 s and 2 s later (`kickLogRefresh()`), as does opening the tab; an 8 s poll while the tab is open (`refreshLogHead()`) is the backstop, and a refresh asked for while one runs is run again after it rather than dropped. Each read crosses Port A, so a stalled sidekick still delays it (row [dlu3](../ROADMAP.md#dlu3)). **A log read is given up after 10 s** (`logFetchJson()`, which every read of the log in `app.html` goes through; host-tested by `webapp/tests/test_log_timeout.js`): one in flight when the sidekick restarts may never settle, and each reader holds a busy flag while it waits, so a single such read froze the list until a reload (2026-11-11, 44 s in Chromium). The next poll reads again, and a day's rows that failed to load are not kept. A line under the toolbar shows the main board's log storage, "N MB free of M MB", from the live `storage_total_kb` / `storage_used_kb` config lines; it is hidden while the board has not said, and red under 10% free. Each row's second line names the QSO's band, mode and frequency as a decode batch's header does, "20m FT4 · 14.080 MHz" (`qsoBandText()`), so FT8 and FT4 contacts read apart.
* **The callsign card's POTA / SOTA row says when the call was heard calling CQ POTA or CQ SOTA** ("Called CQ POTA here · 20m FT8 · 3 min ago"), beside the internet spots and before they load, so an activator nobody has spotted still shows as one, offline included. Every decode is offered to `learnCq()` (`callinfo.js`), which keeps the newest sighting per call for the UTC day in this browser's storage, at most 500 calls; a CQ decoded while no page listened is not seen. It is the first slice of Ideas [hw2z](../roadmap/ideas.md#hw2z) (operator, 2026-11-09).
* **The callsign card's QSO history comes from the QSOs loaded so far** (`qsoHistoryFor()`), so a QSO on a day not yet loaded is missing from it. Row [I32](../roadmap/ideas.md#I32) would answer it from the P4.

### The CQ row

The queue's last row, always present (`app.html`, `#opCqRow`), above the radio bar: the queued CQ, which is an ordinary queue entry with its own tries ([autoseq.md](autoseq.md), **Tries**), drawn here rather than among the QSO rows. It sits below the scrolling QSO rows, not inside them, so a long queue neither hides it nor loses rows to it. The queue's other rows read `queue`, the CQ row too, from the same `QUEUE_ENTRY` stream (`renderCqRow()`; the CQ is the entry whose call is `CQ`).

* **Call CQ** (`POST /api/cq`) when no CQ is queued. It keys the transmitter in one tap, as Reply does; the main board picks the parity and the tries, and both show once the CQ is queued.
* **Once queued:** the parity, **Even ⇄** or **Odd ⇄**, which a tap moves to the other period (`POST /api/queue/parity`, for a strong station nearby); the count, `2/6 tries`, which opens the tries stepper (**Tries on a queue row** below); and **×**, which ends the CQ, stopping one on the air in the same press (`POST /api/queue/cancel`; the P4 stops a cancelled entry that is on the air, [autoseq.md](autoseq.md), **The slot cycle**).
* **Arrangement:** the Sends text over the status line on the left, the controls on the right, then a gear (`#cqSettingsBtn`, labelled "CQ settings").
* **The Sends text** mirrors autoseq's `generate_cq_text_into()` (`components/autoseq/autoseq.cpp`): the type's prefix (`CQ`, `CQ SOTA`, `CQ POTA`, `CQ QRP`, `CQ FD`) plus the call and the grid's first four characters, or the free-text field verbatim for a Free-text CQ. Tapping it, or the gear, opens Settings on its Station page (**Settings › Station** below).
* **The status line** reads "Not calling"; "Calling · even/odd slots" when the CQ is queued and the queue holds no other station; or "Waits for the queue · even/odd slots" once a real QSO is active, since every live QSO outranks a CQ ([autoseq.md](autoseq.md)).
* **Stop, during our own CQ, ends the CQ too.** The radio bar's Stop reads **Stop CQ** while the CQ is what's on the air, and posts `/api/tx/cancel` then the CQ's `/api/queue/cancel`; during a QSO message it reads **Stop TX** and only cancels that transmission. Which one is decided from the text on the air (`txIsOurCq()`: it starts with `CQ `, or is a Free text CQ's `free_text`), never from the queue: the CQ stays queued behind a QSO that answers it, while our report is what transmits. Otherwise the CQ stayed queued and the next one went out a cycle later regardless of the operator's tap.

### Tries on a queue row

Every queue row's count is a button, `2/6 tries` (tries sent of the limit, [autoseq.md](autoseq.md), **Tries**), reading `· custom` when the entry has a count of its own. A tap opens the tries stepper (`#opTriesEdit`), static markup under the CQ row for the reason the CQ row is static: the QSO rows are rebuilt on every poll.

* **The stepper** is `[−] n [+]`: − and + repeat while held (`holdRepeat()`: after 450 ms, every 100 ms), and the count is not typed (operator decision 2026-10-14). Buttons carry `touch-action: manipulation`, so quick taps do not zoom the page on iOS. It names the entry and what its count bounds ("K9ABC · tries at each step", "CQ · tries in all") with the tries already sent, and steps 1–20 for a QSO, 1–99 for the CQ. A change applies on its own about a second after the last tap (`POST /api/queue/tries`, "`<entry_id> <tries>`"), since an Operate control takes effect when touched (**Why not, on Operate**). **Use default** sends 0, and the entry follows Settings › Station's Tries again.
* **A count at or below the tries already sent ends the entry**, so the stepper does not send it on its own: it says so ("2 already sent: this ends this step, after the try on the air if there is one.") and waits for **End it**.
* **Done** closes it, and so does the entry ending.
* **The CQ decode color** (`--good-hot`, `.c-cq`) is `#007a00` in light mode, `#4ade80` in dark. The light value was `#00c800` (about 2.3:1 on white), which fails WCAG's 4.5:1 text-contrast minimum.

### Operate's pinned regions

Operate keeps its status on top and its controls at the bottom, and only the decode list scrolls. Decodes are the scarce resource on a phone, and every control touched mid-QSO stays in thumb reach however long the list grows on a busy band (operator, 2026-10-24).

* **Why they sit outside the Operate panel.** Each tab is its own scrollport (`#viewTrack > section`), and the three tabs slide on a track moved by a CSS transform, so neither a sticky nor a fixed element inside a panel stays on screen. The top region (`#opTop`) sits at the top of `#viewport`, outside the track, and shows on every tab (operator decision 2026-10-26: "am I on the air, and is RF going out" matters on QSOs and Tools too, and a row that stays put keeps tabs from jumping); every panel starts below it (`--optop-h`). The bottom one (`#opDock`) is a fixed sibling of the tab bar, hidden off Operate (`body.on-operate`), and `#view-operate` alone ends above it (`--dock-h`). `layoutDock()` measures both and the tab bar. The map and SWR sweep pages are separate pages and have no slot bar. A hidden region reports 0 and the last height is kept, so leaving Operate does not resize the panel and clamp its scroll.
* **Top, on every tab:** the slot bar, with a tag at its left for the parity of the slot now, **E** or **O**. A tap on its row goes to Operate from any other tab, since that is where Stop is when the bar turns red, and on Operate scrolls the decodes back to the newest slot (`slotRowTap()`); the row is a button to a keyboard and a screen reader. The bar is 18 px whether or not we transmit, so the row never changes height. Its countdown runs while audio arrives (`radioLive()`), CAT or not: the HL2 has none. With no audio it still counts the slot and says why (**The slot bar's receive cues**); only with no word from the main board is it blank. It fills over the slot, full height while we receive too: the station strip's white ticks read over the blue fill (operator decision 2026-10-27, after trying the fill as a thin line along the top), with a cyan cursor at the TX offset and, while we receive, a strip of where the stations are on the same axis and an approximate signal count, or the clock cue (**The slot bar's activity trace** below); red while we transmit, with the readout inside it (`txReadout()`: "4.9 W · SWR 1.30" from the TX HUD event, "Tune · …", "— W" before the first reading, "Write blocked"); amber while TX is halted, or with "0.0 W · no RF" when a keyed transmission still reads 0 W 1.5 s in, past its first tone and meter reply: the radio is keyed and sending nothing, and the SWR it reports then means nothing (operator decision 2026-10-26). At an activation, one line under it (**Activation progress** below). The decode count and the CAT, Audio and Link checks are in the drawer's status line.
* **The Decodes bar** (`#dvBar`) is sticky at the top of the scrolling list.
* **Bottom, top to bottom:** the QSO rows, one line each (call, `n/N tries`, state, ×), about two showing before they scroll in place, with no label and no empty line; rows scrolled out of sight show as a fade and a count at that edge, "+2 more ▾" below and "1 above ▴" above (`renderQueueMore()`, operator request 2026-10-25), which take no taps; the CQ row; the tries stepper while open; the radio bar; the drawer while open, below the bar.
* **Measured** in the browser at 402 × 874 pt, the iPhone 17 Pro's screen, on 2026-10-26, with no title row or status line: the decode list under the Decodes bar is 512 pt closed with two QSOs and an activation line (the canvas drew about 510). With the drawer open it loses about 190 pt (the canvas's drawer was about 150; this one adds the radio's line). On the phone, Safari's own bars take more; the layout passed the operator's phone check on 2026-10-26, unmeasured there.

### The radio bar

The bottom row of Operate (`#opRadioBar`): the band and frequency, a sub-line, and on the right a label, or **Stop** while something is on the air. It shows one state, highest first (`radioBarState()`, host-tested by `webapp/tests/test_radio_bar.js`), each with a glyph as well as a tint:

1. **On the air** (red): the band and frequency, and under them "Sending" with the message and the offset. Power and SWR are in the slot bar (**Operate's pinned regions**). **Stop CQ**, **Stop TX** or **Stop Tune** takes the label's place and is its own tap target, never the drawer toggle (`#rbStop`; **The CQ row** says what each stops). Tune reads "Tuning".
   - **CAT lost while on the air keeps this state** (decided 2026-10-25), so Stop stays under the operator's thumb; the sub-line ends "· CAT lost". The state ends with the TX HUD event's falling edge, or 3 s after the last event (`expireStaleTxHud()`), and the bar then shows CAT lost.
2. **A transmission that did not go**, with no Stop since nothing is on the air: **SWR protection tripped** (red: "Stopped, not sent · K9ABC tries next slot"); **Stopped: SWR tripped twice** (red: "CQ ended · queue cleared · check the antenna"), kept until the next transmission starts, since the main board stays stopped until the operator calls CQ, replies or tunes ([radio.md](radio.md), **SWR protection trips on a QMX**); **TX aborted** for another reason (red); **Not keyed** (amber: "Not counted: <reason>"), a TX HUD event with its `nk` flag when the clock was unset, CAT was not ready or SWR protection held the slot. `noteTxHud()` counts tripped transmissions in a row as the main board does: once per transmission, and a clean one resets the count.
3. **Main board not connected** (red: "Check the cable between the boards and the main board's power"), when the sidekick answers and says it has no main board (`mainBoardAway()`): its `host_linked`, from the main board's HELLO, rides on every config reply, one the main board did not answer included ([sidekick.md](sidekick.md), **Port A**), so the page knows from its first poll and not after a timeout. It is its own state because the fix is a cable, and because it is what a new operator sees who powers the sidekick first. One sentence says it everywhere (`noMainText()`): the drawer; a toast when Call CQ, a reply, Tune or a Settings write is tried, none of which is sent; the QSOs list; and the Station, Radio & bands and Amplifier rows of the Settings menu, in amber. Settings › Station still shows the values this browser last saved, marked as such. It clears with the first reply that says a main board is linked. Then **No contact with the station** (red; a firmware update has no state of its own here, since the page following one shows its progress sheet over every tab, the bar included: **Settings › Software update**), then **Not paired** (amber: "Not paired · press the sidekick's button"; this phone can watch but not transmit or change anything, and the Settings tab carries a dot; `paired()` is whether a token is stored, so one the sidekick rejects shows at once), when nothing has answered for 30 s (`linkLost()`): the browser not reaching the sidekick, or a main board that is linked and has stopped answering; the drawer says what to check. A page that has never had an answer says it too, 30 s after it loads. It clears with the next answer. Then **a radio problem**, from `radioChipState()`: **Found · syncing** (the device is there, CAT and audio are not both up; the HL2, until its stream is up), **Receive only** (the HL2 streaming: it has no CAT and no transmit yet, so it is never CAT lost), **HL2 busy** (amber: another program has its stream), **Stream lost** (red: it streamed this session and stopped, the HL2's CAT lost); for the HL2 they come from the main board's `hl2=` (main_board.md, **Ethernet**), and an HL2 with no link or no answer is **No radio**, the slot bar saying which and **Radio moved** (the radio reports a frequency, mode or split other than the one the main board set; while Tune is on, the mode is not checked, since the QMX reports its SWR Tune carrier as CW) amber; **CAT lost** (CAT was up this session and stopped) and **Not decoding** (the main board's decoder could not start) red; **No radio** and **Unknown USB** (a device that is not the QMX) grey. The label becomes the way to the actions: "Review ›", "Radio ›".
4. **Ready**, quiet: "QMX ready", and at an activation "· 3 refs · 0000Z 3h12m", the time to 0000Z, when a POTA activation's day starts over.

**The drawer** (`#opDrawer`) opens from the bar's chevron, body or label (`setDrawerOpen()`) and asks the radio for its state. It opens below the bar, so the bar rides up to the top of the open section, and it slides open and closed (its one grid row animates from 0fr to 1fr in .25 s, with no motion under the system's reduce-motion setting; operator request 2026-10-25). While closed it is `inert`, out of the tab order and VoiceOver. Open, the bar turns blue, the chevron fills and points down, and the label reads **Close**. A band is two taps (operator decision 2026-10-25). Top to bottom:

* **A problem state's note and actions first:** **Put it back** and **Use it** when the radio moved, **Retry now** when CAT is lost, **Retune VFO** when not decoding.
* **The band grid and the frequency row** (**Band and frequency** below).
* **The status line:** the CAT, Audio and Link checks, the decodes in the last 5 minutes, and **Station ›** (**Settings › Station**).
* **What the radio said:** in Ready, one line (the device, its firmware, what it reports) with **Retune VFO** and **Tune**; in a problem state, its rows.

The rest of radio state:

* **Found shows at plug-in.** The main board announces the device when the USB host first sees it, not when CDC opens about 11 s later (`qmx_transport.cpp`, `track_usb_presence()` and the descriptor callback): `USB_STATUS` attach, with VID/PID `0` when the device is there but not yet named. An attach whose device leaves before CDC opens is cleared by the same task, since no CDC disconnect comes.
* **Read-back.** `POST /api/radio/read` sends the `RADIO_READ` action; the main board sends `IF;` (`radio_control_query_state()`) and the parsed reply (frequency, TX/RX, mode, split) rides in the config snapshot as `radio_hz`, `radio_tx`, `radio_mode`, `radio_split`, with `want_hz`, what the station means the VFO to be (during a transmission that retuned the radio, the dial it retuned to: [radio.md](radio.md), **TX timing on a QMX**). A sync asks too. Never during a transmission or Tune, and never polled: the page reads when the drawer opens, and the radio pushes the rest (next bullet). The `IF;` layout parsed is the Kenwood TS-480 one the QMX follows (`components/radio_control/cat_reply_parser.cpp`); it is host-tested but unchecked against a real QMX (TEST_PLAN, Pending).
* **Pushed state.** The main board sends `AI2;` once per connection (`sync_vfo()`, with the `VN;` read), and the QMX then sends `IF;` unprompted whenever its frequency, mode, TX or split changes. `cat_reply_parser` counts each `IF;` that differs from the one before (`if_changes`); `porta_p4_radio_push_tick()` sees the count move and sends one `RADIO_STATE` event (`PORTA_EVT_RADIO_STATE`, at most one per 100 ms) with what the radio last said. The sidekick serves it in `/api/events` as `"d":7` (`hz`, `tx`, `md`, `sp`, and `want`, the wanted dial), and the page puts it where the poll would (`applyRadioPush()`), so the bar follows a knob turn at once; the next poll carries the same values. The tick holds back during a sync and 150 ms after, and likewise while a transmission has the radio retuned (`radio_control_tx_retuned_hz()`), because the radio answers each command we send with its state and those are not its own doing. **The page compares what the radio reports only with the wanted dial sent with it.** The poll carries both (`radio_hz`, `want_hz`), and so does the push (`want`, from the same `want_dial_hz()` on the main board), and `applyRadioPush()` sets them together. During a transmission that retuned the radio, the wanted dial is the retuned one; the radio's push when the dial came back, read against the previous poll's wanted dial, showed **Radio moved** for up to a poll (the 40 m FT4 field check, 2026-11-09), so two values from different moments never meet. The drawer-open read stays for firmware that does not answer `AI2;` (it replies `?;`, which the parser ignores). There is no `AI0;`: the P4 has no clean stop to send it from, and a QMX power cycle clears `AI2;`. Host-tested by `host_test_cat_reply_parser`, `host_test_porta_proto` and `webapp/tests/test_radio_push.js`; the sync gating and the radio itself are field-only (TEST_PLAN, Pending).
* **Firmware version.** The main board asks `VN;` once per connection (after the first sync) and the parser keeps the answer until the radio goes; it rides in the config snapshot as `radio_fw`, and the drawer shows it ("FW" on Ready's line, "Radio firmware" in a problem state's rows). A QMX answers `VN1_04_003QMX;` (the release and the model run together, read on the bench 2026-10-24), shown as `1.04.003 (QMX)`.
* **Actions.** **Retune VFO** (**Put it back** when the radio moved) is the old Connect: sync the Station band, Digi, VFO A. **Use it** saves the radio's frequency as that band's frequency. **Tune** sends a carrier, with power and SWR large on the bar and in the drawer while it is on. **Retry now** when CAT is lost is the same sync, refused while CAT is down.

### Decode rows and tap to reply

Each decode row is two lines, about 51 pt. The first is the message at 1.05rem, with the → ME badge kept whole, and the SNR in bold mono right-justified at its end. The second is one mono line: DT, the place (a link to the map at the station's grid, cut short with … when long) and the distance at the right. The grid itself is on the station's card, and so is the bearing, which Settings' **Show the bearing on decode rows** (this phone only, off by default) adds to the row (operator requests 2026-10-25 and 26: DT is acted on more than the grid). Nothing shares the message's line but the SNR, so it does not wrap: measured at 402 pt with "-24 dB" on every row, every FT8 message shape tried fits, where beside a fixed 172 px number column 13 of the same 16 wrapped. Two cases still wrap, their badges going to the next line: a compound call to us (`KB2SLO <PJ4/K1ABC> RR73 → ME`), and a long message carrying both activation badges. A decode's audio offset is not on the row: the station's card lists it beside each decode heard this session (decided 2026-10-25: it is a detail of one station, and the card is where a station's details are). The slot header is one line: band and frequency, then the slot's span without the date, and its age ("14:02:30–45z · 6s ago", `fmtSlotTime()`). It sticks under the Decodes bar while its slot is on screen (each slot is its own `.dslot` box, so the header lets go when the slot ends), so the slot being read keeps its time in view.

**Rows never move under a finger** (operator request 2026-10-25). A new slot arrives at the top, and a tap that landed as the list shifted would reply to a different station. So a redraw waits while a finger is on the list, for 600 ms after it lifts (the tap's click comes after the lift), and while the list still coasts from a flick (`decodeRedrawHeld()`), then runs once. A redraw the operator's own reply asks for (Sending…) runs at once.

* **Tap a row to reply.** There is no Reply button. A row replies when its message is replyable (`isReplyableDecode()`: a CQ, or a closing 73 or RR73) on a slot still open for a reply (`slotReplyOpen()`), and no reply from it is sending or queued (`decodeRowReplyable()`). Such a row ends in a blue › and is a button for assistive technology, labelled "Reply to <call>: <message>". Its callsign and grid links keep their own taps (`decodeTapAction()`), with hit areas padded without moving the text. A row that is not replyable has quieter text and no ›; a message to us keeps its colour and badge. One listener on `#opDecodeRows` serves every row, so a row rebuilt by a poll keeps its tap. A tap meets the same refusals as before: a slot that aged out, and a decode heard on another frequency (**Band and frequency**). Host-tested by `webapp/tests/test_decode_tap.js`.
* **Feedback** (`sendReply()`). The row says **Sending…** at once; the sidekick holds the POST until the main board accepts or refuses, about a second. Accepted, the row is tinted, with a **Queued** badge after the message in place of the ›, and a dashed placeholder for the sender's call stands in the queue until a `QUEUE_ENTRY` for the same call arrives (matched on the call, no protocol change); a call already queued is highlighted instead. A refusal, or no entry within 10 s, removes the placeholder and shows the reason under the row with **Retry**. The row is tappable again once the queue entry goes away. State is `replyState`, reconciled by `reconcileReplies()` on each queue render and once a second.
* **The queue in the decodes** (operator request 2026-10-26). A decode that names a station in our queue (never our CQ entry, `queuedCalls()`) says what it means for that QSO (`queueInvolvement()`): the station is calling **CQ again**, **Working** someone else, **Done with** someone else (73 or RR73), or **Called by** someone else. The row gets an accent bar at its left edge, that station's call in bold, and the phrase on its second line in place of the place; no filter hides it, and it sorts right after messages to us (`decodeViewOf()`'s `involves`). A message to us from a queued station is already red with → ME and gets nothing more. Each queue row repeats the newest such phrase, with its age, while that slot is under two slot lengths old (`queueLastHeard()`, "Working W1XYZ · 6s", or "→ you"); within a slot, what the station sent outranks someone else calling it. WSJT-X gives this its own pane; on a phone it is a mark on rows already shown. Settings' **Mark decodes about stations in the queue** (this phone only, on by default) turns all of it off: the marks, the filter pass-through and order, and the queue rows' cue. Host-tested by `webapp/tests/test_queue_cues.js` and `test_decode_view.js`.
* **Undo.** An accepted reply to a call not already queued shows a toast, "Queued K4XYZ · Undo", for 5 s. **Undo** cancels that entry (`POST /api/queue/cancel`); an entry not in the queue yet is cancelled when it arrives, or forgotten if none comes within 10 s. A call that was already queued gets no Undo, since cancelling would end the QSO that was there.

### Decode sort and filter

The Decodes bar (`#dvBar`), sticky at the top of the list: the label and one non-wrapping row of same-shape pills, filled when active. **Sort** opens its four choices: Default (the order `decodeSortCmp()` stored: decodes to us, replyable lines with CQs strongest first, the rest, recent partners), Strongest (SNR), Nearest or Farthest (distance from the Station grid, for DX); it applies within each slot and slots stay newest first, because replies go to the newest slot and the 15 s rhythm stays readable. A decode with no known grid sorts last under Nearest and Farthest. **Filters** combine: **Replyable** keeps the lines a tap replies to by `isReplyableDecode()` (a CQ, or a closing 73 or RR73), whatever the clock says, and POTA/SOTA (`CQ POTA`, `CQ SOTA`). There is no distance filter: Nearest and Farthest already order by distance, and a filter hid every decode with no known grid. A message to us stays on top and is never filtered, and a decode naming a station in our queue comes next and is never filtered either (**Decode rows and tap to reply**). The choice is kept per browser (`localStorage`, a per-viewer convenience), and "N/M" (shown of all) sits right-aligned in the row while any decodes are on screen. Applied when a slot is drawn (`decodeViewOf()`), so changing it re-sorts what is on screen; host-tested by `webapp/tests/test_decode_view.js`. A New filter waits on row `I32`: the app knows only the log it has loaded.

### The slot bar's activity trace

While we receive, white ticks rise from the slot bar's floor where stations are: the bar's width is the passband, 200 to 3000 Hz, the same axis as the TX cursor, which is cyan so the two are not confused (`activityStrip()`). Each tick is one of the main board's 28 Hz frequency cells ([decode.md](decode.md), **Band activity**), as tall as the share of the slot's signal span heard so far that the cell or a cell beside it held a signal, so a station on for the whole slot stands full height, about 85 Hz wide, and a fading one shorter. **Why the neighbours count:** an FT8 signal hops among 8 tones over 50 Hz, so one 28 Hz cell holds it about half the time, and a steady station drew as two or three half-height ticks. Counting the neighbours, decodes standing under a tick of half height or more went from 18 of 29 to 27 of 29 on 40 m, and to 54 of 57 over the next six slots (2026-10-27). A cell held under `ACTIVITY_STRIP_MIN` (20%) of the span is noise and is not drawn. The strip shows where the stations are and whether our offset sits among them or in a gap. **Why frequency across, not time:** every FT8 station transmits for the whole slot, so on a real band a level per block is flat from 0.5 s to the end (2026-10-27); time across carried nothing the fill does not. Inside the bar, where the TX readout goes while we transmit, the text reads "≈N signals" (`activityLabel()`): the median level of the blocks heard so far from 0.8 s to 70% of the slot, inside every signal in both modes, so a gap between stations or one burst does not move it (`activityCount()`). **Quiet** at 2 or less: with the antenna off the QMX's own noise reads 1 or 2 (2026-10-27). "≈30+ signals" from `ACTIVITY_COUNT_CAP` up, where the count flattens. It counts signals heard, decodable or not, so it is "≈" and is not the decode count. On 2026-10-27 it read within about 4 of the decode count on busy 20 m (22–28 decodes) and within about 2 on 40 m (6–11).

**The clock cue.** Signals heard and nothing decoded is what a clock too far off looks like, and an empty band, a dead antenna or no audio do not look like it: they hear nothing. When the last two received slots each heard `CLOCK_CUE_MIN_SIGNALS` (8) or more and decoded a quarter of them or fewer, the bar's text turns amber and reads "Clock? N decoded of ≈M signals" (`clockCue()`). `noteBandEvent()` keeps the tally: FT8's decodes per slot (an FT4 decode, `sl` 75, counts toward none, since activity is FT8's slots), and a slot is closed when the next one's activity arrives, by which time its decodes are in. A slot we sent in has no count and is skipped, so the two slots need not be adjacent; a slot the main board did not decode breaks the run, read from its `PAUSED <slot>` or `SKIP <slot>` log line. `SKIP` is a slot deaf by overlap: one an FT4 transmission fell in still hears signals, and counted as a failed decode it cued "Clock?" every slot of an FT4 QSO (2026-11-08). These are Port A log lines the app parses, so moving per-slot logs off Port A (row [p8yv](../ROADMAP.md#p8yv)) must give the app another way to know. The cue never touches the clock. On 2026-10-27 a reflash left the clock about 1.6 s off for ten slots: about 20 signals each, 0–2 decodes, and the decodes' DT −1.5 to −1.6 s. Auto-sync could not recover it, since it steps only from a slot with four decodes. A real band decoded 0.6 to 1.2 of its signals. `webapp/tests/test_band_activity.js` replays that session (`webapp/tests/fixtures/clock_off_2026-10-27.jsonl`, slots, decode counts and levels only) and checks the cue is on for exactly those ten slots.

FT8 decodes only arrive at the slot's end, so the bar is the first word on whether anything is on the band and how busy it is. The sidekick serves each `ACTIVITY` event in `/api/events` as `"d":8` with `si` (the slot), `bm` (block ms), `b` (the first block), `lo` and `hi` (the span the cells cover, Hz), `v` (the levels) and `m` (each block's cell mask, hex in wire byte order, cell 0 in bit 0 of the first byte). `noteActivity()` keeps one slot: a later slot starts over, an earlier one is dropped. `activityStrip()` draws only when that slot is the one the bar shows, on the phone's clock (as the fill is, [time.md](time.md)). Nothing is drawn while we transmit. Activity is not state: a reload draws from its next event, so the slot it reloads in is partial. The bar stays 18 px (**Operate's pinned regions**). A time-and-frequency waterfall would need more height; the masks are what one would draw from (**Decisions a reference app would make differently**, Waterfall). Host-tested by `webapp/tests/test_band_activity.js`; the station simulator sends made-up activity, so `tools/serve_webapp_local.py --sim` draws it.

### The slot bar's receive cues

The bar says why this slot is not decoding, in the clock cue's amber, first match wins (`rxCue()`, then `clockCue()`): **No audio** and why (the HL2's transport state: "no Ethernet link", "HL2 not answering", "HL2 busy, another program has it", "HL2 found, starting", "stream lost"; the QMX's: "QMX not connected", "QMX connecting", "QMX audio down"); **Not decoding · decoder could not start**; **Overload · ADC clipping** (the HL2 clipped with its LNA already at its floor, within the last 15 s); then the clock cue. With no audio the bar counts the slot on the phone's clock and draws no activity. `webapp/tests/test_rx_cue.js` holds the cues and the HL2's chip states.

### Band and frequency

In the radio bar's drawer (**The radio bar** above), so a band is two taps: open the drawer, tap the band.

* **The band grid** (`#opBandGrid`) shows `active_bands`, one button of at least 44 px per band. Up to seven bands share one row with columns equal to the count (`grid-template-columns: repeat(N, 1fr)`, `buildDockBandGrid()`); more than seven wrap to a second row on their own, so no band is ever a swipe away.
* **A tap changes band at once** (`changeBand()`), asking first only when a QSO is queued or our own transmission is on the air ("This ends your QSO with K9ABC and stops the transmission on the air.", `confirmRetune()`), in the page's own dialog (`askConfirm()`, since a native `confirm()` often cancels silently on a phone; the update's review uses the same dialog and sentence, `endsClauses()`, host-tested by `webapp/tests/test_ask_confirm.js`), then cancelling both (`cancelQsosAndTx()`) and writing the band's standard frequency and `band_sel` in one PUT; the drawer closes. A "no" leaves the grid as it was and the drawer open — it never shows the new band until the write actually lands.
  - Settings > Amplifier > **Prime RF-sensing amp on band change**, off by default, makes a successful change send the bounded QMX SWR Tune pulse described in [radio.md](radio.md), **Prime an RF-sensing amplifier on a band change**. The P4 owns its timing; the browser only saves the option and requests the band.
* **A band tap always lands on the band's standard frequency** (`standardKhz()`, the app's table), never the last frequency typed there (operator decision 2026-09-28), including a tap on the band already selected; one already at its standard sends nothing. A typed or nudged frequency therefore holds only until the next band tap. Keeping chosen frequencies is row `y9js`.
* **The frequency row** (`#opFreqRow`): **−**, the operating frequency in MHz, **+**, **Set**. The field shows the frequency except while it is being edited (`syncFreqInput()`), so a poll never overwrites a typed value. There is no Standard button: a tap on the band already selected returns to its standard.
  - A typed value under 1000 is MHz, otherwise kHz, kept to 0.1 kHz (the station file stores tenths).
  - **Set**, Enter and the keyboard's ✓ / Done apply it, and a change that goes ahead closes the drawer; a refusal or a declined confirmation leaves it open with the typed value. Escape puts the frequency back. **On iOS, Done sends no key event** (operator request 2026-09-28), only closing the keyboard, so an edit committed with no tap just before it applies; a tap (Set, −, +, anywhere) reaches the page first and its own handler decides instead.
  - **Set**, **−** and **+** (1 kHz) write the operating band's own key (`band<N>`, or `ft4_band<N>` under FT4) with one `putConfigLine()` PUT; − and + leave the drawer open.
  - **A value in another active band always asks first** ("Change band to 20m? 14.080 MHz is on 20m.", plus what it would end; operator decision 2026-09-28), then cancels like `changeBand()` and sends that band's key and `band_sel` in one PUT, frequency first. A non-standard value, such as the calling frequency SOTA's FT8 advice asks for ([logging.md](logging.md), **What POTA and SOTA require**), holds until the next band tap; saving one to return to is row `y9js`.
  - A value outside every Region 2 amateur band, or on a band not in `active_bands`, is refused client-side (`bandForKhz()`) with the reason, in a dialog. The band edges (kHz, ITU Radio Regulations Article 5) are a sanity check, not a licence check; 60 m is one range spanning the US channels and the WRC-15 allocation:

    | Band | 160 | 80 | 60 | 40 | 30 | 20 | 17 | 15 | 12 | 10 | 6 | 2 |
    |---|---|---|---|---|---|---|---|---|---|---|---|---|
    | From | 1800 | 3500 | 5330 | 7000 | 10100 | 14000 | 18068 | 21000 | 24890 | 28000 | 50000 | 144000 |
    | To | 2000 | 4000 | 5407 | 7300 | 10150 | 14350 | 18168 | 21450 | 24990 | 29700 | 54000 | 148000 |

  - **A same-band change mid-QSO is treated like a band change** (operator decision 2026-09-28): the same confirmation, then the queued QSOs end and a transmission on the air stops before the new frequency is written. The partner is listening on the old frequency. Stopping the TX first also matters because a frequency the VFO cannot reach mid-TX is still saved, and nothing retunes the radio when the TX ends, so the bar would show a frequency the radio is not on. With nothing to end, no cancel is sent: a cancel also blocks a TX armed for the current slot.
* **Reply refuses a decode heard on another frequency** (`replyFrequencyMismatch()`; operator request 2026-09-28). A reply goes out on the frequency the radio is on now, so after a band or frequency change a decode from before it gets a dialog ("K1ABC was heard on 7.074 MHz, and the radio is on 14.074 MHz now…") and nothing is queued. The decode's own frequency comes from the main board (next bullet); the radio's now is the bar's. If either is unknown, the reply goes ahead.
* **The main board names each decode's slot and frequency** (Port A v2, [sidekick.md](sidekick.md), **Port A**). The app used to label a slot by what was current when its decodes arrived, a second or two after the slot ended, so headers missed the slot grid and a band change in that gap mislabelled a slot. Now each decode carries the slot it was recorded in (`si`, `sl`) and the dial frequency at the middle of its own signal (`fq`). The app groups decodes by slot (a new slot starts a new batch; SLOT_STATE's parity is only the fallback for a v1 host) and, within a slot, by frequency: a slot retuned partway through reads as two batches with the same time, each under the frequency its decodes were heard on, and nothing is dropped (operator decisions 2026-09-28). **A slot is timed at its end**, on the :00/:15/:30/:45 grid (7.5 s for FT4), so a batch that has just arrived reads "0 s ago", and its header shows its span, `2026-09-28 19:03:30–45z` (`fmtSlotSpan()`), so a WSJT-X-style start reads true too; its band is named from its frequency. **Reply is offered by the clock, not by position in the list** (`slotReplyOpen()`): only on a slot that ended less than two slot lengths ago, the current and previous slot (30 s on FT8, 15 s on FT4). Decodes shown after the app sat idle, restored from its cache or caught up from the sidekick, carry their real slot time and are not replyable however high they sit, and a tab that stayed open redraws the moment it is visible again. A station still calling reappears with its own button, and the main board remembers only its last 64 decodes for a reply, two or three slots on a busy band (operator decisions 2026-09-28). **A reload adds no second copy:** it restores the shown slots from the cache and then reads the sidekick's event ring from its start, so a decode already shown (the same id and text, and the same slot when the host names it) is skipped (`decodeAlreadyShown()`). The text is part of the match because the main board numbers decodes from 1 at each boot. The QSO log is untouched by any of this. Covered by `webapp/tests/test_decode_batching.js`.
* **FT4 beside FT8 is its own batch** (Settings, **Also decode FT4**, Station's `rx_ft4`; [decode.md](decode.md), **FT4**). Its decodes carry `sl` 75 and FT4's own dial in `fq`, so they batch apart from FT8's by slot and by frequency as any slot does, and every batch header names its mode, "20m FT8 · 14.074 MHz" and "20m FT4 · 14.080 MHz" (`slotMode()` from the slot's length). A tap on an FT4 decode queues a reply on FT4, as one on FT8 does ([autoseq.md](autoseq.md), **The queue**). The frequency check compares it with FT4's dial (`currentFt4DialKhz()`), where it was heard and where the reply goes, not FT8's. On 40 m, where FT4's dial is below FT8's, the reply goes out by a retune ([radio.md](radio.md), **TX timing on a QMX**). The setting's note says what it does and where it cannot: QMX only, CQ on FT8 only, not on 15 m or 10 m.
* **The main board refuses a frequency write that does not reach the radio.** `station_key_names_operating_band()` (`components/station/station.cpp`, host-tested) answers whether a CONFIG key names the band actually being operated — `band_sel`, or that band's own frequency key under the active protocol. `porta_host_config_set()` calls it where it already tested for `band_sel`, and refuses with `station_vfo_refusal()`'s text: "band saved, VFO not moved (TX active)" for `band_sel`, "frequency saved, …" for a frequency key, or "… (CAT not ready)". A write to any other band's frequency, or to `active_bands`, stays silent on a sync miss, same as before. The refused value is still saved: the refusal says the radio did not move, not that nothing changed. So after any refused write the app re-reads the station, and the bar shows what it holds; a refusal of a drawer action also shows in a dialog, since the operator is looking at the drawer (`putConfigLine()`). With CAT down, the P4 retunes to the saved frequency when the radio reconnects.
* **Settings keeps only which bands appear** (`active_bands`, `buildBandRows()`, on its Radio & bands page). `band_sel` and the per-band frequency rows are in the radio drawer, not Settings; Settings sends neither key, so a Settings save cannot meet the P4's mid-TX `band_sel` refusal.

### Settings › Station

The one home of the station's own settings, a page of Settings (**Settings**; operator decision 2026-11-11). Operate has no sheet for them: a second place split one set of settings, and a full-screen sheet covered the slot bar. The CQ row's gear and Sends text and the radio drawer's **Station ›** open it (`openStationPage()`: the Settings tab, on this page), and its Back then reads **‹ Operate** and returns there; from the menu it reads **‹ Settings**. The slot bar stays in view, which the sheet covered. There is no Save button: **each control writes its own key the moment it changes**, with one `putConfigLine()` PUT, which reloads the whole station either way: a success brings the CQ row's Sends text and the dock line back in sync with what actually landed, and a refusal is a toast, the control reloaded to what the station still holds. The menu's row reads the call, the grid square and how it calls ("KB2SLO · EM10 · CQ POTA").

* **Identity:** **Call** and **Comment** (each its own key, by the `FIELDS` loop), and **Grid**, below.
* **Calling CQ:**
  - A **Sends** preview, `cqSendsText()`, the same function the CQ row's own preview uses.
  - **Type** (`cq_type`, 0–5: CQ, SOTA, POTA, QRP, FD, FreeText).
  - **One free-text field, shown only for FD and FreeText,** writing `free_text` for both (`setStationSheetForm()`): the label switches between "FD exchange" and "CQ message", and only FreeText caps it at 13 characters (`maxlength`, removed for FD, which has no such limit). Since both types write the same key, switching from one to the other leaves the previous type's text sitting in the field until a new CQ actually goes out under the new type.
  - **Grid**, with a client-side format check (`gridFormatOk()`) matching `normalize_grid_maidenhead()` exactly (`components/station/station.cpp`): 4, 6 or 8 characters, field `A`–`R`, square `0`–`9`, subsquare `A`–`X`, extension `0`–`9`. A malformed grid is refused in a toast and never sent — the firmware itself only silently *keeps the old value* on a bad write (`StationKey::Grid` in `station_parse()`) rather than reporting a refusal, so without this check a typo would read as accepted while the grid never changed. A note under the field always says the CQ carries the first four characters, plus the same compact location badge a decode or QSO row shows for a grid (`CallInfo.shortLocation()`, `callinfo.js` — "TX·US"), so typing a grid gives the same "is this where I think it is" check the operator already gets on someone else's. **Set from GPS** reuses the `geo.html` handoff (**A non-secure origin** below); its return route is `#station`, which `applyHashRoute()` opens straight to this page.
* **QSOs:** **Skip TX1** (`skiptx1`), **Tries** (`tries`, 1–20, the same stepper control as a queue row's count, written about 0.8 s after the last change: how many times each QSO message goes out, and how many CQs Call CQ sends, [autoseq.md](autoseq.md), **Tries**) and TX offset (`offset`, `offset_src`).
* **Activation:** a program+reference list (`act_refs`, e.g. `POTA:US-1234,SOTA:W7O/CC-001`) with an Add row and an × per reference. The program is inferred from the reference itself — a `/` means SOTA, otherwise POTA — and a reference containing `,` or `:` (the list's own delimiters) is refused client-side before it is ever sent, since it could never round-trip. Format-only: there is no store, nearby list, map, or verified/unverified badge yet, since nothing exists to check a reference against until the reference store ships (epic [I18](../roadmap/activator-mode.md)). `components/station/station.cpp`'s `normalize_act_refs()` is the actual source of truth — it drops a malformed token on its own rather than rejecting the whole write, and is what a manual Station.txt edit or a future add-screen (A3) is also held to. **Adding the first reference (empty → non-empty `act_refs`) switches `cq_type` to `CQ POTA` or `CQ SOTA` on its own** (SOTA if any SOTA reference is present, a mixed activation defaults to SOTA), in `porta_host_config_set()` ([logging.md](logging.md), **CQ type follows the activation**). Only that one transition derives it — adding or removing a reference afterward never overrides a manual Type change made on this same page.
* **Not on the page:** Call CQ and an entry's own count (the queue's rows) and band/frequency (the radio drawer): each control has one home.
* **`free_text`** is the Free text CQ's message and, with Type FD, our Field Day exchange ([autoseq.md](autoseq.md), **Field Day follows the CQ type**); there is no separate CQ free-text key.
* **Not yet on the page:** the grid check against a station's references (epic [I18](../roadmap/activator-mode.md), **Later**).

### Settings › Amplifier: the PTT check

**Amplifier**, On or Off (`amp`, [radio.md](radio.md), **The amplifier switch**), is the page's first row. Off, the rest of the page is not shown (`syncAmpDetail()`), the check below is not run, and the menu's row reads "Off"; the main board keeps the settings and puts none in force. On, the page shows them as saved.

**Amp keyed by** (`amp_ptt` in Station.txt: 0 Not checked, the default; 1 TX PTT grounded; 2 TX PTT +5V) says which of the QMX's PTT outputs keys the amplifier. A Micro PA100+ keys from TX PTT grounded (operator, 2026-11-09). Below it, `ampPttCheck()` (host-tested by `webapp/tests/test_amp_ptt_check.js`) compares the radio's own per-band PTT outputs, which the main board reads when the radio connects ([radio.md](radio.md), **The QMX's settings, read at link-up**), on each active band the radio has:

* **Right:** the chosen output alone on. Another TX output on with it would key the amp from both, and an RX output keys it on receive, so either is named. The line then says the radio's model and that every active band is right.
* **Wrong:** an amber line names each active band that differs and what it has on ("40 m: no PTT output on"), and Serial 6 on PTT when it makes the jack a serial port. Below it, **Set the radio's PTT outputs** asks first, naming the bands the radio transmits on (`radioTransmitBands()`), then posts `/api/radio/ptt` with the keying; the main board writes the radio ([radio.md](radio.md), **Setting the PTT outputs**). While `radio_ptt_write` reads `writing` the button is disabled and the line says so; a failure is shown under the bands.
* **Not read yet,** before the read finishes, it says so; Not checked hides the line. It is redrawn on every config poll (`applyOperateLive()`), so a radio plugged in while Settings is open updates it.

### Settings › Software update

**One Update for the station** (maintainer, 2026-11-12; epic [ukk6](../roadmap/ota-updates.md)): the app, the main board and the sidekick are its parts, named in its progress and in a failure and nowhere else offered apart. * **What is published.** `checkFwUpdates()` reads `https://micro-ft8.kalikstein.com/download/manifest.json` for the boards, and `build.json` beside the app bundle on the sidekick's bundle host (`GET /api/bundle-host`) for the app (**Build**), when the page opens, when it becomes visible and every 60 s while it is; the review reads both again. The HTTPS fetches are what authenticate the hashes ([system.md](system.md), **The inversion**). With no internet from the phone's network, the section says updates cannot be checked from here.
* **Versions are commits, with no order,** so a part is offered the published build whenever it differs: a board by the version it reports, the app by the commit in its stamped build id against `build.json`'s (`FwUpdates.appOffer()`). A locally built, `-dirty` or unbuilt part always is. There is no "skip this version": the next build replaces it. Firmware is published only when a push touches it and the app on every push, so the parts' builds differ on an up-to-date station, and no one version is shown for it (row [nufg](../roadmap/ota-updates.md#nufg) publishes them as one).
* **Unavailable,** with the reason in place of the line, while no main board is linked (the boards update together; a sidekick alone is updated over USB) or the sidekick is on its own access point (no internet to download from) (`plan().unavailable`). **A plan that would leave the two boards on different `PORTA_PROTO_VERSION`s is not offered** (`blocked: 'pair'`, from the manifest's `proto` for a board being updated and `/api/config`'s `sk_proto` and `host_proto` for one that is not): a main board the sidekick cannot talk to can only be recovered over USB.
* **Review, before anything happens,** in the dialog a band change asks in (`askConfirm()`, **Band and frequency**), from `FwUpdates.reviewText()`: about how long, that transmitting stops until the update is done and what that ends now (the band change's sentence, `endsClauses()`, with a running CQ, which a band change leaves calling), the radio off when firmware is in it ("Switch the radio off, or unplug its USB, before you update. If it stays connected it may need switching off and on afterwards."; nothing checks, [main_board.md](main_board.md), **Firmware updates**), and to keep the page open until the app is in. It does not say the station keeps receiving: the main board decodes nothing while its image is sent. A phone that is not paired is asked to pair instead. The time is "under a minute" for the app alone, "about a minute" with the sidekick, "about two minutes" with a main board and "about three minutes" with both, from the bench (2026-11-10: 28 to 42 s and 98 s).
* **What a tap does** (`runUpdate()`), in order. The page takes the hold on transmit (`POST /api/fw/hold`, said again every 20 s while it holds; [sidekick.md](sidekick.md), **Firmware updates**), so the main board ends a running CQ and the queue at once. It installs the app by its own relay (`FwUpdates.relayApp()`, the steps `/update` takes: [sidekick.md](sidekick.md), **Installing the app bundle**); a file that no longer matches the manifest (published again mid-relay) is tried once more against the manifest as it is then. Then it posts every firmware offer, the main board first, to `/api/fw/start` as one body the sidekick carries out by itself, so a phone that locks or leaves stops nothing; the sidekick's own hold takes over. Each image's URL is its dated name under `ota/`, which no later publish overwrites, so a build published while an update runs changes nothing in it ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Public Cloudflare mirror**). With no firmware to follow, the page gives the hold back.
* **An app the sidekick's firmware is too old for** is refused at `begin`, before any file lands (`api_min`). When the plan updates the sidekick, the app waits for it: its row reads "after the firmware", and once the sidekick is back on the new firmware the page takes the hold again and installs the app. Otherwise the update fails there and says the app needs newer sidekick firmware.
* **Progress, on every phone** (`followFw()`, `stepRows()`), on a sheet that covers every tab until the update ends, so nothing under it (the radio bar, the Settings menu) has a state for an update in hand: a list of the steps, each done, in hand or to come: the app's (`appRow()`), then for each board download, verify, send to the main board, restart. The app's install, download and transfer show a percentage. Through the firmware the page polls `/api/fw/status` once a second and draws what the sidekick says, so a phone that opens the app mid-update shows the same sheet, and one already open finds it on its next check (when it becomes visible, and every 60 s); the app's step is the starting page's alone. **Cancel update** is offered until a board's image is handed over (not during the app's step or while a board restarts). A poll that fails is taken as the sidekick's own restart, the plan's last step.
* **Result:** "Updated to d18f9b2", or the reason ("Verification failed — still on 7e61488", "New version did not start — rolled back to 7e61488", "The app was published again while it installed") with the step it failed at marked and **Retry**, which opens the review again against what is published then. A phone that did not start the update sees the same result with no Retry, since it has no plan to run again; and a sidekick that comes back idle with no record of the update (it lost power partway) is reported as that after ten seconds, not waited on. A success with firmware in it says to switch the radio back on, and to switch it off and on if it was connected during the update and does not reconnect. After 12 minutes with no result the sheet says to check the phone's network and reload. **Close reloads the page that ran the update,** into the app it installed. That page follows the update to its result: one reloaded mid-update is no longer the one that started it and loses the result and Retry.
* **The logic is `updates.js`** (`FwUpdates`: the offers, the plan and its request body, the review's text, the relay, the steps, every sentence), host-tested by `webapp/tests/test_updates.js`, which also reads the sidekick's sources and fails when it can report a failure code the page has no words for. The sheet itself, its buttons, the hold and the polling are checked only on a phone.

## Build

`webapp/app/` holds the hand-edited sources; what Pages serves and the sidekick installs is their build, `webapp/dist/app/`, produced by `webapp/tools/build.py`. Pages, CI's Host tests and `install_app.py` all run it, so what is tested is what ships. `install_app.py --usb` installs the same build with no network: `webapp/tools/install_app_usb.py` packs it into a LittleFS image (the firmware's block size, `name_max` 64 and 512 KB file cap) and `esptool` writes it to the `web` partition. It replaces the whole filesystem and leaves NVS alone; the next boot re-hydrates the seed pages. Needs `pip install littlefs-python`. Nothing on that path reads `api_min`, so a sidekick on firmware before API 3 would serve the gzipped files as they are: flash the firmware first. None of the output, its manifest or `build.json` is committed: a committed manifest had to be regenerated by hand after every edit, and it was forgotten twice.

In order, the build:

1. copies the sources;
2. stamps the build id (`<short sha>[-dirty] <UTC date>`, dirty meaning `webapp/app/` has uncommitted changes) over `app.html`'s one `__APP_BUILD__`. Settings' **App** line shows it beside the FNV-1a self-hash, and an unbuilt page shows `source`;
3. minifies every `.html` and `.js` (`minify.mjs`: html-minifier-terser and terser, versions pinned in `webapp/tools/package-lock.json`);
4. compile-checks every script with `node:vm` and compacts the JSON data files;
5. gzips each asset, keeping its name (**Each asset ships gzipped**, below);
6. writes `manifest.json` from the output, so it lists the bytes as shipped;
7. fails if a file exceeds the sidekick's 512 KB per-file limit or the bundle exceeds 800 KB, both counted in bytes as shipped.
8. writes `build.json` beside the manifest: the build id and the bundle's size, which the page compares with its own build id to offer an update (**Settings › Software update**). It is never one of the manifest's assets, so the sidekick never stores it and an installer never posts it: the sidekick's manifest parser refuses a field it does not know (`web_manifest.c`), and every installer posts the manifest as fetched, so a field there would stop every sidekick already flashed from installing an app.

**Minification is conservative on purpose.** Top-level names are never renamed: the pages share globals across files (`CallInfo` from `callinfo.js`, `MicroFT8Pairing` from the sidekick's `/pairing.js`), and a readable top-level name is what makes an error on a device traceable to the source. Whitespace collapses to one space, never to none. A file the minifier would grow ships as it is. The first build took the bundle from 637 KB to 469 KB (73%).

**Each asset ships gzipped.** Served as it was, the bundle was 619 KB of the 800 KB budget, and an install stages a second copy. `build.py` gzips every asset at level 9 after minifying, under its own name, with no timestamp or file name in the header, so the same sources build the same bytes; an asset gzip would not shrink ships as it was. The manifest, the sidekick's size and hash checks, its 512 KB file limit and the budget all count the bytes as shipped, and `install_app.py` and `install_app_usb.py` send what the build made. The sidekick keeps no manifest, so it tells a gzipped file by its first two bytes, `1f 8b`, and serves it with `Content-Encoding: gzip` ([sidekick.md](sidekick.md), **Web root**); the build refuses a plain asset that starts with them. Firmware before that serves the bytes as they are, so the manifest's `api_min` is 3 and such a sidekick refuses the bundle at `begin` ([sidekick.md](sidekick.md), **Installing the app bundle**). The page hashes `app.html` as the browser decoded it (Settings' **App** line), so `install_app.py` prints its FNV-1a over the decompressed file to match. `webapp/tools/test_build.py` holds the compress step and the manifest written after it. Measured 2026-11-13: 909,917 bytes of source ship as 185,745, `app.html` 51 KB of them.

**The 800 KB budget**, in bytes as shipped, comes from the `web` partition (1,920 KB). An install stages a second copy of the bundle before renaming it into place ([sidekick.md](sidekick.md), **Installing the app bundle**), and the reference store's proposed cap is 256 KB (epic [I18](../roadmap/activator-mode.md), **The reference store**): 2 × 800 + 256 leaves 64 KB for the bootstrap pages and LittleFS overhead. Raising the budget means shrinking the store cap.

**Previewing:** `tools/serve_webapp_local.py` serves the sources at `/app/`; with `--dist` it serves the last build there instead, sending `Content-Encoding: gzip` on a gzipped file as the sidekick does, which is how a minifier problem shows up before a push. Without `--sim` there is no sidekick behind it, so the pages load and render but no API call succeeds; a bench check still needs `install_app.py`. `--sim` proxies `/api/` to `host_mock/sim_station`, which plays `host_mock/test_qso.json` (or `--scenario`) on a real 15 s clock (`--scale` divides that wait) and serves the same event JSON the sidekick does. Open `http://127.0.0.1:8787/app/app.html`. The simulator's pairing window stays open, so the page pairs without a button press. That is a scripted station, not a radio: USB, CAT, and audio timing are not what it exercises.

## Serving the site

`micro-ft8.kalikstein.com` is `webapp/` deployed by `.github/workflows/pages.yml` to Cloudflare Workers Static Assets, after the build above has replaced `webapp/app/` with `webapp/dist/app/`. **Static by default:** `wrangler.jsonc`'s `run_worker_first` names only `/download/*` (the R2 firmware mirror, [RELEASE_PROCESS.md](../RELEASE_PROCESS.md)), so every other request is a static file served without running `worker.js`, and costs none of the free plan's daily Worker requests. A Worker route added later goes in that list too. A path with no matching file gets `webapp/404.html` with status 404 (`not_found_handling: "404-page"`), also without the Worker, so stray URLs and bot scans cost nothing either.

Static responses get their headers from **`webapp/_headers`** (one rule per path pattern; its comments carry the reasons too). Static Assets reads it from the root of the deployed directory and never serves it; wrangler leaves it, `_redirects` and `.assetsignore` out of the upload by default. It applies to nothing `worker.js` returns, so the Worker's routes set their own headers.

* **`Access-Control-Allow-Origin: *` on every file**, redirects and 404s included. Load-bearing: the sidekick's plain-HTTP page fetches the bundle from `/app/` cross-origin to install and update the app ([sidekick.md](sidekick.md), **Installing the app bundle**), and `map.html` fetches `/data/ne_10m_places.json` the same way. Static Assets sends no CORS header by default, unlike GitHub Pages, which that doc's host requirement was measured against. The redirect needs it as much as the file: the sidekick asks for `/app/app.html`, which the default `html_handling` 307s to `/app/app`, and a cross-origin fetch that meets a redirect without the header fails.
* **`/app/` is for the sidekick's relay, not for pages.** It holds the bundle as built, gzipped files included (**Build**), and nothing tells Static Assets a file is gzip, so it sends none as `Content-Encoding` and a page reading one gets compressed bytes. No page of the site may load from it; one that needs the app's data keeps its own copy (`/data/`). What the relay reads is the stored bytes; how that was measured, and what is not yet ([sidekick.md](sidekick.md), **What the release host must provide**).
* **`Cache-Control: public, max-age=31536000, immutable` on `/geo` only.** `geo.html` (**A non-secure origin**) is the one page whose point is working with no network: an operator who reaches it already crossed the hard part, getting internet once. Static Assets' default, `public, max-age=0, must-revalidate` (measured 2026-09-22), forces a revalidation round trip on every visit; immutable with a long max-age lets a browser holding a fresh copy skip the network outright. Every other file changes on every deploy and keeps the default. The rule is on `/geo`, not `/geo.html`: the `.html` form is 307'd to the extensionless URL first, so a header on it lands on the redirect (confirmed live 2026-09-22), and `geo_handoff.js` links straight to `/geo`, one round trip fewer.

**Every HTML page declares `<meta charset=utf-8>` itself**, before anything else in its head, so its encoding never depends on the host. Static Assets has served `text/html` with no charset (measured 2026-09-22), while the sidekick's `web_fs.c` always sends `text/html; charset=utf-8`; without either, the browser guesses, and guesses better the more UTF-8 it sees. That is why the dense, tens-of-KB `app.html` and `map.html` looked fine and the few-hundred-byte `geo.html`, with one non-ASCII character, showed mojibake on a real phone (2026-09-22): not a defect of that page, only the first small enough to expose it. A new page, `getting_started.mjs`'s template included, carries the tag too; the minifier keeps it.
