# Web app architecture

The web app (`webapp/app/`) is the station's only UI on the headless P4, served by the sidekick ([sidekick.md](sidekick.md)) and run in the phone's browser. System context: [system.md](system.md).

## Screens

**Operate / QSOs / Tools / Settings** are four tabs, switched from the tab bar (`app.html`, `#tabbar`), with no swipe between them and no title row above them (operator decisions 2026-10-25). **A shortcut may land on a tab where it saves a step toward something the operator is already reaching for** (operator decision 2026-11-11); there are three: the slot bar's row, tapped on any tab, goes to Operate (**Operate's pinned regions**); the CQ row's gear and the drawer's **Station ›** go to Settings' Station page (**Settings › Station**); and the QSOs tab's QRZ gear goes there too, to the QRZ key (**QRZ sync**). The title row held only the title, a pairing badge and the Settings gear, and its height went to the decodes. Not paired shows as a radio bar state and a dot on the Settings tab (**The radio bar**).

**Every action reports where the operator is looking.** Operate has no status line and no banners (operator decision 2026-10-25): what an action changes shows where it changed (the radio bar, a row, the queue), progress and "ok" are not reported, and a failure's reason is a toast at the bottom for 6 s, above the tab bar and Operate's pinned bottom (`failMsg()`, `showToast()`; the Undo after a reply is the same toast). A lost link is the radio bar's No contact state (**The radio bar**). A page that is no longer the app the sidekick serves says so on a sheet over every tab, with Reload (`noteServedApp()`, **Settings › Software update**). Settings has no status line either (operator decision 2026-11-11: the line sat over Settings' menu and every page, repeating "ok"); `setMsg()` is gone, and `failMsg()` is the toast alone, which shows over Who hears me's list too. Settings has no Save button for the station: each field writes its own key when it changes (blur or Enter for text, a pick for a menu, a tap for a band), and a refusal is a toast with the reason, the field reloaded to what the station holds. The sidekick's own network keeps its Save, since saving restarts it. What stays a message beside its control: the sidekick actions' own lines (`#netMsg`, `#apMsg`, `#tokMsg`, `#resetMsg`, `#updMsg`), and Set from GPS's progress, under the Grid field (**Settings › Station**). A log download or clear that fails is a toast; it used to write to Settings' line, unseen from QSOs.

* **Operate** pins its status above the decodes and its controls below them, so only the decode list scrolls (**Operate's pinned regions** below): the slot bar on top; the queue (**The CQ row** below) and the radio bar (**The radio bar** below, with band and frequency in its drawer) at the bottom.
* **Grow by destination, never by feature.** QRZ is not a screen: per-callsign data expands on the row it belongs to. One shared expand-on-tap component, used on decode, queue and QSO rows, shows **offline-derived** facts at once (DXCC and zones from the prefix, distance and bearing from grid arithmetic) and **online-enriched** ones (QRZ bio, photo) when reachable, failing legibly when not.
* **QSOs is one continuous list** with day dividers ("Today", "Sep 13"), not a day-file picker. The main board keeps one ADIF file per UTC day; the list loads the current day on open and older days as the operator scrolls (`FILE_LIST`/`FILE_READ`), because Port A's budget cannot carry the whole log on every open. **A new QSO shows at once:** the main board writes it as our RR73, RRR or 73 starts, so a TX event turning active with such a message (`txLogsQso()`) reads today's file 0.5 s and 2 s later (`kickLogRefresh()`), as does opening the tab; an 8 s poll while the tab is open (`refreshLogHead()`) is the backstop, and a refresh asked for while one runs is run again after it rather than dropped. Each read crosses Port A, so it waits behind any other request to the main board ([sidekick.md](sidekick.md), **Tasks and cores**). **A log read is given up after 10 s** (`logFetchJson()`, which every read of the log in `app.html` goes through; host-tested by `webapp/tests/test_log_timeout.js`): one in flight when the sidekick restarts may never settle, and each reader holds a busy flag while it waits, so a single such read froze the list until a reload (2026-11-11, 44 s in Chromium). The next poll reads again, and a day's rows that failed to load are not kept. A line under the toolbar shows the main board's log storage, "N MB free of M MB", from the live `storage_total_kb` / `storage_used_kb` config lines; it is hidden while the board has not said, and red under 10% free. Each row's second line names the QSO's band, mode and frequency as a decode batch's header does, "20m FT4 · 14.080 MHz" (`qsoBandText()`), so FT8 and FT4 contacts read apart.
* **The callsign card's POTA / SOTA row says when the call was heard calling CQ POTA or CQ SOTA** ("Called CQ POTA here · 20m FT8 · 3 min ago"), beside the internet spots and before they load, so an activator nobody has spotted still shows as one, offline included. Every decode is offered to `learnCq()` (`callinfo.js`), which keeps the newest sighting per call for the UTC day in this browser's storage, at most 500 calls; a CQ decoded while no page listened is not seen. It is the first slice of Ideas [hw2z](../roadmap/ideas.md#hw2z) (operator, 2026-11-09).
* **The callsign card's QSO history comes from the QSOs loaded so far** (`qsoHistoryFor()`), so a QSO on a day not yet loaded is missing from it. Row [I32](../roadmap/ideas.md#I32) would answer it from the P4.

### The CQ row

The queue's last row, always present (`app.html`, `#opCqRow`), above the radio bar: the queued CQ, which is an ordinary queue entry with its own tries ([autoseq.md](autoseq.md), **Tries**), drawn here rather than among the QSO rows. It sits below the scrolling QSO rows, not inside them, so a long queue neither hides it nor loses rows to it. The queue's other rows read `queue`, the CQ row too, from the same `QUEUE_ENTRY` stream (`renderCqRow()`; the CQ is the entry whose call is `CQ`).

* **Call CQ** (`POST /api/cq`) when no CQ is queued. It keys the transmitter in one tap, as Reply does. Its body names the channel to call on, `FT4 14080000`, its mode and its dial in Hz (`cqChannels()`, `cqCallBody()`; [autoseq.md](autoseq.md), **The queue**): FT8's at the band's dial, or FT4's at the band's FT4 dial. The main board refuses a channel it does not listen to, and picks the parity and the tries, and both show once the CQ is queued.
* **The mode button** (`#cqModeBtn`, **FT8 ⇄** or **FT4 ⇄**), before Call CQ, chooses which of the two it calls on, and shows only while both are listened to (**Band and frequency**), so there are two channels to choose from; with one, Call CQ calls on it, FT4's when it is alone; the choice is kept on the phone (`microft8_cq_mode_v1`), and Call CQ falls back to the channel listened to when the one chosen is not. It is hidden once a CQ is queued: a queued CQ keeps its channel, and changing it is × and Call CQ again (maintainer, 2026-11-20). One button beside the parity's, not a Call button per mode, so the row keeps its width on a phone; past two channels it becomes a chooser (epic [u8mc](../roadmap/several-channels.md), **Later**). Host-tested, with the status line below, by `webapp/tests/test_cq_row.js`. With no radio ready the main board refuses it, and a reply too, and the toast says why ("Calling CQ failed: No radio"; [autoseq.md](autoseq.md), **Where entries come from**).
* **Once queued:** the parity, **Even ⇄** or **Odd ⇄**, which a tap moves to the other period (`POST /api/queue/parity`, for a strong station nearby); the count, `2/6 tries`, which opens the tries stepper (**Tries on a queue row** below); and **×**, which ends the CQ, stopping one on the air in the same press (`POST /api/queue/cancel`; the P4 stops a cancelled entry that is on the air, [autoseq.md](autoseq.md), **The slot cycle**).
* **Arrangement:** the Sends text over the status line on the left, the controls on the right, then a gear (`#cqSettingsBtn`, labelled "CQ settings").
* **The Sends text** mirrors autoseq's `generate_cq_text_into()` (`components/autoseq/autoseq.cpp`): `CQ`, the modifier if there is one, the call and the grid's first four characters (`cqSendsText()`). Tapping it, or the gear, opens Settings on its Station page (**Settings › Station** below).
* **The status line** reads "Not calling"; "Calling · even/odd slots" when the CQ is queued and the queue holds no other station; or "Waits for the queue · even/odd slots" once a real QSO is active, since every live QSO outranks a CQ ([autoseq.md](autoseq.md)). An FT4 CQ's 7.5 s periods are periods: "Calling · odd periods" (`cqStatusText()`). It does not name the mode: beside the CQ's own buttons that cut the line off on a phone (bench, 2026-11-21), and the mode button names it before calling and the CQ's slot bar while it calls.
* **Stop, during our own CQ, ends the CQ too.** The radio bar's Stop reads **Stop CQ** while the CQ is what's on the air, and posts `/api/tx/cancel` then the CQ's `/api/queue/cancel`; during a QSO message it reads **Stop TX** and only cancels that transmission. Which one is decided from the text on the air (`txIsOurCq()`: it starts with `CQ `), never from the queue: the CQ stays queued behind a QSO that answers it, while our report is what transmits. Otherwise the CQ stayed queued and the next one went out a cycle later regardless of the operator's tap.

### Tries on a queue row

Every queue row's count is a button, `2/6 tries` (tries sent of the limit, [autoseq.md](autoseq.md), **Tries**), reading `· custom` when the entry has a count of its own. A tap opens the tries stepper (`#opTriesEdit`), static markup under the CQ row for the reason the CQ row is static: the QSO rows are rebuilt on every poll.

* **The stepper** is `[−] n [+]`: − and + repeat while held (`holdRepeat()`: after 450 ms, every 100 ms), and the count is not typed (operator decision 2026-10-14). Buttons carry `touch-action: manipulation`, so quick taps do not zoom the page on iOS. It names the entry and what its count bounds ("K9ABC · tries at each step", "CQ · tries in all") with the tries already sent, and steps 1–20 for a QSO, 1–99 for the CQ. A change applies on its own about a second after the last tap (`POST /api/queue/tries`, "`<entry_id> <tries>`"), since an Operate control takes effect when touched (**Why not, on Operate**). **Use default** sends 0, and the entry follows Settings › Station's Tries again.
* **A count at or below the tries already sent ends the entry**, so the stepper does not send it on its own: it says so ("2 already sent: this ends this step, after the try on the air if there is one.") and waits for **End it**.
* **Done** closes it, and so does the entry ending.
* **The CQ decode color** (`--good-hot`, `.c-cq`) is `#007a00` in light mode, `#4ade80` in dark. The light value was `#00c800` (about 2.3:1 on white), which fails WCAG's 4.5:1 text-contrast minimum.

### Operate's pinned regions

Operate keeps its status on top and its controls at the bottom, and only the decode list scrolls. Decodes are the scarce resource on a phone, and every control touched mid-QSO stays in thumb reach however long the list grows on a busy band (operator, 2026-10-24).

* **Why they sit outside the Operate panel.** Each tab is its own scrollport (`#viewTrack > section`), and the three tabs slide on a track moved by a CSS transform, so neither a sticky nor a fixed element inside a panel stays on screen. The top region (`#opTop`) sits at the top of `#viewport`, outside the track, and shows on every tab (operator decision 2026-10-26: "am I on the air, and is RF going out" matters on QSOs and Tools too, and a row that stays put keeps tabs from jumping); every panel starts below it (`--optop-h`). The bottom one (`#opDock`) is a fixed sibling of the tab bar, hidden off Operate (`body.on-operate`), and `#view-operate` alone ends above it (`--dock-h`). `layoutDock()` measures both and the tab bar. The map and SWR sweep pages are separate pages and have no slot bar. A hidden region reports 0 and the last height is kept, so leaving Operate does not resize the panel and clamp its scroll.
* **Top, on every tab:** the slot bar, with a tag at its left for the parity of the slot now, **E** or **O**. A tap on its row goes to Operate from any other tab, since that is where Stop is when the bar turns red, and on Operate scrolls the decodes back to the newest slot (`slotRowTap()`); the row is a button to a keyboard and a screen reader. The bar is 18 px whether or not we transmit, so the row never changes height. Its countdown runs while audio arrives (`radioLive()`), CAT or not: the HL2 has none. With no audio it still counts the slot and says why (**The slot bar's receive cues**); only with no word from the main board is it blank. **A bar per channel listened to** (`slotBarsModel()`, host-tested by `webapp/tests/test_cq_row.js`; maintainer, 2026-11-21, option C of three mocked up): with FT8 and FT4 both on, two half-width bars side by side, FT8's then FT4's; with one, one bar across the row, FT4's on FT4's timing when it is heard alone. Each fills over its own channel's slot, FT8's 15 s or FT4's 7.5 s, with its own E or O tag, and draws its own channel's activity and count. The bar whose mode the TX that goes next is in (`SLOT_STATE`'s `md`) carries the cursor at its offset, and turns red with the readout while that TX is keyed; Tune and a sweep, which have no mode, use the first. While one bar is red, and to the end of each of the other's slots that transmission touched (`slotMuteUntil()`), the other is **RX muted**, as the decoder skips each slot our transmission overlaps ([decode.md](decode.md), **Deaf by overlap**): an FT4 transmission costs the whole FT8 slot it falls in. It shows static grey diagonal stripes, no fill and no activity, its E or O kept, and the text "RX muted", since the radio is half-duplex and that channel hears nothing while another transmits (maintainer, 2026-11-21: the bar went quiet with nothing saying why). So while an FT4 CQ calls with both on, FT8 decodes nothing: a call every 15 s falls in every FT8 slot (bench, 2026-11-21). "Muted" is the rig term for a receiver cut while keying; "deaf" also means a receiver with poor sensitivity. A receive cue is the first bar's. Chosen over two lanes inside the 18 px bar (no room for the readout) and a main bar with a thin lane under it (FT4 without activity): each half's activity strip has half the width to draw the passband in. Before it, with both on, an FT4 call armed turned the one bar to FT4's timing and hid FT8's activity while showing FT8's count (bench, 2026-11-21). It fills full height while we receive too: the station strip's white ticks read over the blue fill (operator decision 2026-10-27, after trying the fill as a thin line along the top), with a cyan cursor at the TX offset and, while we receive, a strip of where the stations are on the same axis and an approximate signal count, each bar its own channel's, or the clock cue (**The slot bar's activity trace** below); red while we transmit, with the readout inside it (`txReadout()`: "4.9 W · SWR 1.30" from the TX HUD event, "Tune · …", "— W" before the first reading, "Write blocked"); amber while TX is halted, or with "0.0 W · no RF" when a keyed transmission still reads 0 W 1.5 s in, past its first tone and meter reply: the radio is keyed and sending nothing, and the SWR it reports then means nothing (operator decision 2026-10-26). At an activation, one line under it (**Activation progress** below). The decode count and the CAT, Audio and Link checks are in the drawer's status line.
* **The Decodes bar** (`#dvBar`) is sticky at the top of the scrolling list.
* **Bottom, top to bottom:** the QSO rows, one line each (call, its mode, **FT8** or **FT4**, from the entry's `md`, `n/N tries`, state, ×; the entry's dial and offset, `fq` and `off`, are kept on it unread until several channels need them), about two showing before they scroll in place, with no label and no empty line; rows scrolled out of sight show as a fade and a count at that edge, "+2 more ▾" below and "1 above ▴" above (`renderQueueMore()`, operator request 2026-10-25), which take no taps; the CQ row; the tries stepper while open; the radio bar; the drawer while open, below the bar.
* **Measured** in the browser at 402 × 874 pt, the iPhone 17 Pro's screen, on 2026-10-26, with no title row or status line: the decode list under the Decodes bar is 512 pt closed with two QSOs and an activation line (the canvas drew about 510). With the drawer open it loses about 190 pt (the canvas's drawer was about 150; this one adds the radio's line). On the phone, Safari's own bars take more; the layout passed the operator's phone check on 2026-10-26, unmeasured there.

### The live polls

The page follows the station by polling the sidekick (`tick()`, once a second): `/api/state` on its first poll and `/api/events?since=` after it, and `/api/state` again in the same poll when a reply says it fell behind the sidekick's ring (`lost`; [sidekick.md](sidekick.md), **Port A**), and `/api/config` every 5 s (`pollLiveStatus()`).

* **Polls never overlap** (`pollEvents()`, `pollLiveStatus()`; `webapp/tests/test_live_poll.js`). A poll still out when the next is due is not sent again, and one is given up after 10 s, so a stalled network leaves one request a page, not one more a second: overnight on 2026-11-18 a page had four events reads with one `since` out at once, and the requests that piled up took the sidekick's heap to 660 bytes ([sidekick.md](sidekick.md), **Tasks and cores**). 10 s, not less: a slow answer cut short is asked again from the same `since`, its backlog with it, in the middle of the stall; overnight 0.7% of events reads took over 5 s and 0.1% over 10 s. A config read waits up to 5 s on the main board, so its 10 s is the same as a log read's (`logFetchJson()`).

### The radio bar

The bottom row of Operate (`#opRadioBar`): the band and each channel listened to with its frequency ("15m · FT4 21.140 MHz" with one, `listenedLabel()`; with two, the band at its size and the channels stacked beside it in a smaller font, "FT8 14.074" over "FT4 14.080", since on one line FT4's frequency was cut off on a phone, `radioBarSplit()`), a sub-line, and on the right a label, or **Stop** while something is on the air. It shows one state, highest first (`radioBarState()`, host-tested by `webapp/tests/test_radio_bar.js`), each with a glyph as well as a tint:

1. **On the air** (red): the band and frequency, and under them "Sending" with the message and the offset. Power and SWR are in the slot bar (**Operate's pinned regions**). **Stop CQ**, **Stop TX** or **Stop Tune** takes the label's place and is its own tap target, never the drawer toggle (`#rbStop`; **The CQ row** says what each stops). Tune reads "Tuning".
   - **CAT lost while on the air keeps this state** (decided 2026-10-25), so Stop stays under the operator's thumb; the sub-line ends "· CAT lost". The state ends with the TX HUD event's falling edge, or 3 s after the last event (`expireStaleTxHud()`), and the bar then shows CAT lost.
2. **A transmission that did not go**, with no Stop since nothing is on the air: **Tune stopped: high SWR** (red: "SWR 9.98 over 3.0 · check the antenna"), when the main board ended Tune itself ([radio.md](radio.md), **SWR protection trips on a QMX**), not counted as a trip; **SWR protection tripped** (red: "Stopped, not sent · K9ABC tries next slot"); **Stopped: SWR tripped twice** (red: "CQ ended · queue cleared · check the antenna"), kept until the next transmission starts, since the main board stays stopped until the operator calls CQ, replies or tunes ([radio.md](radio.md), **SWR protection trips on a QMX**); **TX aborted** for another reason (red: the reason, "keyed too long" for the TX watchdog's stop, [radio.md](radio.md), **The TX watchdog**); **Not keyed** (amber: "Not counted: <reason>"), a TX HUD event with its `nk` flag when the clock was unset, CAT was not ready or SWR protection held the slot. `noteTxHud()` counts tripped transmissions in a row as the main board does: once per transmission, and a clean one resets the count. **TX aborted and Tune stopped: high SWR stay said after their slot** (`noteHeldStop()`, maintainer, 2026-11-20): the main board says a stop only for the rest of the slot it came in, and one made mid-slot, as the TX watchdog's and the Tune stop are, showed for a second or not at all (bench, 2026-11-20: the watchdog's for about 4 s). The bar keeps the stop until the operator taps it, which also opens the drawer as any tap does, or the next transmission or Tune starts. It ranks below no main board, no contact and not paired, which are about now, and above a radio problem. Only a stop seen on this page is held, never one replayed from an earlier visit's cache. A single SWR trip is not held: its QSO tries again in the next slot.
3. **Main board not connected** (red: "Check the cable between the boards and the main board's power"), when the sidekick answers and says it has no main board (`mainBoardAway()`): its `host_linked`, from the main board's HELLO, rides on every config reply, one the main board did not answer included ([sidekick.md](sidekick.md), **Port A**), so the page knows from its first poll and not after a timeout. It is its own state because the fix is a cable, and because it is what a new operator sees who powers the sidekick first. One sentence says it everywhere (`noMainText()`): the drawer; a toast when Call CQ, a reply, Tune or a Settings write is tried, none of which is sent; the QSOs list; and the Station, Radio & bands and Amplifier rows of the Settings menu, in amber. Settings › Station still shows the values this browser last saved, marked as such. It clears with the first reply that says a main board is linked. Then **No contact with the station** (red; a firmware update has no state of its own here, since the page following one shows its progress sheet over every tab, the bar included: **Settings › Software update**), then **Not paired** (amber: "Not paired · press the pairing button"; this phone can watch but not transmit or change anything, and the Settings tab carries a dot; `paired()` is whether a token is stored, so one the sidekick rejects shows at once), when nothing has answered for 30 s (`linkLost()`): the browser not reaching the sidekick, or a main board that is linked and has stopped answering; the drawer says what to check. A page that has never had an answer says it too, 30 s after it loads. It clears with the next answer. Then **a radio problem**, from `radioChipState()`: **Found · syncing** (the device is there, CAT and audio are not both up; the HL2, until its stream is up), **Receive only** (the HL2 streaming: it has no CAT and no transmit yet, so it is never CAT lost), **HL2 busy** (amber: another program has its stream), **Stream lost** (red: it streamed this session and stopped, the HL2's CAT lost); for the HL2 they come from the main board's `hl2=` (main_board.md, **Ethernet**), and an HL2 with no link or no answer is **No radio**, the slot bar saying which and **Radio moved** (the radio reports a frequency, mode or split other than the one the main board set; while Tune is on, the mode is not checked, since the QMX reports its SWR Tune carrier as CW) amber; **CAT lost** (CAT was up this session and stopped) and **Not decoding** (the main board's decoder could not start) red; **No radio** and **Unknown USB** (a device that is not the QMX) grey. The label becomes the way to the actions: "Review ›", "Radio ›".
4. **SWR sweep running** (red: "A carrier at each point · tap to open the sweep"), with **Stop sweep**, while the main board says one runs (`swr_sweep` in the config reply) (maintainer, 2026-11-16: leaving the sweep page while it ran left no way to see or stop it). A sweep keys the radio a point at a time and sends no TX status, so On the air does not cover it. **Stop sweep** posts the same cancel as the sweep page's Stop, and a tap on the bar opens the sweep page, which rejoins the run ([radio.md](radio.md), **The SWR sweep on the main board**). The radio bar is on Operate; on every tab the slot bar turns red and reads **SWR sweep running**, and a tap on its row comes here, as for a transmission (**Operate's pinned regions**). Bench-checked against a real sweep, 2026-11-16.
5. **Ready**, quiet: "QMX ready", and at an activation "· 3 refs · 0000Z 3h12m", the time to 0000Z, when a POTA activation's day starts over.

**The drawer** (`#opDrawer`) opens from the bar's chevron, body or label (`setDrawerOpen()`) and asks the radio for its state. It opens below the bar, so the bar rides up to the top of the open section, and it slides open and closed (its one grid row animates from 0fr to 1fr in .25 s, with no motion under the system's reduce-motion setting; operator request 2026-10-25). While closed it is `inert`, out of the tab order and VoiceOver. Open, the bar turns blue, the chevron fills and points down, and the label reads **Close**. A band is two taps (operator decision 2026-10-25). Top to bottom:

* **A problem state's note and actions first:** **Put it back** and **Use it** when the radio moved, **Retry now** when CAT is lost, **Retune VFO** when not decoding.
* **The band grid and the frequency row** (**Band and frequency** below).
* **The status line:** the CAT, Audio and Link checks, the decodes in the last 5 minutes, and **Station ›** (**Settings › Station**).
* **What the radio said:** in Ready, one line (the device, its firmware, what it reports) with **Retune VFO** and **Tune**; in a problem state, its rows.

The rest of radio state:

* **Found shows at plug-in.** The main board announces the device when the USB host first sees it, not when CDC opens about 11 s later (`qmx_transport.cpp`, `track_usb_presence()` and the descriptor callback): `USB_STATUS` attach, with VID/PID `0` when the device is there but not yet named. An attach whose device leaves before CDC opens is cleared by the same task, since no CDC disconnect comes.
* **Read-back.** `POST /api/radio/read` sends the `RADIO_READ` action; the main board sends `IF;` (`radio_control_query_state()`) and the parsed reply (frequency, TX/RX, mode, split) rides in the config snapshot as `radio_hz`, `radio_tx`, `radio_mode`, `radio_split`, with `want_hz`, what the station means the VFO to be (during a transmission that retuned the radio, the dial it retuned to: [radio.md](radio.md), **TX timing on a QMX**). A sync asks too. Never during a transmission or Tune, and never polled: the page reads when the drawer opens, and the radio pushes the rest (next bullet). The `IF;` layout parsed is the Kenwood TS-480 one the QMX follows (`components/radio_control/cat_reply_parser.cpp`); it is host-tested but unchecked against a real QMX (TEST_PLAN, Pending).
* **Pushed state.** The main board sends `AI2;` once per connection (`sync_vfo()`, with the `VN;` read), and the QMX then sends `IF;` unprompted whenever its frequency, mode, TX or split changes. `cat_reply_parser` counts each `IF;` that differs from the one before (`if_changes`); `porta_p4_radio_push_tick()` sees the count move and sends one `RADIO_STATE` event (`PORTA_EVT_RADIO_STATE`, at most one per 100 ms) with what the radio last said. The sidekick serves it in `/api/events` as `"d":7` (`hz`, `tx`, `md`, `sp`, and `want`, the wanted dial), and the page puts it where the poll would (`applyRadioPush()`), so the bar follows a knob turn at once; the next poll carries the same values. The tick holds back during a sync and 150 ms after, and likewise while a transmission has the radio retuned (`radio_control_tx_retuned_hz()`), because the radio answers each command we send with its state and those are not its own doing. **The page compares what the radio reports only with the wanted dial sent with it.** The poll carries both (`radio_hz`, `want_hz`), and so does the push (`want`, from the same `want_dial_hz()` on the main board), and `applyRadioPush()` sets them together. During a transmission that retuned the radio, the wanted dial is the retuned one; the radio's push when the dial came back, read against the previous poll's wanted dial, showed **Radio moved** for up to a poll (the 40 m FT4 field check, 2026-11-09), so two values from different moments never meet. The drawer-open read stays for firmware that does not answer `AI2;` (it replies `?;`, which the parser ignores). There is no `AI0;`: the P4 has no clean stop to send it from, and a QMX power cycle clears `AI2;`. Host-tested by `host_test_cat_reply_parser`, `host_test_porta_proto` and `webapp/tests/test_radio_push.js`; the sync gating and the radio itself are field-only (TEST_PLAN, Pending).
* **Firmware version.** The main board asks `VN;` once per connection (after the first sync) and the parser keeps the answer until the radio goes; it rides in the config snapshot as `radio_fw`, and the drawer shows it ("FW" on Ready's line, "Radio firmware" in a problem state's rows). A QMX answers `VN1_04_003QMX;` (the release and the model run together, read on the bench 2026-10-24), shown as `1.04.003 (QMX)`. An HL2 has no `VN;`: the drawer's **Gateware** row is the version its discovery reply gave ([hl2.md](hl2.md), **Gateware**).
* **Actions.** **Retune VFO** (**Put it back** when the radio moved) is the old Connect: sync the Station band, Digi, VFO A. **Use it** saves the radio's frequency as that band's frequency. **Tune** sends a carrier, with power and SWR large on the bar and in the drawer while it is on. **Retry now** when CAT is lost is the same sync, refused while CAT is down.

### Decode rows and tap to reply

Each decode row is two lines, about 51 pt. The first is the message at 1.05rem, with the → ME badge kept whole, and the SNR in bold mono right-justified at its end. The second is one mono line: DT, the place (a link to the map at the station's grid, cut short with … when long) and the distance at the right. The grid itself is on the station's card, and so is the bearing, which Settings' **Show the bearing on decode rows** (this phone only, off by default) adds to the row (operator requests 2026-10-25 and 26: DT is acted on more than the grid). Nothing shares the message's line but the SNR, so it does not wrap: measured at 402 pt with "-24 dB" on every row, every FT8 message shape tried fits, where beside a fixed 172 px number column 13 of the same 16 wrapped. Two cases still wrap, their badges going to the next line: a compound call to us (`KB2SLO <PJ4/K1ABC> RR73 → ME`), and a long message carrying both activation badges. A decode's audio offset is not on the row: the station's card lists it beside each decode heard this session (decided 2026-10-25: it is a detail of one station, and the card is where a station's details are). The slot header is one line: band and frequency, then the slot's span without the date, and its age ("14:02:30–45z · 6s ago", `fmtSlotTime()`). It sticks under the Decodes bar while its slot is on screen (each slot is its own `.dslot` box, so the header lets go when the slot ends), so the slot being read keeps its time in view.

**Rows never move under a finger** (operator request 2026-10-25). A new slot arrives at the top, and a tap that landed as the list shifted would reply to a different station. So a redraw waits while a finger is on the list, for 600 ms after it lifts (the tap's click comes after the lift), and while the list still coasts from a flick (`decodeRedrawHeld()`), then runs once. A redraw the operator's own reply asks for (Sending…) runs at once.

* **Tap a row to reply.** There is no Reply button. A row replies when its message is replyable (`isReplyableDecode()`: a CQ, or a closing 73 or RR73) on a slot still open for a reply (`slotReplyOpen()`), and no reply from it is sending or queued (`decodeRowReplyable()`). Such a row ends in a blue › and is a button for assistive technology, labelled "Reply to <call>: <message>". Its callsign and grid links keep their own taps (`decodeTapAction()`), with hit areas padded without moving the text. A row that is not replyable has quieter text and no ›; a message to us keeps its colour and badge. One listener on `#opDecodeRows` serves every row, so a row rebuilt by a poll keeps its tap. A tap meets the same refusals as before: a slot that aged out, and a decode heard on another frequency (**Band and frequency**). Host-tested by `webapp/tests/test_decode_tap.js`.
* **Feedback** (`sendReply()`). The row says **Sending…** at once; the sidekick holds the POST until the main board accepts or refuses, about a second. Accepted, the row is tinted, with a **Queued** badge after the message in place of the ›, and a dashed placeholder for the sender's call stands in the queue until a `QUEUE_ENTRY` for the same call arrives (matched on the call, no protocol change); a call already queued is highlighted instead. A refusal, or no entry within 10 s, removes the placeholder and shows the reason under the row with **Retry**. The row is tappable again once the queue entry goes away. State is `replyState`, reconciled by `reconcileReplies()` on each queue render and once a second.
* **The queue in the decodes** (operator request 2026-10-26). A decode that names a station in our queue (never our CQ entry, `queuedCalls()`) says what it means for that QSO (`queueInvolvement()`): the station is calling **CQ again**, **Working** someone else, **Done with** someone else (73 or RR73), or **Called by** someone else. The row gets an accent bar at its left edge, that station's call in bold, and the phrase on its second line in place of the place; no filter hides it, and it sorts right after messages to us (`decodeViewOf()`'s `involves`). A message to us from a queued station is already red with → ME and gets nothing more. Each queue row repeats the newest such phrase, with its age, while that slot is under two slot lengths old (`queueLastHeard()`, "Working W1XYZ · 6s", or "→ you"); within a slot, what the station sent outranks someone else calling it. A row the main board holds (its `QUEUE_ENTRY` says `hd`, [autoseq.md](autoseq.md), **The busy hold**) says so whatever that setting: "Working W9XYZ · waiting", from the newest decode naming the station's QSO, or "Waiting" with none on the page (`queueHeldCue()`). WSJT-X gives this its own pane; on a phone it is a mark on rows already shown. Settings' **Mark decodes about stations in the queue** (this phone only, on by default) turns all of it off: the marks, the filter pass-through and order, and the queue rows' cue. Host-tested by `webapp/tests/test_queue_cues.js` and `test_decode_view.js`.
* **Undo.** An accepted reply to a call not already queued shows a toast, "Queued K4XYZ · Undo", for 5 s. **Undo** cancels that entry (`POST /api/queue/cancel`); an entry not in the queue yet is cancelled when it arrives, or forgotten if none comes within 10 s. A call that was already queued gets no Undo, since cancelling would end the QSO that was there.

### Decode sort and filter

The Decodes bar (`#dvBar`), sticky at the top of the list: one non-wrapping row of same-shape pills, filled when active, with no label, since it sits on the decodes it sorts (a screen reader hears "Decodes"). It shows once any decode is listed (`decodeBarShown()`), counting rows a filter hides: shown only while rows are visible, a filter that hid them all would take away the control that turns it off. The page never empties its list, so once shown it stays until a reload. **Sort** and **Filter** each open a panel that drops from under the Decodes bar, a caret pointing at the pill and the pill ringed while it is open (`openDvPanel()`; placed by `placeDvPanel()` on open and on a resize, since the bar's place moves with the slot bar and the activation line), so what opened it stays in view; they are the one kind of panel in the app anchored to its control, as these are the one controls in a top bar that open one. Each choice is a row with a one-line explanation. The rule: a panel with buttons waits for one, and a panel without is a menu. **Sort** is a menu, since a pick-one choice is the whole decision and a wrong one only reorders: a tap on a row sets it and closes, and a tap anywhere else (or Escape) closes it unchanged. **Filter** waits: ticks change nothing until **Apply**, **Cancel** (or Escape) closes it unchanged, and a tap outside does nothing, so several ticks are never lost or applied by accident. Sort's rows are circles, filled when chosen, and the pill reads the choice ("Sort" for Default): Default (the order `decodeSortCmp()` stored: decodes to us, replyable lines with CQs strongest first, the rest, recent partners), Strongest (SNR), Nearest or Farthest (distance from the Station grid, for DX); it applies within each slot and slots stay newest first, because replies go to the newest slot and the 15 s rhythm stays readable. A decode with no known grid sorts last under Nearest and Farthest. **Filter** is one pill for the filters, since a pill each overran the bar on a phone. Its choices are pick-any, a checkbox each, a rounded square since a circle reads as pick-one, filled with a tick when on, and Apply sets exactly what is ticked (`decodeViewWithFilters()`). The pill reads "Filter", the one filter that is on, or "Filters · N" (`decodeFilterLabel()`), filled when any is on. The filters combine: **Replyable** keeps the lines a tap replies to by `isReplyableDecode()` (a CQ, or a closing 73 or RR73), whatever the clock says; **POTA/SOTA** keeps `CQ POTA` and `CQ SOTA`; **Hide worked** drops a decode whose sender carries the **Worked** flag, by the same rule and from the same read of today's log (**Worked and activation cues on decodes**), so a QSO just logged leaves the list on the next read. There is no distance filter: Nearest and Farthest already order by distance, and a filter hid every decode with no known grid. A message to us stays on top and is never filtered, and a decode naming a station in our queue comes next and is never filtered either (**Decode rows and tap to reply**). The choice is kept per browser (`localStorage`, a per-viewer convenience), and "N/M" (shown of all) sits right-aligned in the row while any decodes are on screen. Applied when a slot is drawn (`decodeViewOf()`), so changing it re-sorts what is on screen; host-tested by `webapp/tests/test_decode_view.js`. A New filter (never worked, in the whole log) waits on row `I32`: the app knows only the log it has loaded.

**The mode filter** (maintainer, 2026-11-21) is one row of three segments under the Filter panel's filters, **Both**, **FT8** or **FT4**, pick one (`#dvFilterMode`; a row, not three rows, so the panel stays short), shown and in force only while both channels are listened to (`decodeModeFilterOn()`, `decodeViewInForce()`): with one, it is set aside and filters nothing. It hides the other mode's batches, but never a message to us or a decode about a station in our queue, as every filter does, so a QSO on the hidden mode stays in view (the reason the bar's mode chip was taken away on 2026-11-13: a hidden mode's queue hid why slots went deaf, 20 m, 2026-11-10). The pill names it ("FT4 only") or counts it ("Filters · 2"), and it is saved with the view. It lives in the panel and not on the bar, which a fourth pill overran on a phone; pinning a filter to the bar is idea [s2dj](../roadmap/ideas.md#s2dj). What the station hears is chosen in the drawer (**Band and frequency**). The bar fits at 320 px wide and up: measured in Chromium with Strongest, "Filters · 2", a mode chip since removed and a "128/140" count (2026-11-20). If a pill is added and it no longer fits, the controls keep their size and something on the bar gives way; the app is not scaled down instead, since text in a field under 16 px makes iOS zoom into it.

### Worked and activation cues on decodes

`refreshOpLog()` loads today's UTC day file (`YYYYMMDD.adi`) itself every `LOG_REFRESH_MS` into `opLog.rows` (the Log tab's list is separate): while Operate is showing, and on every tab while the station has references (`act_refs`, **Settings › Station**), for the progress line. A decode whose sender is in that file on this band and mode gets a grey **Worked** flag (`dupeIndex()`). With references, only a QSO logged at one of them counts, since each park or summit is its own log (an n-fer record counts for each reference). Only today's file is read, so a station worked yesterday is not flagged; the whole log waits on row [I32](../roadmap/ideas.md#I32). A cue, never a block: a tap still replies. While the station has references, `refreshOpLog()` also primes `callinfo.js`'s activator-spot cache, and a decode whose sender is a spotted FT8 activator (`CallInfo.activeSpotFor()`, online only) gets a badge with their reference: **P2P** for a POTA spot when we are at a park, **S2S** for a SOTA spot when we are at a summit, else the plain program. A decode's mode comes from its slot length. Host-tested by `webapp/tests/test_activation_cues.js`.

### The slot bar's activity trace

**Each channel's activity has its own record** (`band.act` for FT8, `band.act4` for FT4, routed by the event's `md` in `noteBandEvent()`), since an FT4 period's index counts 7.5 s and is about twice an FT8 slot's: with one record for both, after FT4 alone every FT8 event read as older than the FT4 record held, and the strip stayed blank until a reload (bench, 2026-11-21). The clock cue tallies FT8's slots only.

While we receive, white ticks rise from the slot bar's floor where stations are: the bar's width is the passband, 200 to 3000 Hz, the same axis as the TX cursor, which is cyan so the two are not confused (`activityStrip()`). Each tick is one of the main board's 28 Hz frequency cells ([decode.md](decode.md), **Band activity**), as tall as the share of the slot's signal span heard so far that the cell or a cell beside it held a signal, so a station on for the whole slot stands full height, about 85 Hz wide, and a fading one shorter. **Why the neighbours count:** an FT8 signal hops among 8 tones over 50 Hz, so one 28 Hz cell holds it about half the time, and a steady station drew as two or three half-height ticks. Counting the neighbours, decodes standing under a tick of half height or more went from 18 of 29 to 27 of 29 on 40 m, and to 54 of 57 over the next six slots (2026-10-27). A cell held under `ACTIVITY_STRIP_MIN` (20%) of the span is noise and is not drawn. The strip shows where the stations are and whether our offset sits among them or in a gap. **Why frequency across, not time:** every FT8 station transmits for the whole slot, so on a real band a level per block is flat from 0.5 s to the end (2026-10-27); time across carried nothing the fill does not. Inside the bar, where the TX readout goes while we transmit, the text reads "≈N at ≥ -16 dB" (`activityLabel()`): the median level of the blocks heard so far from 0.8 s to 70% of the slot, inside every signal in both modes, so a gap between stations or one burst does not move it (`activityCount()`). **Quiet** at 2 or less: with the antenna off the QMX's own noise reads 1 or 2 (2026-10-27). "≈30+ at ≥ -16 dB" from `ACTIVITY_COUNT_CAP` up, where the count flattens. It counts signals heard, decodable or not, so it is "≈" and is not the decode count. **The floor is said on the label** (`ACTIVITY_MIN_SNR_DB`, maintainer, 2026-11-20): a bin counts at 10 dB over its block's median, about -16 dB in the 2500 Hz the decode rows' SNR uses ([decode.md](decode.md), **Band activity**), and `webapp/tests/test_band_activity.js` holds the label to the main board's threshold. Decodes weaker than that are not counted. On 2026-10-27 it read within about 4 of the decode count on busy 20 m (22–28 decodes) and within about 2 on 40 m (6–11). On 2026-11-20, daytime 20 m with a median decode at -17 dB, it read 8 to 11 against 13 to 23 decodes a slot: the stronger 40%, which "≈9 signals" read as broken.

**The clock cue.** Signals heard and nothing decoded is what a clock too far off looks like, and an empty band, a dead antenna or no audio do not look like it: they hear nothing. When the last two received slots each heard `CLOCK_CUE_MIN_SIGNALS` (8) or more and decoded a quarter of them or fewer, the bar's text turns amber and reads "Clock? N decoded of ≈M signals" (`clockCue()`). `noteBandEvent()` keeps the tally: FT8's decodes per slot (an FT4 decode, `sl` 75, counts toward none, since activity is FT8's slots), and a slot is closed when the next one's activity arrives, by which time its decodes are in. A slot we sent in has no count and is skipped, so the two slots need not be adjacent; a slot the main board did not decode breaks the run, read from its `UNDECODED` event (`"d":9`: transmitting, the decoder busy, or paused; [decode.md](decode.md), **Slot lines**). A slot deaf by overlap is the case that needed it: one an FT4 transmission fell in still hears signals, and counted as a failed decode it cued "Clock?" every slot of an FT4 QSO (2026-11-08). A busy one is the same. The cue never touches the clock. On 2026-10-27 a reflash left the clock about 1.6 s off for ten slots: about 20 signals each, 0–2 decodes, and the decodes' DT −1.5 to −1.6 s. Auto-sync could not recover it, since it steps only from a slot with four decodes. A real band decoded 0.6 to 1.2 of its signals. `webapp/tests/test_band_activity.js` replays that session (`webapp/tests/fixtures/clock_off_2026-10-27.jsonl`, slots, decode counts and levels only) and checks the cue is on for exactly those ten slots.

FT8 decodes only arrive at the slot's end, so the bar is the first word on whether anything is on the band and how busy it is. The sidekick serves each `ACTIVITY` event in `/api/events` as `"d":8` with `si` (the slot), `bm` (block ms), `b` (the first block), `lo` and `hi` (the span the cells cover, Hz), `v` (the levels) and `m` (each block's cell mask, hex in wire byte order, cell 0 in bit 0 of the first byte). `noteActivity()` keeps one slot: a later slot starts over, an earlier one is dropped. `activityStrip()` draws only when that slot is the one the bar shows, on the phone's clock (as the fill is, [time.md](time.md)). Nothing is drawn while we transmit. Activity is not state: a reload draws from its next event, so the slot it reloads in is partial. The bar stays 18 px (**Operate's pinned regions**). A time-and-frequency waterfall would need more height; the masks are what one would draw from (**Decisions a reference app would make differently**, Waterfall). Host-tested by `webapp/tests/test_band_activity.js`; the station simulator sends made-up activity, so `tools/serve_webapp_local.py --sim` draws it.

### The slot bar's receive cues

The bar says why this slot is not decoding, in the clock cue's amber, first match wins (`rxCue()`, then `clockCue()`): **No audio** and why (the HL2's transport state: "no Ethernet link", "HL2 not answering", "HL2 busy, another program has it", "HL2 found, starting", "stream lost"; the QMX's: "QMX not connected", "QMX connecting", "QMX audio down"; "connecting" only once the main board has said a device is on the port, since it reports the port when it changes and a sidekick that restarted has no word of it, which with no CAT and no audio reads "not connected", as the radio bar's **No radio** does); **Not decoding · decoder could not start**; **Overload · ADC clipping** (the HL2 clipped with its LNA already at its floor, within the last 15 s); then the clock cue. The chip says what state the radio is in; the bar says what that means for the slot. With no audio the bar counts the slot on the phone's clock and draws no activity. `webapp/tests/test_rx_cue.js` holds the cues and the HL2's chip states.

### Activation progress

Only while the station has references: a line under the slot bar with each reference's count of today's QSOs (`opLog.rows`, the day file the cues above read) against its target, ✓ once reached (`activationCounts()`, `renderActLine()`). A QSO counts for every reference on its record, so an n-fer counts for each. ### Band and frequency

In the radio bar's drawer (**The radio bar** above), so a band is two taps: open the drawer, tap the band.

* **The band grid** (`#opBandGrid`) shows `active_bands`, one button of at least 44 px per band. Up to seven bands share one row with columns equal to the count (`grid-template-columns: repeat(N, 1fr)`, `buildDockBandGrid()`); more than seven wrap to a second row on their own, so no band is ever a swipe away.
* **A tap changes band at once** (`changeBand()`), asking first only when a CQ is running, a QSO is queued or our own transmission is on the air ("This ends your CQ, ends your QSO with K9ABC and stops the transmission on the air.", `retuneEnds()`, `confirmRetune()`), in the page's own dialog (`askConfirm()`, since a native `confirm()` often cancels silently on a phone; `endsClauses()` builds the sentence, host-tested by `webapp/tests/test_ask_confirm.js`), then ending all of them (`endQueueAndTx()`) and writing the band's standard frequency and `band_sel` in one PUT; the drawer closes. A "no" leaves the grid as it was and the drawer open — it never shows the new band until the write actually lands.
  - Settings > Amplifier > **Prime RF-sensing amp on band change**, off by default, makes a successful change send the bounded QMX SWR Tune pulse described in [radio.md](radio.md), **Prime an RF-sensing amplifier on a band change**. The P4 owns its timing; the browser only saves the option and requests the band.
* **A retune ends a running CQ too** (maintainer, 2026-11-13), as it ends the QSOs: one rule and one code path for a band change, a frequency change and the update (**Settings › Software update**), with nothing that depends on which asked. It replaces a CQ that kept calling, with the tries it had left, on the new frequency. The operator calls CQ again there.
* **A band tap always lands on the band's standard frequencies** (`standardKhz()`, the app's table), FT8's and FT4's both, never the last frequency typed there (operator decision 2026-09-28), including a tap on the band already selected; one already at both standards sends nothing. The main board refuses a frequency write only when it moves two channels that fit out of the window, so the tap's two dials land whichever line comes first. A typed or nudged frequency therefore holds only until the next band tap. Keeping chosen frequencies is row `y9js`.
* **Listening to: the channel chips** (`#opListenChips`, `renderListenChips()`; maintainer, 2026-11-21, chosen over a row of three modes, FT8 / FT4 / Both, from the 2026-11-20 mockup: a chip shows its channel's frequency, and more channels or an HL2's bands add chips without a redesign). In the drawer, as band is, not pinned on Operate: a pinned row costs decode rows on a phone (**Why not, on Operate**), and channels change less often than band. Under the band grid, a chip per channel the band has, its mode and frequency (**FT8 14.074 MHz**, **FT4 14.080 MHz**), pressed while it is listened to: Station's `listen<N>`, 1 FT8, 2 FT4, 3 both, FT8 alone when unset ([decode.md](decode.md), **Channels**). The model is pure and host-tested by `webapp/tests/test_channels.js` (`bandChannels()`, `listenChipTap()`, `listenedLabel()`), which also holds its window bounds to `qmx_iq_channel.h`'s.
  - **Where both fit the radio's window** (a QMX, every band but 15 m and 10 m: FT4's dial from 33 kHz below FT8's to 6 kHz above it; `bandBothFit()`), a tap toggles a chip, and one always stays on ("The station listens to at least one channel."). **Where they do not**, a tap on the other chip switches to it, and the note under the chips says why and where the dial goes ("On 15m FT8 and FT4 are 66 kHz apart, and the radio hears one at a time: FT4 replaces FT8, and the dial moves to 21.140 MHz."). So FT4 works on every band: alone, at FT4's dial. An HL2 hears one channel at a time. Both stored for a band where they do not fit, a choice made before the radio changed, reads as FT8 alone, as the main board plans it.
  - **A change that drops a channel asks first** what it ends, in a band change's words, then ends only the queue entries on the channels it drops, and a transmission on the air (`listenChangeEnds()`), before it writes `listen<N>` with one `putConfigLine()` PUT. Adding a channel ends nothing. The main board refuses both where they do not fit, with the reason, and moves the dial when FT4 alone is chosen or left.
  - **A frequency row per channel listened to** (below), so FT4's dial can be set as FT8's is.
* **The VFO line** (`#opVfoLine`, `vfoLine()`, host-tested by `webapp/tests/test_channels.js`; maintainer, 2026-11-21), under the frequency rows: the radio's own dial as it reports it, and how far each channel listened to sits from it ("VFO **14.074 MHz** · the radio's dial; FT4 is heard 6 kHz above it"), since a channel need not be at the VFO: with both on, FT4 is decoded and sent 6 kHz above it on 20 m. The Ready summary line no longer names the frequency, which it cut off. **The dial still moves for FT4 alone** (FT4's dial on every band): what costs decodes at a change of channels is the receive run restarting, which keeping the dial would not avoid, and on the bench (2026-11-21, four changes on 20 m) a change cost at most one period on a channel, the one in progress, whether the dial moved or not.
* **The frequency rows** (`#opFreqRow`, `#opFt4FreqRow`), one per channel listened to, each named by its mode: **FT8** or **FT4**, **−**, that channel's frequency in MHz, **+**, **Set** (maintainer, 2026-11-21: FT4 leaves its standard dial for a contest's plan or a DXpedition, as FT8 does). FT8's row writes `band<N>`, FT4's `ft4band<N>`; one set of handlers serves both (`FREQ_ROWS`), each row with its own edit state. With FT4 alone, FT4's row is the radio's dial. While both are listened to, the main board refuses an edit of either that would move the two out of the radio's window, with how far apart they would be, and the refusal shows in a dialog. Everything below holds for both rows. The field shows the frequency except while it is being edited (`syncFreqInput()`), so a poll never overwrites a typed value. There is no Standard button: a tap on the band already selected returns to its standard.
  - A typed value under 1000 is MHz, otherwise kHz, kept to 0.1 kHz (the station file stores tenths).
  - **Set**, Enter and the keyboard's ✓ / Done apply it, and a change that goes ahead closes the drawer; a refusal or a declined confirmation leaves it open with the typed value. Escape puts the frequency back. **On iOS, Done sends no key event** (operator request 2026-09-28), only closing the keyboard, so an edit committed with no tap just before it applies; a tap (Set, −, +, anywhere) reaches the page first and its own handler decides instead.
  - **Set**, **−** and **+** (1 kHz) write the operating band's own key (`band<N>`) with one `putConfigLine()` PUT; − and + leave the drawer open.
  - **A value in another active band always asks first** ("Change band to 20m? 14.080 MHz is on 20m.", plus what it would end; operator decision 2026-09-28), then cancels like `changeBand()` and sends that band's key and `band_sel` in one PUT, frequency first. A non-standard value, such as the calling frequency SOTA's FT8 advice asks for ([logging.md](logging.md), **What POTA and SOTA require**), holds until the next band tap; saving one to return to is row `y9js`.
  - A value outside every Region 2 amateur band, or on a band not in `active_bands`, is refused client-side (`bandForKhz()`) with the reason, in a dialog. The band edges (kHz, ITU Radio Regulations Article 5) are a sanity check, not a licence check; 60 m is one range spanning the US channels and the WRC-15 allocation:

    | Band | 160 | 80 | 60 | 40 | 30 | 20 | 17 | 15 | 12 | 10 | 6 | 2 |
    |---|---|---|---|---|---|---|---|---|---|---|---|---|
    | From | 1800 | 3500 | 5330 | 7000 | 10100 | 14000 | 18068 | 21000 | 24890 | 28000 | 50000 | 144000 |
    | To | 2000 | 4000 | 5407 | 7300 | 10150 | 14350 | 18168 | 21450 | 24990 | 29700 | 54000 | 148000 |

  - **A same-band change mid-QSO is treated like a band change** (operator decision 2026-09-28): the same confirmation, then the CQ and the queued QSOs end and a transmission on the air stops before the new frequency is written. The partner is listening on the old frequency. Stopping the TX first also matters because a frequency the VFO cannot reach mid-TX is still saved, and nothing retunes the radio when the TX ends, so the bar would show a frequency the radio is not on. With nothing to end, no cancel is sent: a cancel also blocks a TX armed for the current slot.
* **Reply refuses a decode heard on another frequency** (`replyFrequencyMismatch()`; operator request 2026-09-28), or in a mode no longer listened to ("K1ABC was heard on FT4, and the station is not listening to FT4 now. Turn its chip on in the radio drawer to reply."). A reply goes out on the channel of its decode's mode, at that channel's frequency, so after a band or frequency change a decode from before it gets a dialog ("K1ABC was heard on 7.074 MHz, and the radio is on 14.074 MHz now…") and nothing is queued. The decode's own frequency comes from the main board (next bullet); the radio's now is the bar's. If either is unknown, the reply goes ahead.
* **The main board names each decode's slot and frequency** (Port A v2, [sidekick.md](sidekick.md), **Port A**). The app used to label a slot by what was current when its decodes arrived, a second or two after the slot ended, so headers missed the slot grid and a band change in that gap mislabelled a slot. Now each decode carries the slot it was recorded in (`si`, `sl`) and the dial frequency at the middle of its own signal (`fq`). The app groups decodes by slot (a new slot starts a new batch; SLOT_STATE's parity is only the fallback for a v1 host) and, within a slot, by frequency: a slot retuned partway through reads as two batches with the same time, each under the frequency its decodes were heard on, and nothing is dropped (operator decisions 2026-09-28). **A slot is timed at its end**, on the :00/:15/:30/:45 grid (7.5 s for FT4), so a batch that has just arrived reads "0 s ago", and its header shows its span, `2026-09-28 19:03:30–45z` (`fmtSlotSpan()`), so a WSJT-X-style start reads true too; its band is named from its frequency. **Reply is offered by the clock, not by position in the list** (`slotReplyOpen()`): only on a slot that ended less than two slot lengths ago, the current and previous slot (30 s on FT8, 15 s on FT4). Decodes shown after the app sat idle, restored from its cache or caught up from the sidekick, carry their real slot time and are not replyable however high they sit, and a tab that stayed open redraws the moment it is visible again. A station still calling reappears with its own button, and the main board remembers only its last 64 decodes for a reply, two or three slots on a busy band (operator decisions 2026-09-28). **A reload adds no second copy:** it restores the shown slots from the cache and then reads the sidekick's event ring from its start, so a decode already shown (the same id and text, and the same slot when the host names it) is skipped (`decodeAlreadyShown()`). The text is part of the match because the main board numbers decodes from 1 at each boot. The QSO log is untouched by any of this. Covered by `webapp/tests/test_decode_batching.js`.
* **FT4 is its own batch** (the drawer's chips, Station's `listen<N>`; [decode.md](decode.md), **FT4**). Its decodes carry `sl` 75 and FT4's own dial in `fq`, so they batch apart from FT8's by slot and by frequency as any slot does, each mode in its own open batch (`pendingBatches`, by slot length), since FT4's decodes arrive between FT8's and are no sign that an FT8 slot ended (one shared batch split an FT8 slot in two around them, 2026-11-16; host test: `webapp/tests/test_decode_batching.js`), and every batch header names its mode, "20m FT8 · 14.074 MHz" and "20m FT4 · 14.080 MHz" (`slotMode()` from the slot's length). A tap on an FT4 decode queues a reply on FT4, as one on FT8 does ([autoseq.md](autoseq.md), **The queue**). The frequency check compares it with FT4's channel (`listenedChannels()`), where it was heard and where the reply goes, not FT8's. On 40 m with both, where FT4's dial is below FT8's, the reply goes out by a retune ([radio.md](radio.md), **TX timing on a QMX**); with FT4 alone the radio is on FT4's dial and transmits there. A queue row names its mode only while both are listened to.
* **The main board refuses a frequency write that does not reach the radio.** `station_key_names_operating_band()` (`components/station/station.cpp`, host-tested) answers whether a CONFIG key names the band actually being operated — `band_sel`, or that band's own frequency key. `porta_host_config_set()` calls it where it already tested for `band_sel`, and refuses with `station_vfo_refusal()`'s text: "band saved, VFO not moved (TX active)" for `band_sel`, "frequency saved, …" for a frequency key, or "… (CAT not ready)". A write to any other band's frequency, or to `active_bands`, stays silent on a sync miss, same as before. The refused value is still saved: the refusal says the radio did not move, not that nothing changed. So after any refused write the app re-reads the station, and the bar shows what it holds; a refusal of a drawer action also shows in a dialog, since the operator is looking at the drawer (`putConfigLine()`). With CAT down, the P4 retunes to the saved frequency when the radio reconnects.
* **Settings keeps only which bands appear** (`active_bands`, `buildBandRows()`, on its Radio & bands page). `band_sel` and the per-band frequency rows are in the radio drawer, not Settings; Settings sends neither key, so a Settings save cannot meet the P4's mid-TX `band_sel` refusal.
* **The radio's bands bound both grids** once the main board has read them (`radio_bands`, `radioBandSet()` in `bands.js`; [radio.md](radio.md), **The QMX's settings, read at link-up**). Settings offers only the radio's bands, and `active_bands` stays the operator's subset. A band saved there that this radio lacks is still shown, ticked, struck through and named in a note under the grid, so it is not dropped without the operator; unticking it drops it. Operate's grid offers the active bands the radio has (`dockBands()`), or every band it has when none of them is active. Before the read, and with no radio, every band is offered, as before a radio is known. The grids are rebuilt when `radio_bands` changes (`applyOperateLive()`), not on every poll.

### Settings › Station

The one home of the station's own settings, a page of Settings (**Settings**; operator decision 2026-11-11). Operate has no sheet for them: a second place split one set of settings, and a full-screen sheet covered the slot bar. The CQ row's gear and Sends text and the radio drawer's **Station ›** open it (`openStationPage()`: the Settings tab, on this page), and its Back then reads **‹ Operate** and returns there; from the menu it reads **‹ Settings**. The slot bar stays in view, which the sheet covered. There is no Save button: **each control writes its own key the moment it changes**, with one `putConfigLine()` PUT, which reloads the whole station either way: a success brings the CQ row's Sends text and the dock line back in sync with what actually landed, and a refusal is a toast, the control reloaded to what the station still holds. The menu's row reads the call, the grid square and how it calls ("KB2SLO · EM10 · CQ POTA").

* **Identity:** **Call** and **Comment** (each its own key, by the `FIELDS` loop), and **Grid**, below. Under Comment, **Logged as:** the comment with `/Radio` and `/Grid` filled in as the main board fills them when it logs (`commentPreview()`, host-tested by `webapp/tests/test_comment_hint.js`), so a new station's `micro-ft8 /Radio` reads as what a QSO carries, "micro-ft8 QMX", and not as the words themselves (maintainer, 2026-11-20); hidden for a comment with neither.
* **Calling CQ:**
  - A **Sends** preview, `cqSendsText()`, the same function the CQ row's own preview uses.
  - **Type** is the CQ's modifier (`cq_mod`; [autoseq.md](autoseq.md), **The queue**): CQ, CQ DX, CQ POTA, CQ SOTA, CQ QRP, or **Other…** (`cqModChoice()`). A named choice writes at once.
  - **A field, shown only for Other,** for any other modifier, such as `HI` or `AK`. Picking Other writes nothing by itself; a modifier that is not one to four letters or three digits is refused in a toast (`cqModOk()`, held to the main board's `station_cq_mod_ok()` by shared vectors in `webapp/tests/test_cq_mod.js`), and a valid one writes `cq_mod`. A modifier Type names, typed here, shows as that choice.
  - **Grid**, with a client-side format check (`gridFormatOk()`) matching `normalize_grid_maidenhead()` exactly (`components/station/station.cpp`): 4, 6 or 8 characters, field `A`–`R`, square `0`–`9`, subsquare `A`–`X`, extension `0`–`9`. A malformed grid is refused in a toast and never sent — the firmware itself only silently *keeps the old value* on a bad write (`StationKey::Grid` in `station_parse()`) rather than reporting a refusal, so without this check a typo would read as accepted while the grid never changed. A note under the field always says the CQ carries the first four characters, plus the same compact location badge a decode or QSO row shows for a grid (`CallInfo.shortLocation()`, `callinfo.js` — "TX·US"), so typing a grid gives the same "is this where I think it is" check the operator already gets on someone else's. **Set from GPS** reuses the `geo.html` handoff (**A non-secure origin** below); its return route is `#station`, which `applyHashRoute()` opens straight to this page.
* **QSOs:** **Skip TX1** (`skiptx1`), **Tries** (`tries`, 1–20, the same stepper control as a queue row's count, written about 0.8 s after the last change: how many times each QSO message goes out, and how many CQs Call CQ sends, [autoseq.md](autoseq.md), **Tries**) and TX offset (`offset`, `offset_src`: **Random**, **RX** or **Fixed**, which sends the firmware's 0, 2 and 1, the last being Offset Hz, pinned by `webapp/tests/test_offset_src.js`; on Random a QSO keeps one offset and a CQ rolls each time, [autoseq.md](autoseq.md), **TX offset**).
* **Activation:** a program+reference list (`act_refs`, e.g. `POTA:US-1234,SOTA:W7O/CC-001`) with an Add row and an × per reference. The program is inferred from the reference itself — a `/` means SOTA, otherwise POTA — and a reference containing `,` or `:` (the list's own delimiters) is refused client-side before it is ever sent, since it could never round-trip. Format-only: there is no store, nearby list, map, or verified/unverified badge yet, since nothing exists to check a reference against until the reference store ships (epic [I18](../roadmap/activator-mode.md)). `components/station/station.cpp`'s `normalize_act_refs()` is the actual source of truth — it drops a malformed token on its own rather than rejecting the whole write, and is what a manual Station.txt edit or a future add-screen (A3) is also held to. **Adding the first reference (empty → non-empty `act_refs`) switches `cq_type` to `CQ POTA` or `CQ SOTA` on its own** (SOTA if any SOTA reference is present, a mixed activation defaults to SOTA), in `porta_host_config_set()` ([logging.md](logging.md), **CQ type follows the activation**). Only that one transition derives it — adding or removing a reference afterward never overrides a manual Type change made on this same page.
* **Not on the page:** Call CQ and an entry's own count (the queue's rows) and band/frequency (the radio drawer): each control has one home.
* **Not yet on the page:** the grid check against a station's references (epic [I18](../roadmap/activator-mode.md), **Later**).

The Settings tab's dots (not paired, update available) therefore each lead to an amber row.
* **A page** has **‹ Settings** and its title in a header that stays, and comes in from the right; the menu comes back from the left (no motion under the system's reduce-motion setting). Focus goes to the page's title, and on the way back to the row that opened it. The Settings tab, tapped while on Settings, returns to the menu; leaving the tab and coming back keeps the page. `#network` opens the Network page and `#station` the Station page (`applyHashRoute()`). A warning (`.setnote.warn`) is the radio bar's amber tint with an edge.

### Settings › Radio & bands: In the radio

The radio's own settings (`RADIO_SETTINGS` and `radioSettingRefusal()` in `radio_settings.js`, shared with the SWR sweep, which sets Tune power too; `renderRadioSettings()`; [radio.md](radio.md), **The radio's settings in Radio & bands**): **Tune power (%)** and **Max. ### Settings › Amplifier: the PTT check

**Amplifier**, On or Off (`amp`, [radio.md](radio.md), **The amplifier switch**), is the page's first row. Off, the rest of the page is not shown (`syncAmpDetail()`), the check below is not run, and the menu's row reads "Off"; the main board keeps the settings and puts none in force. On, the page shows them as saved.

**Amp keyed by** (`amp_ptt` in Station.txt: 0 Not checked, the default; 1 TX PTT grounded; 2 TX PTT +5V) says which of the QMX's PTT outputs keys the amplifier. A Micro PA100+ keys from TX PTT grounded (operator, 2026-11-09). Below it, `ampPttCheck()` (host-tested by `webapp/tests/test_amp_ptt_check.js`) compares the radio's own per-band PTT outputs, which the main board reads when the radio connects ([radio.md](radio.md), **The QMX's settings, read at link-up**), on each active band the radio has:

* **Right:** the chosen output alone on. Another TX output on with it would key the amp from both, and an RX output keys it on receive, so either is named. The line then says the radio's model and that every active band is right.
* **Wrong:** an amber line names each active band that differs and what it has on ("40 m: no PTT output on"), and Serial 6 on PTT when it makes the jack a serial port. Below it, **Set the radio's PTT outputs** asks first, naming the bands the radio transmits on (`radioTransmitBands()`), then posts `/api/radio/ptt` with the keying; the main board writes the radio ([radio.md](radio.md), **Setting the PTT outputs**). While `radio_ptt_write` reads `writing` the button is disabled and the line says so; a failure is shown under the bands.
* **Not read yet,** before the read finishes, it says so; Not checked hides the line. It is redrawn on every config poll (`applyOperateLive()`), so a radio plugged in while Settings is open updates it.

### Settings › Software update

**One Update for the station** (maintainer, 2026-11-12; [updates.md](updates.md)): the main board and the sidekick are its parts, named in its progress and in a failure and nowhere else offered apart. **The web app is part of the sidekick's image** ([sidekick.md](sidekick.md), **Web root**), so it moves with the sidekick and is no part of its own: no step installs it, and nothing is fetched for it. The page has two parts. **Installed** shows what runs now: both boards' versions, each as its label and commit, "b1322 (0c5ccec)" (`FwUpdates.versionText()`): **Sidekick and app**, one version for the two, since the app is built into the sidekick's image and stamped with its version, and **Main board firmware**; then the station's **Channel**, Stable or Dev. A line **App, pushed from the bench** shows only while the sidekick serves a bench push, with that app's own build id (`FwUpdates.pushedApp()`; [sidekick.md](sidekick.md), **The bench push**). **A page that is not the app the sidekick now serves says so on a sheet over every tab, with Reload** (`noteServedApp()`, `syncAppSheet()`, `FwUpdates.appStale()`; maintainer, 2026-11-15, at the bench, where a notice on this page alone went unseen): every config reply names the app the sidekick serves (`sk_app`: its own version, or a bench push's build id), the page was stamped with that same string when it was built, and the two differ once the sidekick has been updated, rolled back or pushed to under an open page. It is read from the poll the page already makes, with no fetch of `app.html`, on every reply, one the main board did not answer included (`updateNetInfo()`, which both kinds of reply reach; `webapp/tests/test_app_stale.js` holds that), so it clears by itself; a sidekick that does not say, and an unbuilt page, are never called stale. **It compares build ids, not bytes:** two builds of one changed tree report the same `-dirty` version and are not told apart, which is why a bench push's id carries the time it was built, so each push is another app to a page left open. The sheet reads **The app has been updated**, "A reload is required to use it.", with the one button, **Reload**: there is nothing to decide, so nothing dismisses it. A page from before an update, talking to the firmware after it, is the mismatch the app's place in the image is there to remove, and the state arises only after an update, a roll back or a bench push, none of which leaves a QSO in progress. It is a tap all the same, never a reload by itself, which could take a half-typed setting with it. **One guard keeps a broken setup from shutting the operator out:** the page remembers which app it last reloaded for (`sessionStorage`, this tab), and when a fresh page is still not that app, as when something hands back a cached copy or two sidekicks answer to one name, the sheet does not come back for it; the notice with Reload on this page stays, and the menu's row is amber. It never shows over the update's own sheet, whose **Close** reloads instead (**Result**, below). **Updates** is one line, "A newer build is published" and about how long, and one **Update** button, with "Switch the radio off first." under it (`FwUpdates.offerNote()`). Under it, when the other channel has a build, is its button: **Switch to Stable (0.1.0)** or **Switch to Dev (b1322)** (**Channels**, below). The Settings tab carries a dot while an update is offered, as it does when not paired, and the menu's row reads **Update available**. Nothing on Operate announces an update: Operate has no banners (**Screens**). Settings does not link the sidekick's `/update` page.

* **What is published.** `checkFwUpdates()` reads each channel's manifest for the boards, `https://micro-ft8.kalikstein.com/download/manifest.json` (dev) and `manifest-stable.json` (stable, absent until a release is cut, which is no error; [RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Public Cloudflare mirror**), when the page opens, when it becomes visible and every 60 s while it is; the review reads both again. The HTTPS fetches are what authenticate the hashes ([system.md](system.md), **The inversion**). With no internet from the phone's network, the section says updates cannot be checked from here.
* **Channels.** A station is on stable or dev, read from the version its main board reports and stored nowhere (`FwUpdates.channelOf()`): a release, `0.1.0+0c5ccec`, is stable; anything else is dev, a bench build's bare SHA included ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **An image carries its version**). **Update** goes to the station's own channel's manifest, and a board on that channel is offered only a later build, by its number on dev and its release's on stable, never an older one; a board running anything from outside the channel (the other channel's build, a bench build, a changed tree's) is offered the channel's (`FwUpdates.offers()`). A manifest never offers an image that is not its own channel's. Sentences name a version by its label, "Updated to b1322"; requests and comparisons use the whole string.
* **Switching channel** is the one Update against the other channel's manifest (`fwPlan(target)`, `plan()`'s `switching`): every board that differs is offered, an older build included, by the same review, hold, progress and result. Its review opens "This station moves to the Stable channel, 0.1.0.", and adds "That is an older build than the one it runs." when the station's dev build is numbered above the release's commit (the manifest's `build`); a bench build's age is not known and not guessed, and dev is never older than a release. The main board updates first, so a switch that fails after it already reads as the new channel: the next **Update** finishes it, and Retry reopens whichever of the two it now is. Before 1.0 nothing promises an older build can read settings or a log a newer one wrote. **A switch to a release from before the app shipped in the sidekick's image, 0.1.0, leaves the sidekick with no app of its own:** that image serves its app from the `web` filesystem, which a sidekick on the current table does not have, so after the switch it serves no app, and USB is the way back (how 0.1.0 runs with no `web` partition is not checked). Nothing guards against it: the next release carries its app.
* **The app, on each channel,** is the sidekick's image's: a release's image carries the app built at its tag, and a dev image the app at its commit, so a switch of channel moves the app with the sidekick. A push to `main` that touches only the app builds and publishes firmware too ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md)), so an app change reaches a dev station as an update of both boards: every board whose version differs is offered. There is no "skip this version": the next build replaces it.
* **Unavailable,** with the reason in place of the line, while no main board is linked (the boards update together; a sidekick alone is updated over USB) or the sidekick is on its own access point (no internet to download from) (`plan().unavailable`). **A plan that would leave the two boards on different `PORTA_PROTO_VERSION`s is not offered** (`blocked: 'pair'`, from the manifest's `proto` for a board being updated and `/api/config`'s `sk_proto` and `host_proto` for one that is not): a main board the sidekick cannot talk to can only be recovered over USB.
* **Two questions, before anything happens** (maintainer, 2026-11-13). With a CQ running, a QSO queued or a transmission on the air, the first is the band change's own (`confirmRetune('Update')`, **Band and frequency**): "Update? This ends your CQ…", and a yes ends them by the band change's code (`endQueueAndTx()`), at once, as a band change does; with nothing in progress it is not asked. The second is the update's review (`askConfirm()`, `FwUpdates.reviewText()`), which stops nothing. **It opens with the release notes** (`FwUpdates.notesFor()`; [RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Release notes**): for a station on stable, every release after the one its main board runs, up to the one offered, newest first, so one that skipped a release reads both, each as "What 0.3.0 changes:" and a line per item ("New: …", "Changed: …", "Removed: …"); for a switch from dev, or a main board on no release, the offered release's alone, since a dev build is not ordered against a release by number; on the dev channel, none. They show only there, not again after the update. Then: about how long, that nothing transmits until the update is done, the radio off ("Switch the radio off, or unplug its USB, before you update. If it stays connected it may need switching off and on afterwards."; nothing checks, [main_board.md](main_board.md), **Firmware updates**), and that the update goes on if the phone locks. It does not say the station keeps receiving: the main board decodes nothing while its image is sent. A phone that is not paired is asked to pair instead. The time is "about a minute" for the sidekick alone, "about two minutes" for a main board and "about three minutes" for both, from the bench (2026-11-10: 28 to 42 s and 98 s).
* **What a tap does** (`runUpdate()`). The page posts every firmware offer, the main board first, to `/api/fw/start` as one body the sidekick carries out by itself. That is the page's whole part: the sidekick takes the hold on transmit as it accepts the plan, and the main board ends the queue again, so nothing taken up between the two questions keys ([sidekick.md](sidekick.md), **Firmware updates**), and a phone that locks or leaves from the tap on stops nothing. **A start request that does not get through is asked after, then sent once more** (`postFwPlan()`, `FwUpdates.startCheck()`): the sidekick closes its least recently used connection to make room for a new one, and a browser never sends a POST again by itself, so a network error does not say whether the request arrived. A second later the page reads `/api/fw/status`: the plan already running is a start, another plan running is "An update is already running", and otherwise the request goes once more; a second failure is "The sidekick did not answer", with Retry. Seen once, on 2026-11-15, right after a relay of the app that the page then still ran, with no record of the request on the sidekick and the cause not known, so a start that needed any of this says so on the result, with the browser's own error. Each image's URL is its dated name under `ota/`, which no later publish overwrites, so a build published while an update runs changes nothing in it ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Public Cloudflare mirror**).
* **Progress, on every phone** (`followFw()`, `stepRows()`), on a sheet that covers every tab until the update ends, so nothing under it (the radio bar, the Settings menu) has a state for an update in hand: a list of the steps, each done, in hand or to come: for each board download, verify, send to the main board, restart. A download and a transfer show a percentage, at the end of the row's first line (`stepRows()` gives it apart from the text, so a long step's wrap cannot leave it on a line of its own). Through the firmware the page polls `/api/fw/status` once a second and draws what the sidekick says, so a phone that opens the app mid-update shows the same sheet, and one already open finds it on its next check (when it becomes visible, and every 60 s). **Cancel update** is offered until a board's image is handed over (not while a board restarts). A poll that fails is taken as the sidekick's own restart, the plan's last step.
* **Result:** "Updated to b1322", or the reason ("Verification failed — still on b1321", "New version did not start — rolled back to b1321") with the step it failed at marked and **Retry**, which opens the review again, the update's or the switch's, against what is published then. A phone that did not start the update is shown a result only when the update failed, with no Retry, since it has no plan to run again, and that sheet's **Close** reloads it when the page is by then older than the app the sidekick serves (`fwCloseReloads()`). When the update succeeded, its progress sheet simply goes when the update ends (`followFw()`), and if the sidekick was updated the sheet "The app has been updated" then comes up with Reload (**Installed**, above; seen on the bench 2026-11-15); and a sidekick that comes back idle with no record of the update (it lost power partway) is reported as that after ten seconds, not waited on. A success says to switch the radio back on, and to switch it off and on if it was connected during the update and does not reconnect; when the sidekick was updated it adds "Close opens the new app." After 12 minutes with no result the sheet says to check the phone's network and reload. While the progress or the result is up, **Update** and the channel switch are not shown behind it (`renderFwUpdates()`). **Close reloads the page that ran the update,** into the app the sidekick's new image serves. That page follows the update to its result: one reloaded mid-update is no longer the one that started it and loses the result and Retry.
* **The logic is `updates.js`** (`FwUpdates`: the offers, the plan and its request body, the review's text, the steps, the stale rule, every sentence), host-tested by `webapp/tests/test_updates.js`, which also reads the sidekick's sources and fails when it can report a failure code the page has no words for. `webapp/tests/test_update_flow.js` runs the page's own `runUpdate()`, `postFwPlan()`, `followFw()` and `fwResult()` against a faked sidekick: one tap sends the one request, and a start request that does not get through is asked after and sent again. The sheet itself and its buttons are checked only on a phone.

### Fields

Every text field in the app follows one rule (maintainer, 2026-11-16), and `webapp/tests/test_fields.js` fails on a field that does not:

* **A number is `type=text` with a numeric keypad from `inputmode`** (`numeric`, or `decimal` where a point is allowed), **never `type=number`.** `type=number` has accessibility problems, gives no feedback on a character it drops, suits only values stepped up and down, changes under a mouse wheel, and exposes no selection to script, which select-all needs; the GOV.UK Design System dropped it for these reasons. The field's handler checks the text itself (a plain number, its range) and says what it takes, as `radioSettingRefusal()` and the drawer's frequency do.
* **Every text input says what a tap does, with `data-select`.** `all`: a tap selects the whole value, so the first key typed replaces it; for a number and a short code replaced whole (frequency, offset, Min TX delay, Tune power, Max. PA voltage, call, grid, the CQ's modifier). `off:<why>`, one word: the caret goes where the tap put it; for prose edited in place (`off:prose`, the comment), a field that starts empty (`off:empty`), a secret (`off:secret`) or a name (`off:name`). A second tap on a focused field places the caret either way.
* **How a tap selects** (`webapp/app/fields.js`, loaded by every page with a field): iOS Safari ignores `select()` from a focus handler and puts the caret at the end (WebKit bug 193040), so the selection is set again just after the tap, from focus and from click, and a desktop's first `mouseup` is cancelled so it does not clear it. Checked in Chrome, by mouse and by touch (2026-11-16); on an iPhone it is a field check. If iOS will not hold it, the fallback is a field that empties on a tap and shows its value as a placeholder until something is typed.
* **A refused value says why, in words** ("Tune power: 0 to 99"). Settings resets the field to what the station holds; the SWR sweep keeps a refused value, marked, so **Run** refuses it rather than sweeping at the old one.

### QRZ sync

The QSOs tab's **QRZ logbook** row says how the station's log stands against the operator's QRZ logbook, and sends what QRZ lacks on a tap. `qrz_sync_core.js` is the sync without the page, run under node by `webapp/tests/test_qrz_sync_core.js`; `app.html` holds the row, the key, the switch and the calls a run makes.

* **The row** (`#qrzRow`, above the list, a Settings menu row in shape) is three buttons side by side (`#qrzLine`): the row, whose tap looks again; **Send** when there is something to send, a text action like **Download ADI** and not a filled button, since sending is mostly by itself and a manual send the exception (maintainer, 2026-11-20); and, once a key is set, the CQ row's gear (`#qrzGear`), which opens Settings › Station at the key and the switch without focusing the field, so no keyboard opens. It is the third of the shortcuts the top of this page allows. The row reads what `qrzRowModel()` says, which is pure and host-tested by `webapp/tests/test_qrz_row.js`: **Not set up** with no key, and a tap opens the key on Settings; **Checking…**; **Up to date** (**Up to date · sends as you log** with the switch below on); with the switch on, **1 QSO waiting · sends at 9:08** for QSOs logged since the last run while it waits out the gap between runs, with no **Send**, since they go by themselves at the time it says and a tap on the row sends them sooner, so the row never reads up to date while one waits (bench, 2026-11-20: it did), and a QSO logged while a run is under way gets a run of its own after it, since the run read the log when it started; a QSO whose after-log check runs late, because the phone slept, is not counted when a run since has read the log (`qrzQsoSeen()`, from the station's time on the transmission that logged it, with 10 s for the clocks to differ; bench, 2026-11-20: "1 QSO waiting" for one sent 15 minutes before); **55 to send** with **Send**; **Sending 55…**; and in amber, with what a tap does about it, **QRZ refused the key**, **Cannot reach QRZ**, **No reply from the station**, **Try again in 4 min** (the call budget), or QRZ's own reason. A key for another callsign's logbook says whose it is. A QSO QRZ refuses is a toast with QRZ's reason, and stays counted.
* **It looks by itself and sends on a tap** (maintainer, 2026-11-19): a send is a write to the operator's logbook that we cannot take back, and the first one carries the station's whole history. It looks when the QSOs tab opens and 6 s after a QSO is logged while that tab shows, inside the budget below; the first look after a key is typed or the page loads does not wait.
* **Send new QSOs to QRZ** (`#qrzLive`, under the key, off until turned on) **sends by itself the QSOs logged from the day it was turned on, and only those.** The day is kept with the key (`live`), so turning it on never sends what was logged before: that still shows its count and waits for **Send**. A run is then made 6 s after each QSO is logged, whichever tab shows, and when the QSOs tab opens. It is the same run, with the core told the day (`sendFrom`), so it reads QRZ first like any other; a QSO logged inside the five minutes between runs goes with the run made when they end. Nothing goes with the page closed or the phone locked: the browser does the sync, and the next run catches up. A problem while nobody is looking at the row puts a dot on the QSOs tab (`#tabQrz`), and no toast. A new key starts with it off. Other loggers send each QSO as it is logged behind such a switch (DXLab, Log4OM).
* **The key** is typed on **Settings › Station**, under QSOs (`#qrzKey`), and is kept in this browser (`localStorage`), not on the station: today's firmware has nowhere for it, so each phone, at each of the station's addresses, is given it. On a change the app asks QRZ what logbook it opens and says so under the field ("KB2SLO logbook · 1,310 QSOs", or **QRZ refused this key**); the logbook's callsign is kept with the key, which saves a call on every run. The sentence under it says where the key goes: "Kept in this browser only. It goes to QRZ through micro-ft8.kalikstein.com, which does not keep it." ([system.md](system.md), **Third-party services**).
* **A run reads the station's log itself** (`qrzReadRows()`), apart from the list's own paging: the day files from the last day a run left nothing unsent, each read until a page comes back empty, since a page can come back short with more to follow.

* **QRZ is read before anything is written to it.** An insert there cannot be taken back by us, and QRZ's own duplicate check is not documented, so a QSO goes up only when none of QRZ's records matches it. A run (`run()`) asks the logbook's status for its callsign, reads the station's rows, pulls QRZ's records for those days through the relay, matches, and sends what is left in batches of 10: QRZ takes one QSO a call, and a batch of 50 took 20.7 ms of the relay's CPU against the free plan's 10 ms a request (2026-11-20). A run's 30 calls an hour then send about 280 QSOs, and a larger backlog goes up over the next runs. That makes QRZ's logbook the record of what has been sent: nothing is kept on the station, and a run cut short is put right by the next one.
* **A match** (`match()`) is the same call, band and mode, compared without regard to case, with times within 30 minutes, nearest first, each record used once. QRZ keeps time to the minute, and a record entered there by hand may be some minutes off; LoTW matches within 30. A QSO logged under a callsign that is not the logbook's is neither matched nor sent, since at QRZ that is another logbook; nor is one dated before 2000, which was logged with the clock unset.
* **The days asked for** (`range()`) run from the day before the first usable QSO to the day after the last, so a record a few minutes off across midnight is still found. `daysToRead()` names the day files a run reads: those from the last day up to which every QSO is at QRZ, that day included, which is the day before the oldest QSO still unsent.
* **The app spends relay calls deliberately** (`mayRun()`, `noteRun()`, `callsLeft()`), because the relay is ours and its free plan has a daily limit ([system.md](system.md), **Third-party services**): a run on its own waits 5 minutes after the last, any run waits after a failure (1 minute, doubling to an hour), and an hour sees at most 30 calls. A run stops at its allowance instead of going over it.
* **Measured 2026-11-19** from a workstation, with the Worker's code run there as the relay: 147 QSOs on the station, 84 of them at QRZ and matched to the minute, 63 to send, in 2 relay calls. A run over two day files then sent 8 in 3 calls, and the next look found 92 at QRZ and 55 to send. The page itself was run in a headless browser against the same station and logbook, up to the count and **Send**, and its sending by itself with the inserts answered by a stand-in.

## Build

`webapp/app/` holds the hand-edited sources; what ships is their build, `webapp/dist/app/` and the pack beside it, produced by `webapp/tools/build.py`. **The sidekick's build runs it and embeds the pack** (`python3 webapp/tools/build.py --version <the image's> --pack <file>`, from `sidekick/main/CMakeLists.txt` on every build; [sidekick.md](sidekick.md), **Web root**), so the app a sidekick serves is the one built with its firmware, and building the sidekick needs Node and `npm ci --prefix webapp/tools`. With `MICROFT8_APP_PACK` naming a pack already built, `--pack` copies that file and builds nothing, refusing one that is not stamped with `--version`'s: CI's sidekick job sets it, since ESP-IDF's container has no Node, after building the pack on the runner from the same checkout. CI's Host tests run the build too, so what is tested is what ships. At the bench, `python3 webapp/tools/install_app.py` runs the build and pushes its pack onto a sidekick, which serves it in its image's place until its firmware next changes ([sidekick.md](sidekick.md), **The bench push**): the way to try an app edit on a phone without building firmware. None of the output or the pack is committed.

In order, the build:

1. copies the sources;
2. stamps the build id (`<short sha>[-dirty] <UTC date>`, dirty meaning `webapp/app/` has uncommitted changes; for a release, CI hands the build its version as `MICROFT8_VERSION` and the id is `<version> <UTC date>`, `0.1.0+0c5ccec 2026-11-14`, which a changed tree never takes: `stamp()`) over `app.html`'s one `__APP_BUILD__`. **The sidekick's build hands it the version its image reports** (`--version`, `PROJECT_VER`: [RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **An image carries its version**) and the app is stamped with exactly that, so the app a sidekick serves and the sidekick say the same. The page shows its own stamp nowhere: it compares it with the app the sidekick says it serves, and offers Reload when they differ (**Settings › Software update**);
3. minifies every `.html` and `.js` (`minify.mjs`: html-minifier-terser and terser, versions pinned in `webapp/tools/package-lock.json`);
4. compile-checks every script with `node:vm` and compacts the JSON data files;
5. gzips each asset, keeping its name (**Each asset ships gzipped**, below);
6. fails if the app exceeds 800 KB, counted in bytes as shipped (**The 800 KB budget**, below);
7. writes `webapp/dist/app.pack`, the assets as one file: a header with the build id, an index of names, offsets and sizes, then each asset's bytes as shipped (`webapp/tools/app_pack.py`; the layout is in `sidekick/main/app_pack.h`). It sits beside the built app, never in it, and is rewritten only when its bytes change, so the sidekick's build relinks only when the app did. The sidekick's reader, `sidekick/main/app_pack.c`, checks a whole pack before anything is served from it, and `host_test_app_pack` runs it on a pack this builder wrote.

**Minification is conservative on purpose.** Top-level names are never renamed: the pages share globals across files (`CallInfo` from `callinfo.js`, `MicroFT8Pairing` from the sidekick's `/pairing.js`), and a readable top-level name is what makes an error on a device traceable to the source. Whitespace collapses to one space, never to none. A file the minifier would grow ships as it is. The first build took the app from 637 KB to 469 KB (73%).

**Each asset ships gzipped.** Served as it was, the app was 619 KB of the 800 KB budget. `build.py` gzips every asset at level 9 after minifying, under its own name, with no timestamp or file name in the header, so the same sources build the same bytes; an asset gzip would not shrink ships as it was. The budget counts the bytes as shipped, and the sidekick's image and `install_app.py` carry what the build made. The pack carries no flag for it, so the sidekick tells a gzipped asset by its first two bytes, `1f 8b`, and serves it with `Content-Encoding: gzip` ([sidekick.md](sidekick.md), **Web root**); the build refuses a plain asset that starts with them. `webapp/tools/test_build.py` holds the compress step and the pack. Measured 2026-11-13: 909,917 bytes of source ship as 185,745, `app.html` 51 KB of them.

**The 800 KB budget**, in bytes as shipped, is the firmware slot's: the pack is part of the sidekick's image, which must fit a 4,032 KB slot with the sidekick's own code, about 1.1 MB of it (measured 2026-11-15: an image of 1,288,160 bytes, 186,869 of them the pack). 800 KB keeps the image under 2 MB, half the slot spare for the code to grow (`BUNDLE_MAX`, `webapp/tools/build.py`). Raising it is a choice about the slot, not about the app alone.

**Previewing:** `tools/serve_webapp_local.py` serves the sources at `/app/`; with `--dist` it serves the last build there instead, sending `Content-Encoding: gzip` on a gzipped file as the sidekick does, which is how a minifier problem shows up before a push. Without `--sim` there is no sidekick behind it, so the pages load and render but no API call succeeds; a bench check needs the app on a sidekick: `install_app.py` for an edit to the app alone, or the sidekick flashed with the build (`cd sidekick && idf.py build flash`), which carries it. `--sim` proxies `/api/` to `host_mock/sim_station`, which plays `host_mock/test_qso.json` (or `--scenario`) on a real 15 s clock (`--scale` divides that wait) and serves the same event JSON the sidekick does. Open `http://127.0.0.1:8787/app/app.html`. The simulator's pairing window stays open, so the page pairs without a button press. That is a scripted station, not a radio: USB, CAT, and audio timing are not what it exercises.

## Serving the site

`micro-ft8.kalikstein.com` is `webapp/` deployed by `.github/workflows/pages.yml` to Cloudflare Workers Static Assets, less what `webapp/.assetsignore` names, `webapp/app/` among them: the app ships in the sidekick's image, not on the site. A page of the site that needs the app's data keeps its own copy (`/data/`). **Static by default:** `wrangler.jsonc`'s `run_worker_first` names only `/download/*` (the R2 firmware mirror, [RELEASE_PROCESS.md](../RELEASE_PROCESS.md)) and `/qrz/*` (the relay to QRZ's Logbook API, [system.md](system.md), **Third-party services**), so every other request is a static file served without running `worker.js`, and costs none of the free plan's daily Worker requests. A Worker route added later goes in that list too. A path with no matching file gets `webapp/404.html` with status 404 (`not_found_handling: "404-page"`), also without the Worker, so stray URLs and bot scans cost nothing either.

Static responses get their headers from **`webapp/_headers`** (one rule per path pattern; its comments carry the reasons too). Static Assets reads it from the root of the deployed directory and never serves it; wrangler leaves it, `_redirects` and `.assetsignore` out of the upload by default. It applies to nothing `worker.js` returns, so the Worker's routes set their own headers.

* **`Access-Control-Allow-Origin: *` on every file**, redirects and 404s included: the sidekick's plain-HTTP app reads `/data/ne_10m_places.json` cross-origin (`map.html`), and Static Assets sends no CORS header by default. The release manifests the app and `/update` read are `worker.js`'s, which sets its own.
* **`Cache-Control: public, max-age=31536000, immutable` on `/geo` only.** `geo.html` (**A non-secure origin**) is the one page whose point is working with no network: an operator who reaches it already crossed the hard part, getting internet once. Static Assets' default, `public, max-age=0, must-revalidate` (measured 2026-09-22), forces a revalidation round trip on every visit; immutable with a long max-age lets a browser holding a fresh copy skip the network outright. Every other file changes on every deploy and keeps the default. The rule is on `/geo`, not `/geo.html`: the `.html` form is 307'd to the extensionless URL first, so a header on it lands on the redirect (confirmed live 2026-09-22), and `geo_handoff.js` links straight to `/geo`, one round trip fewer.

**Every HTML page declares `<meta charset=utf-8>` itself**, before anything else in its head, so its encoding never depends on the host. Static Assets has served `text/html` with no charset (measured 2026-09-22), while the sidekick's `app_serve.c` always sends `text/html; charset=utf-8`; without either, the browser guesses, and guesses better the more UTF-8 it sees. That is why the dense, tens-of-KB `app.html` and `map.html` looked fine and the few-hundred-byte `geo.html`, with one non-ASCII character, showed mojibake on a real phone (2026-09-22): not a defect of that page, only the first small enough to expose it. A new page, `getting_started.mjs`'s template included, carries the tag too; the minifier keeps it.

**Download counts.** `worker.js` writes one Workers Analytics Engine data point for each file `/download/` serves (`countDownload()`, the `DOWNLOAD_COUNTS` binding, dataset `micro_ft8_downloads`): the file's key, and how it was fetched, `usb` when the downloads page's **Flash in browser** fetched it (`downloads.html` asks with `?via=usb`) and `download` for anything else. A station's update is a `download` of a key under `ota/`, and a dated dev name there also says which build. A manifest, a `.sha256`, a `HEAD` and a refused or missing key write nothing: pages and stations read the manifests to see what is published. **Nothing about who asked is written,** no address, user agent or country, so a count is of requests, not of people or stations: a retry, a script or a crawler each count, and `?via=usb` is only what the request says. A write that fails is dropped and the file still served. Analytics Engine keeps three months and its free plan takes 100,000 points a day (read 2026-11-18); reading the counts is in [RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Download counts**.
