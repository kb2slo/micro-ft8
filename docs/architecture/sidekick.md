# Sidekick architecture

The AtomS3 Lite sidekick is the station's WiFi and web server: it serves the web app, guards the control API with the pairing token, and relays between the browser and the main board over Port A. Why it is shaped this way (no TLS, the phone reaches the internet): [system.md](system.md).

## Hardware

**M5Stack AtomS3 Lite**, chosen over the NanoC6 it replaced (2026-09-05) for its dual cores: WiFi, lwIP and an HTTP server run beside the Port A UART work, where the C6 has one 160 MHz core.

* **ESP32-S3FN8**: 8 MB embedded flash, **no PSRAM** (confirmed with `esptool.py flash_id`, 2026-09-04). Anything large is staged in flash, not RAM.
* **Grove** (Port A): `GND / 5V / G2 / G1`. **USB-C** is device mode only — flashing and a console, never a USB host ([system.md](system.md), **Why not**).
* **User button**: GPIO41, active low, used to disclose the pairing token. Everything an operator reads calls it **the pairing button**: they see one station, and "sidekick" is our name for a board (maintainer, 2026-11-15).
* **Flash layout** (`sidekick/partitions.csv`, 8 MB): `nvs` at 0x9000, `otadata`, `phy_init`, and two app slots of 4,032 KB, `ota_0` at 0x20000 and `ota_1` at 0x410000, which fill the part. No factory slot and no filesystem: the app is in the image (**Web root**) and the station's data is the main board's ([updates.md](updates.md), **Decided**). It is final for 1.0 ([release-1-0.md](../roadmap/release-1-0.md#n75z)): a change costs every unit a USB flash, which erases it (**First install**). No code holds an offset (the slots are found by `esp_ota_get_next_update_partition()` and `esp_ota_get_running_partition()`; only `tools/merge_sidekick_bin.sh` names offsets), so a sidekick on the table before this one, two 3 MB slots and a `web` partition nothing mounts, still takes an image over the air while it fits 3 MB, and refuses a larger one with `size` (checked 2026-11-15: one on that table took this build's image, and on this table an update booted from 0x410000 and a broken image rolled back).
* **Over USB it enumerates as Espressif's generic `303A:1001`** with no board string, like any ESP32-S3 on native USB. The MAC address is the only reliable way to tell one from another; a differing flash vendor is a production-batch artifact, not a model identifier.

Building, flashing, and backing up a unit's stock firmware: [`sidekick/README.md`](../../sidekick/README.md).

## Web root

**The web app is part of the sidekick's firmware image, and is served from it** (maintainer, 2026-11-15; [updates.md](updates.md), **Decided**).

* **Served locally, not loaded from the internet.** An HTTPS page cannot reach `http://micro-ft8.local` (browsers block active mixed content, with no exception for private addresses), and an app fetched from the internet each session does not exist on a summit. Served from the sidekick, the app and the API are the same origin.
* **Inside the firmware image,** so the app and the firmware are one artifact: an update moves both, a rollback brings both back, and a sidekick flashed over USB serves the app with no internet. Kept apart, on a filesystem the phone installed it to, the two could be left on different builds by a failed step or a rollback (2026-11-15: a dev app on release firmware until Retry), and a newly flashed sidekick had no app until it found internet.
* **One pack, embedded as built.** The sidekick's build runs the web build, which writes the app as one pack ([webapp.md](webapp.md), **Build**), and embeds that file as it is (`sidekick/main/CMakeLists.txt`). A target that runs on every build writes the pack, rewriting it only when its bytes change, and the embed depends on that target, so an image cannot link with a pack older than the sources and an unchanged app relinks nothing. Nothing of the app is read when the build is configured: a size read then once went stale and truncated every page served (2026-09-20), so the pack's length at run time is the linker's own, its end symbol minus its start. The build needs Node and the web build's packages (`npm ci --prefix webapp/tools`); CI builds the pack on the runner and hands it to the build in ESP-IDF's container, which has no Node (`MICROFT8_APP_PACK`). Measured 2026-11-15: an image of 1,288,160 bytes in a 3 MB slot, 186,869 of them the pack.
* **One version.** The build stamps the app with the version the image reports, one string handed to both (`PROJECT_VER`; [webapp.md](webapp.md), **Build**), and `/api/config` names the app the sidekick serves as `sk_app`: that version, or the build id of a bench push. A page whose stamp differs is no longer what a reload would get, and offers one ([webapp.md](webapp.md), **Settings › Software update**), from the config poll, with no fetch of `app.html` to compare.
* **Served from mapped flash, never copied** (`app_serve.c`). The embedded pack is read-only data the chip maps from flash. At boot `app_pack_open()` checks the whole pack (`app_pack.c`, host-tested by `host_test_app_pack` on a pack the web build's packer wrote); then `GET /<name>` finds the name in its index and sends the asset's bytes from where they lie, in one call with their length. There is no file, no staging and nothing to be half-written, and no heap is used: a whole-file read of `app.html` once failed for want of one contiguous block (2026-09-21), and the 16 KB buffer that replaced it is gone too. A name is looked up, never opened, so one with a slash or dots in it matches nothing. On the bench a pushed pack can take the image's place (**The bench push**).
* **The bootstrap pages,** `sidekick/main/web/` (provisioning, `/update`, `pairing.js`, the error pages), are embedded by a CMake glob and served from their embed the same way; a name that is neither an asset nor one of them is a 404. `error.html`, `provision.html` and `saved.html` go out through `web_page.c`'s `{{...}}` substitution, and `update.html` through the same call with none (`wifi_prov.c`).
* **A gzipped asset is served as one.** The web build gzips each asset where that shrinks it, under its own name ([webapp.md](webapp.md), **Build**), and refuses a plain one that starts with gzip's magic, so `get_static` reads an asset's first two bytes: `1f 8b` adds `Content-Encoding: gzip`. `Accept-Encoding` is not consulted, every browser taking gzip. The bootstrap pages are plain.
* **Factory reset** (`POST /factory-reset`, pairing-guarded, both modes) erases the `sidekick` NVS namespace (WiFi credentials, AP-mode flag, pairing token) and drops a bench push, then restarts as a new unit serving its image's app. It resets the main board first, with the `FACTORY_RESET` Port A action (v7): the P4 reseeds its Station settings to defaults in place (no restart, since a P4 reset can leave the QMX unenumerated, row [qdcm](../roadmap/declined.md#qdcm)), cancels TX and clears the queue, the CQ with it, and with `?logs=1` also deletes the daily QSO logs. The sidekick wipes itself only if the board ACKed; no link, a transmission on the air or a storage fault answers `{"ok":false,"why":"main board: …"}` and changes nothing, so a sidekick with no main board attached cannot be reset from the app (`idf.py erase-flash` does it).
* **Budget:** the web build holds the app to 800 KB as shipped ([webapp.md](webapp.md), **Build**), because the pack is part of an image that must fit a 4,032 KB firmware slot, the sidekick's own code about 1.1 MB of it.

## The bench push

For work on the app at the bench, `python3 webapp/tools/install_app.py` builds the app and sends its pack to the sidekick in one request, and the sidekick serves it in its image's place: an edit to the app is on the phone in seconds, with no firmware build. It is a bench tool and no way to ship: no page sends one.

* **`POST /api/app/push`** (token required), the body a pack ([webapp.md](webapp.md), **Build**). The sidekick writes it into its spare firmware slot, where a firmware update stages its image, from the slot's second flash sector on, each sector erased as the write reaches it. It then maps the pack, checks its SHA-256 where it lies, which is a read back of what was written, and checks it as a pack (`app_pack_open()`); only then does it write a header into the slot's first sector (`post_push()`, `app_serve.c`). The header is erased first and written last, so the slot holds a whole push or none, and a push cut short leaves the image's app served. The answer is `{"ok":true,"build":…}`, the build id of the pack now served.
* **Pinned to the image it was pushed onto.** The header names the running image by the SHA-256 of its ELF (the app description's `app_elf_sha256`), not by its version: two builds of one changed tree report the same `-dirty` version and are different images. At boot the sidekick serves a push only when the header in its spare slot names the image that is running (`app_push_head_read()`) and the pack's hash and form still check. So any firmware change returns a station to its image's app: after an update or a roll back the spare slot holds a firmware image, and after a USB flash of another build the header names an image that is not running. The same image flashed again is no change, and a push onto it is still served. **A release serves no push whatever its slot holds** (the same function, by the running version): the slot has other writers, a main board's image being staged there as plain bytes, so the rule is held where a push is served and not only where one is accepted.
* **The push, and only the push.** While one is served, `GET /<name>` looks only in it: a name it lacks is a 404 though the image's pack has it, so a page is never one build's HTML with another's script. The bootstrap pages are the image's either way.
* **Refused** with 409 and `{"ok":false,"why":…}` (`app_push_refusal()`, host-tested by `host_test_app_push`): `release`, by an image whose version is a release's (`0.1.0+0c5ccec`), a check made at run time and not compiled out, so a release is the same code its dev build was and serves only the app it was built with; `busy`, while a firmware update runs, since its image is staged in the same slot; `confirming`, while the running image is on trial, since the slot holds the image to go back to; `size`, a body that is no pack or does not fit. A pack that fails its checks after the write is a 400 `pack`, and a flash write that fails a 500 `flash`; either leaves no push.
* **Any update ends it.** An accepted `POST /api/fw/start` stops serving a push and erases its header before the image is fetched (`app_serve_drop_push()`): a main board's update too, and one that fails before its first byte, which would otherwise write nothing to the slot. That handler runs on the HTTP server's one task, the only task that reads the mapping, so nothing is being served from the slot as it is unmapped. A factory reset drops a push too.
* **What it costs:** the spare slot's contents. After a push the slot no longer holds the firmware image this one replaced, as after a main board's update, which stages there too. A confirmed image is never rolled back, so that image was only what the bootloader would fall back to if the running one stopped being bootable.
* **`install_app.py`** builds, asks, sends, and checks that the sidekick answers with the build it sent. It asks first with a request that carries no pack, which a sidekick that would take one answers `size`: a refusal sent ahead of a pack still arriving can be lost, and firmware from before the push answers 405 and closes the connection, which the tool turns into "flash it". Each refusal has its own words (`tools/test_sidekick_http.py`, which also fails when the sidekick can refuse with a code the tool has no words for). The app it builds is stamped with the web build's own id and the time, `<sha>[-dirty] <UTC date> <time>`, not with a version: Settings shows it on a line of its own, **App, pushed from the bench**, and since a page is offered Reload by comparing build ids, each push must have one of its own (`push_stamp()`).
* **Mapping a pack from the spare slot, and unmapping it as an update starts, are checked only on a device** (TEST_PLAN, Pending).

## Firmware updates

The sidekick downloads firmware images itself, from the release host over plain HTTP, and refuses any image whose SHA-256 differs from the one the web app read over HTTPS and handed it behind the pairing token (the trust argument: [system.md](system.md), **The inversion**). The image never passes through the browser, and the update goes on with the page closed. **The sidekick's own image carries the web app** (**Web root**), so the app is updated, put on trial and rolled back with it, and an update has no step for the app. It has no PSRAM, so an image is staged in flash, in its spare OTA slot: its own next image, or a main board's, which it then sends down Port A (**A main board's image**, below; the main board's side is [main_board.md](main_board.md), **Firmware updates**). One image is staged at a time, so two boards are updated one after the other.

Every decision is in `fw_policy.c`, host-tested (`host_test_fw_policy`), the transfer to a main board included, which the test runs against the main board's own receiver over a link that loses frames. `fw_update.c` is the download, the flash writes and the restart.

* **`POST /api/fw/start`** (token required). The body is one `key=value` per line: `board` (`sidekick` or `main`), `url`, `size`, `sha256` (64 lowercase hex) and `version`, each once, as the manifest's `ota` entry gives them ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Public Cloudflare mirror**). **A body may hold two images,** separated by a line reading `next`, which the sidekick carries out in order with no page needed in between: each board once, and its own image last, since installing it restarts the sidekick (`fw_plan_parse()`). A malformed field is a 400 naming it, and a plan that breaks those rules a 400 `plan`. A request that cannot start is a 409 with `{"ok":false,"why":...}`: `busy` (one is running), `confirming` (the running image is still on trial, and the spare slot holds the image to go back to), `offline` (not joined to a WiFi network: on its own access point it has no internet), `size` (larger than the slot), or `no_host` (a main board's image and no main board answering). Otherwise it answers at once and a task does the rest.
* **The URL is plain HTTP only,** to any host: the hash is what is trusted, and whoever holds the pairing token could already do anything. `fw_url_ok()` refuses anything else at the API, and the client is ESP-IDF's `esp_http_client`, built with `CONFIG_ESP_HTTP_CLIENT_ENABLE_HTTPS` off so it cannot open an HTTPS URL either. The library links its TLS code all the same, 91 KB of the image that nothing calls (1,102,368 bytes against 1,011,232 with a client of our own over a socket, measured 2026-11-10): a proven client was judged worth more than the flash, and linked code costs no heap. The rule is about what the sidekick calls, not what is in its image (**Why the sidekick has no TLS**).
* **Download, then four checks, then restart.** The image is written to the spare slot as it arrives (`esp_ota_begin()` with sequential erase). It is refused, and the running image left as it was, unless: the byte count is `size`; the SHA-256 is `sha256`; ESP-IDF accepts it as an app image for this chip (`esp_ota_end()`); and the project name and version built into it are this project's and the requested `version`. Only then is it made the boot image, and the sidekick restarts 2.5 s later.
* **`GET /api/fw/status`** (open) is the progress, held on the sidekick, so any phone sees the same: `state` (`idle`, `downloading`, `verifying`, `transferring`, `restarting`, `done`, `failed`), `plan` (each image's `board`, `version` and `size`, in order) and `step` (which is in hand); that image's `board`, `version`, `got` and `size` in bytes (downloaded, or sent to the main board); `why`, `at` (the state it failed in) and `detail` for a failure; `running` (the sidekick's version now), `host` and `host_linked` (the main board's version, from its HELLO, and whether one came in the last 16 s) and `online`. A failure's `why` is `connect` (no DNS answer or no route: most often a network with no internet), `download`, `http` (the status in `detail`), `size`, `hash`, `image`, `version`, `flash` or `cancelled`, or, from a main board's update, `link`, `no_slot`, `host_restarted`, `host_flash`, `host`, `rolled_back` or `no_host`. **`POST /api/fw/cancel`** (token required) stops an update until the image is fully handed over.
* **A new image runs on trial, and must earn its place.** The bootloader goes back to the image before it at the next restart unless the new one is marked valid (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`). It is marked valid once it has sent three Port A beacons and is reachable: joined to the WiFi network again, or, on its own access point, having answered a `GET /api/fw/status`. Together those show it can take the next update. Joining is enough, with no client heard from, because the phone that started the update may be locked by then. One that is not reachable within 300 s restarts itself, which is the roll back (`fw_confirm_decide()`). So an image that boots but cannot get on the network undoes itself, with no cable, and one that crashes at boot is rolled back by the bootloader at once. An image written over USB is never on trial.
* **What came of it survives the restart.** Before restarting, the sidekick stores the target version and the one it came from in NVS (`fw_last`); after, `/api/fw/status` carries `last`: `board`, `version`, `from` and `result` (`confirming`, `ok`, or `rolled_back` when what is running is not the target).
* **From a workstation,** `python3 webapp/tools/install_firmware.py` installs a local build the same way: it serves `sidekick/build/sidekick.bin` on the LAN, posts the request with the cached pairing token and follows the status to the result. It is how a build that is not on `main` is installed over the air, a deliberately broken one included.
* **An update stops transmission first, and nothing checks for a radio.** On an accepted start the sidekick tells the main board an update is running (`host_link_update_mode(true)`, the `UPDATE_MODE` action) before it fetches a byte, and drops a bench push, which lies where the image is about to be staged (**The bench push**); says so again every 20 s while it runs (`fw_hold_refresh_due()`), and says it is over when it fails or is cancelled; the main board holds transmit off in between ([main_board.md](main_board.md), **Firmware updates**). A sidekick that has just started says "over" once, at the main board's first HELLO, which ends the hold of its own update and of one it lost power in. The message is sent and not waited on: a lost "on" is said again, and a lost "off" is covered by the main board's own 90 s timeout. This holds for every update, the sidekick's own included, though only a main board's restarts the board that keys the radio: an operator sees one update, and it behaves one way (maintainer, 2026-11-12). The operator is still asked to switch the radio off, by the app's review.
* **`/update`, the way back when the app will not load** (`sidekick/main/web/update.html`, open; the request it makes needs the token). It reads `/api/fw/status`, takes the station's channel from the main board's version as the app does ([updates.md](updates.md), **Decided**), reads that channel's manifest over HTTPS, and posts every board whose version differs from the manifest's to `/api/fw/start`, the main board first, an older build included, since it restores rather than updates; then it follows the status to the result. Like the app's **Update** it needs a main board linked and the sidekick on WiFi; otherwise the way out is USB (**First install**). It is served from the image and needs nothing of the app, which is why it stays: the trial does not notice an app that fails to load. Once it has seen the update running it takes the sidekick's idle for the end, with `last` for what came of it, since a restart can fall between two of its polls and none fail (2026-11-15). Its script is host-tested by `webapp/tests/test_update_page.js`.
* **What the release host must provide:** the manifests over HTTPS with a publicly trusted certificate, since their hashes are what each image is checked against; and an `Access-Control-Allow-Origin` that lets the sidekick's plain-HTTP page read them, a capability and not a security control (`worker.js` sets it on `/download/*`). The fetch stays a simple request, `GET` with no custom headers, so no CORS preflight. Measure any new host before adopting it (the `curl` in [system.md](system.md), **Third-party services**); GitHub Releases, for one, sends no CORS header.

### A main board's image

* **Staged as plain bytes.** `esp_ota_end()` refuses an image built for another chip, so a main board's image is written to the spare slot with the partition calls, each sector erased as the write reaches it. The size and hash are checked as for the sidekick's own, and the version is read from the image's app description (`fw_image_version()`). The main board checks the rest when it has the image.
* **Sent a chunk and its answer at a time** (`fw_transfer_run()`): `FW_BEGIN` with the size, the SHA-256 and the version; `FW_CHUNK`s of 240 bytes, each answered with the next offset wanted; `FW_END`, on which the main board checks the image, makes it the boot image and restarts (`porta_proto.h`, **Firmware update**). A message with no answer in 3 s (10 s for `FW_BEGIN`, 30 s for `FW_END`, which reads the whole image back) is sent again, five times for a chunk, and then the update fails with `link`. **Before a message is sent again the sidekick sends filler,** 259 zero bytes (`PORTA_PROTO_RESYNC_LEN`, `host_link_resync()`), which no decoder can take for a frame's start and which is longer than any frame one can be in the middle of. Without it a retry can be lost the way the first try was: on the bench (2026-11-10) the sidekick's HELLO lost bytes on its way to a main board that was writing flash, the decoder took the next chunk for the rest of that frame, then found a sync byte in the image's own bytes, and five tries in a row went unanswered ("stopped answering during the transfer", 308,400 bytes in). `host_test_fw_policy` reproduces that with the real decoder and an image that is the worst case, and shows the filler getting the first retry through.
* **An interrupted transfer goes on from where it stopped.** Every answer says where the main board is, so a lost frame costs one resend. A `FW_BEGIN` for the image the main board already holds part of is answered with the bytes it has: after a failure, starting the same update again downloads the image again and sends only the rest. A main board that restarted has forgotten the transfer and it starts from 0. Seen on the bench (2026-11-10): the sidekick lost power 199,680 bytes in, and the next run sent the rest and the image booted.
* **While a transfer runs, replies are read as they arrive.** `uart_read_bytes()` waits out its timeout unless its whole buffer fills, which would add 50 ms to each chunk's 9-byte answer, so the receive task waits for one byte and takes what came with it (`host_link_fw_active()`).
* **Done means the new version reported in and was kept.** After `FW_END` the state is `restarting` until the main board's HELLO carries the requested version and the main board says it has kept the image: the sidekick asks with an `FW_END` abort, which with nothing to abort is answered OK, or `TRIAL` while the image is still on trial ([main_board.md](main_board.md), **Firmware updates**). Normally that is within 5 s of the restart. The version alone is not enough: on the bench an image that never counted the sidekick as heard said HELLO for 120 s and then went back (2026-11-10). A HELLO with another version, later than 4 s after `FW_END` (its old image is still running for the first moments), is `rolled_back`; neither in 240 s is `no_host` (`fw_host_result()`).
* **Transfer time: 74.4 s for an 872,384-byte image** (2026-11-10, P4 and sidekick at `7fdc14c`), about 11.7 KB/s or 20 ms a chunk, with no chunk refused or resent and no CRC errors; a whole update of the main board took 98 s. Stop-and-wait at `PORTA_BAUD`; the main board answers from its 10 ms loop. The sidekick logs each run to its console and the app's log (`SK firmware transfer: <sent> of <size> bytes in <s>`; less than the image is sent when the main board already held part of it).
* **From a workstation:** `python3 webapp/tools/install_firmware.py --board main` sends `poe_p4/build/poe_p4.bin` the same way, and `--both` posts both images in one request, as the app does.

## Why the sidekick has no TLS

"TLS on the sidekick" is two questions with different answers.

**As a client — the sidekick calling out over HTTPS: not needed, and not free.**

* **Nothing needs it.** The phone reaches every internet service ([system.md](system.md), **The inversion**). The one thing the sidekick will fetch, firmware, is checked against a SHA-256 the browser read over HTTPS, which proves integrity as well as TLS would; TLS would add only confidentiality, for a public file.
* **Its costs, weighed honestly.** Some are weaker than they first looked:
  * **Flash:** ~116 KB, measured on this target. Affordable: the image is about 1.25 MB in a 4 MB slot.
  * **CA bundle:** it must track root-certificate rotation. Weak, since the device updates itself; only a device offline for years falls behind.
  * **Clock:** checking certificate dates needs the right time. Weak: ESP-IDF's mbedTLS skips the date check by default.
  * **RAM:** a handshake needs tens of KB of heap on a board with no PSRAM that is already running WiFi and the HTTP server. **Unmeasured**, and the one cost that could decide it outright.
* **The cost that holds is architectural.** Once the device can speak HTTPS, the easy path for every new online feature becomes "have the sidekick call it". That erodes the inversion, and those features would then fail in AP mode, where the sidekick has no uplink, while the phone often still has cellular.

**As a server — the browser reaching the sidekick over HTTPS: it would fix our one real security limit, but it cannot be done properly.**

* **What it would fix.** The pairing token and all control traffic cross the LAN in clear ([system.md](system.md), **Who may key the transmitter**). HTTPS would close that, and would also make the app a secure context again: geolocation, a service worker, an offline cache ([webapp.md](webapp.md), **A non-secure origin**).
* **Why it can't be done properly.** Browsers trust a certificate only for a name a public CA can verify, and `micro-ft8.local` resolves on one LAN.
  * A **self-signed** certificate means a full-page warning to click through on every new phone and browser.
  * A **private CA** means installing a root certificate on every phone.
  * The scheme that works — a public domain name that resolves to the device's LAN address, with a CA-issued certificate — puts the private key on the device and needs renewal every few months. Renewal needs internet and a correct clock, exactly what a summit in AP mode lacks.
* **So the limit is accepted and scoped**: a nuisance control, on WPA2/WPA3 networks.

**Reopen TLS as a client** if the release host stops serving plain HTTP, or a feature needs the sidekick itself to reach an HTTPS-only service with no phone present. Measure the handshake's heap first. **Reopen TLS as a server** if a way appears to give a LAN device a browser-trusted certificate without renewal or a clock, or if the station will be operated on networks its owner does not trust.

## The access point

With no WiFi credentials, after a sustained loss of its network, or when the operator picks AP mode, the sidekick runs its own network at `192.168.4.1`, answering to `micro-ft8.local` over mDNS (`wifi_prov.c`, `start_ap()`). Two clients at most.

* **Name and password are the operator's to set** (Settings > Network, `POST /ap-config`, token required). The default is the open SSID `micro-ft8.local`; a password makes it WPA2-PSK (8 to 63 characters). Both live in NVS (`ap_ssid`, `ap_pass`) and no route returns the password. Saving in AP mode answers, then restarts the AP; in station mode it only saves. **Why:** an open AP is what a phone with no internet offers to join, and on 2026-10-09 at a park that drew people to it. **Why not a hidden SSID:** a phone must then be told the name by hand, and with a password it adds nothing. **Recovery:** holding the pairing button for about ten seconds erases both and restarts (`button_check_hold()` in `main.c`), so a forgotten password needs no WiFi to undo. The seconds held ride on every `GET /api/events` reply as `hold`, and the page shows a card from the second second (`updateResetHold()` in `app.html`); the total is `WIFI_PROV_AP_RESET_HOLD_SECS`, sent as `hold_of`; the restart waits 1.5 s after the last second so the card can say it is resetting; a factory reset does the same. The press at the start of a hold also opens the pairing-token window, as any press does. **Not yet verified on a phone:** TEST_PLAN, the AP name and password row.

* **The lease is address-only: no router, no DNS server** (`ap_lease_local_only()`). The sidekick has no uplink, so an offered router is a default route to nowhere that the phone may try before cellular: on the 2026-10-09 activation, with a lease offering both, the phone had internet only some of the time, while with WiFi off it had it throughout ([system.md](system.md), **Connectivity**). Without a route out, the AP is a local link and internet can only go over cellular. Field-checked 2026-10-10 (sidekick `2e3e323-dirty`, iPhone): the lease showed no router, and over 30 minutes on the AP every internet use worked. `CONFIG_LWIP_DHCPS_ADD_DNS=n` (`sdkconfig.defaults`) is part of it: with it on, IDF offers its own address as DNS whatever the code asks, so `wifi_prov.c` refuses to build with it on.
* **Why not a captive portal:** it cannot coexist with an address-only lease. iOS raises the portal sheet only when its probe goes out over the WiFi, which needs an offered router and a DNS server answering every name with `192.168.4.1`. The sheet reaches "Done" only when that probe gets Apple's success page, and from then on iOS treats the WiFi as its internet. Tried with DHCP option 114, 2026-09-20/21: the sheet never reliably reached "Done", iOS kept re-intercepting page loads in Safari, and the captive state fought cellular. Option 114's standard API (RFC 8908) needs an HTTPS URL, which the sidekick cannot serve (**Why the sidekick has no TLS**). Instead, the SSID names the address to open, and the setup sheet's QR codes open it.

## The name `micro-ft8.local`

* **The sidekick answers `micro-ft8.local` over mDNS in both modes** (`mdns_bring_up()`, `wifi_prov.c`; `espressif/mdns` 1.15.1), and advertises `_http._tcp`. It has no IPv6 address, so AAAA questions go unanswered and a phone uses the A record.
* **On a home network, a failed lookup is usually WiFi multicast loss, not the responder.** Measured 2026-11-01 in station mode, from a laptop on the same WiFi: 17% of mDNS questions sent to the multicast group went unanswered, while the same question sent unicast to the sidekick's address was answered 59 times in 60, and ping lost under 3%. An access point sends multicast with no acknowledgement or retry, so a phone's lookup can fail while the sidekick is up and serving. mDNS 1.8.2 and 1.14.1 missed at similar rates with the WiFi dropped every two minutes (13% and 18%), so the library version does not change it. The lever is the access point's multicast handling (a multicast-to-unicast option, where it has one), not our firmware.

## First install

USB-C is the only wire flash path: the ROM bootloader listens only on UART0's default pins, never on Grove ([`sidekick/README.md`](../../sidekick/README.md)). A new unit is flashed with the merged `0x0` image (`tools/merge_sidekick_bin.sh`, or the downloads page); it then serves the app, which is in that image (**Web root**), with no internet needed, and after that it updates over WiFi (**Firmware updates**).

**A USB flash is a full wipe** (maintainer, 2026-11-15). The merged image is written from 0x0, and `merge_bin` fills its gaps with 0xFF, NVS at 0x9000 among them; the downloads page erases the whole chip first (`eraseAll: true`, `webapp/downloads.html`). So the sidekick forgets its WiFi and pairing and comes up on its own network as a new unit, and one flashed over USB is never on trial. It is for a new setup or a full recovery, and the downloads page and Getting started say so; every update is over the air. Checked 2026-11-15 with `esptool`'s erase and a write of the merged image at 0x0: the sidekick booted `ota_0` with no stored credentials and its own network up.

## Port A: the link to the main board

Everything the app needs crosses Port A: decodes at slot cadence, TX control, config reads and writes, and the log. The message set is defined in `components/porta_proto/include/porta_proto.h`, which is the source of truth (host-tested by `host_test_porta_proto`); the sidekick side is `host_link.c`, the main-board side `components/porta`.

* **Framed messages over a byte pipe**, with framing that assumes no stream, so the transport could change without touching the app or the API.
* **Board-agnostic**: specified against the application, never against board hardware, so a second main board could be added without a per-board build or `#if` in the sidekick.
* **Versioned** (`PORTA_PROTO_VERSION`, carried in HELLO), so each end can say which protocol it speaks apart from which build it is. A mismatch is logged, not refused, so both ends must be flashed together when it changes. **Both ends send HELLO** every 5 s, with the protocol version and the build's version; the sidekick serves the main board's in `/api/config` as `host_fw_version` and `host_proto`, beside its own `sk_fw_version` and `sk_proto`. **Frozen from v15 (2026-11-10):** the frame, HELLO, ACK and NAK, the `UPDATE_MODE` action and the `FW_BEGIN`, `FW_CHUNK` and `FW_END` messages never change layout, so any two builds from v15 on can carry a firmware update between them, whatever else differs; `host_test_porta_proto` pins their bytes. v16 and v17 (2026-11-10) kept those bytes: `UPDATE_MODE` is now only ACKed, for the sidekicks of v15 and v16 that still ask it before their own update, and a v17 sidekick does not send it. That an update from `62e1c70` (v15) to `1e55290` (v16) carried both boards across is the rule working. v2 (2026-09-28) added each DECODE's slot index and length and the dial frequency at the middle of its signal, which the main board takes from `components/dial_history` (the frequency the radio reports is noted there, `radio_control_dial_tick()`: [radio.md](radio.md), **The dial a decode was heard on**); the sidekick relays them in `/api/events` as `si`, `sl` and `fq`. v4 (2026-09-30) added the SWR sweep ([radio.md](radio.md), **The SWR sweep on the main board**): the `SWEEP_START` action, which `POST /api/swr/start` (token required, body `lo-hi-step,lo-hi-step` in kHz, at most 12 ranges) sends, and the `SWEEP` event, served in `/api/events` as a row with `"d":6` and `k` (0 point, 1 band skipped, 2 done, 3 aborted), `r` (the range), `hz`, `swr` (hundredths, -1 none) and `why` (0 cancelled, 1 CAT lost, 2 stalled). Stopping is the existing `/api/tx/cancel`. The sidekick only relays: the host validates the ranges and its own state and answers with `{"ok":false,"why":...}`. v10 (2026-10-24) added the `RADIO_STATE` event ([webapp.md](webapp.md), **The radio bar**), served as a row with `"d":7`, `hz`, `tx`, `md` (the MD digit) and `sp`. v11 (2026-10-27) added the `ACTIVITY` event ([decode.md](decode.md), **Band activity**), about one a second while receiving; v12 gave it a frequency mask per block. It is served as a row with `"d":8`, `si`, `bm`, `b`, `lo`, `hi`, `v` and `m`. v20 (2026-11-17) gave `QUEUE_ENTRY` the entry's mode (0 FT8, 1 FT4: a number, so a later mode needs no new bit), the dial it transmits from (on one QMX its mode's dial on the band, worked out as the event is sent) and the QSO's held offset ([autoseq.md](autoseq.md), **TX offset**), 0 until the entry's first transmission is armed (one waiting behind another reads 0), served in its `"d":2` row as `md`, `fq` (the name decodes use for the dial) and `off`. The P4 builds the event from the queue entry in `queue_entry_event()` (`components/autoseq/include/queue_event.h`), which `host_mock`'s scenarios share. The event ring holds 128 rows, so a page that polls about once a second keeps up with a sweep (about 1.3 points a second) but one that sleeps through it does not; the page marks what it never received as missing ([webapp.md](webapp.md), **The SWR sweep**).
* **Port A rests at 2500000** (`PORTA_BAUD`). Both main boards held 14 MB both ways at that rate with no drops or CRC errors (2026-10-01), and decodes reached the app with the link opened there. 4000000 did not. With the receiver on during a link test at 2500000, no extra hiss was audible. The frame stays 255. A firmware update waits on one answer per 240-byte chunk (**A main board's image**); a window on `FW_CHUNK` would be the fix if its measured time is too long (idea [w7rf](../roadmap/ideas.md#w7rf)).
* **What held that rate.** The UART FIFO is 128 bytes. Both boards' UART interrupts are in IRAM so a flash access cannot stall them (`CONFIG_UART_ISR_IN_IRAM`; the main board's since 2026-11-10, when its own flash writes during a firmware update were seen to cost frames), and its receive buffer is 8192 bytes, large enough for one fill of the peer's 4096-byte transmit ring. The P4 receive buffer is 4096, with a separate reader. The decoder does not rescan after a lost byte.
* **The stress test stays in the page, hidden.** `#linkTest` in `webapp/app/app.html` has the `hidden` attribute. Remove it to show Bytes, Baud, Run, and Stop. `POST /api/link-test` with `rx`, `rx <bytes> <baud>`, or `stop` is unchanged (token required); `GET /api/link-test` is the live counters. Bare `rx` is 14 MB at `PORTA_BAUD`. The sidekick is the coordinator. A rate other than the resting rate is one switch, then both ends return to `PORTA_BAUD`. The run does not key the radio. Protocol version 6. The codec is `host_mock`-tested.

* **The sidekick's build identity** is the version its build reports, from `tools/git_version.cmake`: its channel's version from CI, or its exact git SHA plus a dirty flag ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **An image carries its version**). CI pins `MICROFT8_GIT_SHA`, because a pull request builds a synthesized merge commit that is not the SHA anyone can check out.
* **Asymmetric traffic**: commands are rare and want low latency; decodes arrive every 15 s and tolerate hundreds of milliseconds. A full slot of decodes is about 3 KB, so sustained load is a couple of hundred bytes per second.
* **An events or state reply is sent a few KB at a time** (`batch_add()`, `host_link.c`): its rows are written into one 4 KB buffer, sent as a chunk when full. One chunk per row was six small socket writes an event, each held back by TCP until the last was acknowledged, so a full ring took 1 to 2.5 s to send and every other request waited behind it, and a reader that fell behind asked for more next time. Batched, a whole-ring reply (19 KB) took 99 ms median and 226 ms at worst, against 265 ms and 2.6 s (2026-11-08, sidekick on USB power, `tools/sidekick_latency.py`).
* **The browser polls** `GET /api/events?since=<seq>`; the sidekick keeps a ring of the last 128 events (`RING_LEN`, `host_link.c`) so a client can catch up after a short gap. That is about 55 s on a quiet band and 26 s on a busy one with FT8 and FT4, where decodes, state and activity come to about 5 events a second; at 64 a stalled server lost events in under a minute (2026-11-07, `sk_ring_gaps`). An event is 180 bytes and the S3FN8 has no PSRAM, so the ring is internal RAM; larger waits for `sk_heap_min` to show room. A client that falls behind skips to the oldest event the ring holds; repairing that is row [p8yv](../ROADMAP.md#p8yv)'s. Config is `GET /api/config` (open) and `PUT /api/config` (token-guarded).
* **A page that has just loaded reads `GET /api/state?slots=<n>` first** (open): the station as it is now, in `/api/events`' shape, and then polls from its `seq`. The sidekick builds it from the same events, in the same critical section as the ring (`event_state.c`, host-tested by `host_test_event_state`): the newest `n` decode slots (the page sends its `DECODE_SLOTS_MAX`; at most `EVENT_STATE_SLOTS_CAP`, 4), every live queue entry, and the last slot state, TX HUD, USB status and radio state. Log lines, sweep progress and band activity are not state. **Why:** the ring cannot do it. The main board re-sends every live queue entry each second, so on a busy band the ring holds less than a slot, and a reload replayed it over the browser's own cache, which could be hours old. **Queue entries** leave on IDLE, or when not re-sent for 4 s (a lost IDLE, a main-board restart). After a sidekick restart the snapshot is empty until the main board next sends; the page shows that rather than its cache. **Memory:** about 19 KB of static RAM, room for four full slots (`RX_MAX_DECODES` each) and `AUTOSEQ_MAX_QUEUE` entries.
* **Ring entries are the Port A structs themselves** (`event_t`): a frame is parsed straight into one, so every field it carries reaches the browser. A field-by-field copy once dropped the TX HUD's `not_keyed`.
* **The sidekick answers for itself without the main board.** Every `GET /api/config` reply carries its own facts (`sk_*`: firmware version, the app it serves (`sk_app`, **Web root**), WiFi mode, network, IP, uptime, its link counters, its internal heap now, lowest since boot and largest free block: `sk_heap_free`, `sk_heap_min`, `sk_heap_largest`, and its TCP connections, worker queue and sender pool: **Tasks and cores**), built at reply time (`send_config_reply()` in `host_link.c`), including the `{"ok":false,...}` reply when the main board does not answer. **`host_linked`** among them says whether a main board is there at all: `1` while its HELLO, sent every 5 s, is under 16 s old (`HOST_LINK_HELLO_FRESH_MS`, the same test a firmware update's start uses). The app's **Main board not connected** state reads it ([webapp.md](webapp.md), **The radio bar**). The web app shows them only from a live reply, never from its browser cache.

## Tasks and cores

Nothing of ours is pinned to a core: FreeRTOS places our tasks, and ESP-IDF pins some of its own to CPU0 by configuration (`sidekick/sdkconfig`). As of 2026-09-25:

* **The action reply** (verb, OK, reason) is one slot under `s_lock`, the same mutex as the event ring and the state snapshot. `porta_rx` stores OK and the reason before the verb, and a CONFIG_GET retry resets its gather buffer under that lock, so a handler that sees its verb has this reply's OK and reason.
* **The main board's waits are a worker's.** `httpd` runs every handler in turn, and between them it accepts one new connection a pass, so anything slow there holds every client, new connections included. A request that waits on the main board (`wait_reply()`, `host_link.c`: up to 1 s for an action, 3 s for CONNECT, 5 s for a config read or a log read, with one config resend halfway) is therefore handed to `http_main_board` (`pairing_http_register_on_worker()`; IDF's `httpd_req_async_handler_begin()`): `httpd` goes back to its other sockets and leaves that one alone until the worker has answered it. Every route that sends to the main board is registered that way, because `wait_reply()` matches a reply to its request by one byte and holds one reply slot, which needs those requests one at a time; events and state read only what `porta_rx` holds and go to the senders (**A slow client holds one sender**, below), and the link test's counters stay on `httpd`. A request runs on `httpd` only when its worker was never started. When one cannot be handed over (no memory for the copy) it is answered `503` with `{"ok":false,"why":"sidekick busy"}`, not run on `httpd`, since that could overlap the worker's own handler: a second wait on the one reply slot. Each worker's queue is as deep as `httpd` has sockets, so it does not fill. **What is left:** a config read still waits up to 5 s for its own answer, and the app's log read waits behind it; nothing on the sidekick makes the main board answer sooner.
* **A slow client holds one sender, not the server.** A reply's time includes its TCP send, and a client slow to take it, as a phone in WiFi power save is, holds whichever task sends it for as long as it keeps taking a few bytes: on `httpd` that was every client. With one slow client (`tools/sidekick_load/slow_client.py`) beside an events read every 0.5 s, every read timed out for a minute (2026-11-18, `SK httpd held over 30 s`). So files, events and state go to a pool of three senders (`HTTP_SENDERS`, `http_worker.c`) reading one queue, not pinned to a core, and `httpd` only reads requests and hands them over. **Files take at most two senders at once** (`HTTP_FILE_SENDERS`): a third file waits its turn (`sk_files_wait_peak`), so a page loaded slowly, or several, always leaves one for the live feed. With three slow clients the events reads stayed under half a second, against reads stalled up to 10 s when files could take all three. Each sender builds an events or state reply in a 4 KB buffer of its own (`batch_own()`, `host_link.c`). A single worker for files, built and taken out on 2026-11-16, was judged under a load with no slow client in it, so it could not show this.
* **Every reply has a send deadline.** `httpd` sends again after every partial send, so the socket's own send timeout ends a reply only when nothing moves at all, and a client that trickles holds its sender indefinitely. Each connection gets a send of our own (`deadline_send()`, set as the server's `open_fn`) that cuts a reply 20 s after its first byte (`HTTP_SEND_DEADLINE_MS`) and closes the connection, logging `SK send cut at 20000 ms`; `sk_send_cuts` counts them. The page asks again.
* **The server's queue of work for itself holds 16.** `httpd` takes work from other tasks through its control socket's UDP mailbox: every request a worker or sender hands back, every connection to close, and the held check below. IDF sizes it by `CONFIG_LWIP_UDP_RECVMBOX_SIZE`, 6 by default. With four tasks handing requests back during a page load, 6 filled: work to close an idle connection was dropped (`httpd_queue_work: ctrl socket queue full`), and with every session in use the server then refused a new connection (`error accepting new connection`), 14 and 8 times in 24 minutes with six pages on the AP (2026-11-18). At 16 (`sdkconfig.defaults`) the same load logged neither in 58 minutes. A request handed back is never lost, since that path waits for a place; only a close or the held check can be.
* **A pushed app is unmapped only when no sender is reading it.** Files are sent straight from mapped flash, and a push is written and dropped by other tasks than the senders (**The bench push**), so a sender counts itself in and out around a send from the push, and `push_unmap()` waits for none (`app_serve.c`). The deadline bounds the wait.
* **What a connection may have unacknowledged is bounded by the heap.** lwIP keeps a reply's bytes until the client acknowledges them, a closed connection's included, so the worst case is every TCP slot holding a full send buffer. At IDF's 5,760 bytes that is 92 KB, more than the sidekick has free (about 87 KB): overnight on 2026-11-18 a WiFi stall took the free heap to 392 bytes, with all 16 slots in use (`SK heap low 660 free 16200 big 1664 tcp 16/12`), and events reads stalled up to 13.7 s. At 2,880 (`CONFIG_LWIP_TCP_SND_BUF_DEFAULT`, `sdkconfig.defaults`) it is 46 KB. The cost is half the bytes in flight to one client: a page reload's median rose from 343 to 472 ms on the bench's WiFi. The app's polls pile up no requests to fill those slots ([webapp.md](webapp.md), **The live polls**).
* **Each stall says which kind it was.** A request slower than 500 ms (`HOST_LINK_SLOW_MS`), from when `httpd` took it to its answer, writes `SK slow <method> <uri> <ms> ms <client>` into the event ring (`http_worker_note_slow()`; on the worker that time includes its wait in the queue), and a Port A wait that slow writes `SK wait 0x<verb> <ms> ms`, with ` no ACK` when the main board never answered. The main board logs its side on its console: `frame 0x<type> waited <ms> ms for the main loop` when a control frame sat in its 8-deep queue longer than 250 ms, and `control queue full: <n> frames dropped since boot` when one was dropped, which is a sidekick's `no ACK` (`porta_tick()`, `components/porta`). A WiFi loss writes `SK wifi lost: <reason> (<code>)` and its return `SK wifi back after <ms> ms`.
* **When `httpd` itself is held, the held check says by what.** `SK slow` times only a handler, so time `httpd` spends anywhere else (reading a request that has not all arrived, which waits up to `recv_wait_timeout`, 5 s; its own loop) went unseen: on 2026-11-16, events reads of 1.1 to 1.5 s with a clean network and no `SK slow` line. Once a second the main loop queues a no-op on `httpd` (`httpd_queue_work()`), which runs it at the top of its next pass; one that lands more than 500 ms late writes `SK httpd held <ms> ms: <n> req <ms> ms, top <method> <uri>`: the requests `httpd` ran itself since the last check, their time, and the longest. Their time well short of the hold means `httpd` was held outside any handler. `sk_httpd_held_peak_ms` in `/api/config` is the longest since boot. On 2026-11-16 it named an events reply to a phone on WiFi, `SK httpd held 1198 ms: 17 req 2111 ms, top GET /api/events`, beside `SK slow GET /api/events?since=2885 1148 ms`.
* **A heap low says what came with it.** Each time the lowest free internal heap since boot falls a further 4 KB below 48 KB, the main loop writes `SK heap low <min> free <n> big <largest> tcp <used>/<held> wq <n>` into the ring (`heap_low_check()`, `main.c`). **Why:** the lowest fell to 26 KB and then 6.4 KB on 2026-11-16, each time beside a network stall, and its cause is not known. **It varies widely from run to run:** the same image under the same scripted load bottomed out at 46,664 and at 23,344 bytes, so one run says nothing about a build; the line is what tells a real station's lows apart. A floor below which requests are not handed over was considered and not built: run on `httpd` they would race the workers, and answered busy a page could fail to load where it was only slow.
* **Not ours: a second's stall once a minute.** From a laptop on WiFi, pings to the sidekick slowed to 0.3 to 1 s at the same second past each minute, on wall time across three sidekick restarts, while pings to the router stayed under 300 ms (2026-11-16). The sidekick's timers count from its boot and the main board logs nothing then, so it is the access point or the sidekick's 2.4 GHz link, as with multicast (**The name `micro-ft8.local`**).
* **A connection that is never accepted logs nothing at the server**, so the network is counted instead (`net_health.c`). lwIP drops a new connection's SYN without an answer when a listening socket's queue of connections not yet accepted is full (`httpd`'s `backlog_conn`, 5), or when none of its 16 TCP slots (`CONFIG_LWIP_MAX_ACTIVE_TCP`) can be had, and the client sees only its connect time out, retrying at 1, 3 and 7 s. **A slot in TIME_WAIT or closing is not a full one:** out of slots, `tcp_alloc()` takes back the oldest TIME_WAIT, then LAST_ACK, CLOSING and (ESP's lwIP) FIN_WAIT slot. The sidekick sits at 16 of 16 in normal use, 13 to 15 of them in TIME_WAIT (2026-11-16, two app pages and an agent polling), so only the slots it cannot take back count: half open, established, CLOSE_WAIT and bound (`held`). The main loop counts each second; held slots at 16, or a listen queue at its limit, writes `SK tcp full held=<n>/16 syn= est= cw= bk=<n>/<of>` into the ring, once until it drains, and `/api/config` carries `sk_tcp_used`, `sk_tcp_held`, `sk_tcp_held_peak`, `sk_tcp_backlog_peak` `sk_worker_queue_peak`, so a stall can be checked against them afterwards with no console. `tools/sidekick_latency.py` times each connect apart from its reply for the same reason. **Why:** on 2026-11-16 one `GET /api/events` from a laptop timed out connecting after 5 s while the main board answered every log read in under 10 ms, and nothing then said whether the WiFi or the sidekick had lost the connect.
* **Not yet built: row [wgjx](../roadmap/ideas.md#wgjx)** — placing tasks on cores, and only where a measurement of each task's CPU share and core shows them contending.
