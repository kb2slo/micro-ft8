# Sidekick architecture

The AtomS3 Lite sidekick is the station's WiFi and web server: it serves the web app, guards the control API with the pairing token, and relays between the browser and the main board over Port A. Why it is shaped this way (no TLS, the phone reaches the internet): [system.md](system.md).

## Hardware

**M5Stack AtomS3 Lite**, chosen over the NanoC6 it replaced (2026-09-05) for its dual cores: WiFi, lwIP and an HTTP server run beside the Port A UART work, where the C6 has one 160 MHz core.

* **ESP32-S3FN8**: 8 MB embedded flash, **no PSRAM** (confirmed with `esptool.py flash_id`, 2026-09-04). Anything large is staged in flash, not RAM.
* **Grove** (Port A): `GND / 5V / G2 / G1`. **USB-C** is device mode only — flashing and a console, never a USB host ([system.md](system.md), **Why not**).
* **User button**: GPIO41, active low, used to disclose the pairing token.
* **Over USB it enumerates as Espressif's generic `303A:1001`** with no board string, like any ESP32-S3 on native USB. The MAC address is the only reliable way to tell one from another; a differing flash vendor is a production-batch artifact, not a model identifier.

Building, flashing, and backing up a unit's stock firmware: [`sidekick/README.md`](../../sidekick/README.md).

## Web root

**The sidekick serves the whole app, and the app is not in the firmware image.**

* **Served locally, not loaded from the internet.** An HTTPS page cannot reach `http://micro-ft8.local` (browsers block active mixed content, with no exception for private addresses), and an app fetched from the internet each session does not exist on a summit. Served from the sidekick, the app and the API are the same origin.
* **Not inside the firmware image**, because the app ships on its own cadence and firmware flash is the wrong vehicle for a weekly UI.
* **The `web` partition is the only HTTP origin**: LittleFS, 1.9 MB, above `ota_1` (`sidekick/partitions.csv`). What is on the filesystem is what the device serves.
* **The firmware carries only a bootstrap**, `sidekick/main/web/` (provisioning, `/update`, `pairing.js`, error pages), embedded by a CMake glob as a **hydrate seed**, not as a second live origin. On boot, if the filesystem is empty, unmountable, or its seed digest differs from the embed, the firmware copies the seed onto it; after that, HTTP reads the filesystem only. An installed bundle may replace any file, seed pages included.
* **Recovery** from present-but-broken files is a forced re-hydrate: token-guarded `POST /api/web/rehydrate` (`web_fs.c`), which restores the seed pages. USB-C reflash is the floor.
* **Consequence, accepted:** a sidekick that has never had internet has only the bootstrap. It can join WiFi and install a bundle, nothing more. System constraint 2 makes that acceptable. First run is therefore spelled out in the pages themselves: `provision.html` swaps "Operate in AP mode" for the install steps while `app.html` is absent (`web_fs_exists`), `get_static` answers a missing `/app.html` with `web/setup.html` (status 404) instead of a bare "Not found", and `update.html` explains an unreachable host. **Factory reset** (`POST /factory-reset`, pairing-guarded, both modes) erases the `sidekick` NVS namespace (WiFi credentials, AP-mode flag, pairing token, bundle host) and formats the web filesystem, then restarts into exactly this first-run state. It resets the main board first, with the `FACTORY_RESET` Port A action (v7): the P4 reseeds its Station settings to defaults in place (no restart, since a P4 reset can leave the QMX unenumerated, row [qdcm](../roadmap/declined.md#qdcm)), cancels TX and clears the queue, the CQ with it, and with `?logs=1` also deletes the daily QSO logs. The sidekick wipes itself only if the board ACKed; no link, a transmission on the air or a storage fault answers `{"ok":false,"why":"main board: …"}` and changes nothing, so a sidekick with no main board attached cannot be reset from the app (`idf.py erase-flash` does it). `/update` is served in both modes (open, like the other pages; its writes go through the token-guarded `/api/bundle/*`), so a phone joined to the sidekick's own AP can install the app over its cellular data with no home WiFi: the phone fetches the bundle over HTTPS and uploads it to `192.168.4.1`. `update.html` opened as a plain static file has no `{{bundle_host}}` and says to use `/update`. Whether a phone on cellular data can install while joined to the sidekick's own AP is untested.
* **Budget:** `web_fs.c` refuses a file over 512 KB, so large assets (the map's basemap files) ship as separate files, never inlined into `app.html`. The partition is sized for the app plus its bundled data; outgrowing it means a new partition table, which costs a USB reflash of every device.

## Installing the app bundle

The phone relays the bundle: `/update` fetches it from the release host over HTTPS (that fetch is what authenticates it), then writes it to the sidekick in three token-guarded steps, so a truncated upload cannot promote and an incompatible bundle is refused before any bytes land (`web_bundle.c`):

1. `POST /api/bundle/begin` — body is the manifest. Refused if its `api_min` exceeds the device's `WEB_API_VERSION`. Wipes the staging area.
2. `PUT /api/bundle/file?path=<relpath>` — one per asset. `Content-Length` must equal the manifest's size, and the body's SHA-256 must equal its digest.
3. `POST /api/bundle/commit` — every asset must be staged; re-hashes from disk, then renames each onto the live tree. A failed promote leaves staging for a retry; a forced re-hydrate recovers the seed pages.

**The manifest** (`manifest.json` in the built bundle, written from the build's output by `webapp/tools/gen_manifest.py` and never committed ([webapp.md](webapp.md), **Build**), parsed by `web_manifest.c`, host-tested by `host_test_web_manifest`) is constrained JSON: `api_min` and an `assets` list of `path`/`sha256`/`size`; no unknown fields, lowercase hex digests, and relative paths only (no leading `/`, no `..`, no dotfiles). The digests catch a corrupted upload over flaky WiFi, not an adversary. **Version pairing:** `api_min` stops a newer app installing onto firmware whose API it outranks, saying so rather than failing later.

### What the release host must provide

The design depends on two properties of the host, not on which host it is:

1. **HTTPS with a publicly trusted certificate** — the only thing authenticating the bundle.
2. **An `Access-Control-Allow-Origin` that lets the plain-HTTP page read the response.** This is a capability, not a security control: the browser is the courier, and it must be able to read the bytes it re-POSTs.

Today's host is Cloudflare Workers Static Assets (`webapp/wrangler.jsonc`) at `https://micro-ft8.kalikstein.com`; the app lives under `/app/`. Static Assets sends no CORS header by default; `webapp/_headers` adds it to every static file, the `/app/app.html` → `/app/app` redirect included ([webapp.md](webapp.md), **Serving the site**). Without it the header is missing, which once broke `/update` with a generic fetch failure. **Measure any new host before adopting it** (the `curl` in [system.md](system.md), **Third-party services**); GitHub Releases, for one, sends no CORS header and cannot carry the bundle.

Rules that follow:

* **The bundle fetch stays a simple request**: `GET`, no custom headers, so no CORS preflight. Versions belong in the manifest or the URL, never a header.
* **Manifest paths are relative** to the manifest, so the host can move.
* **The host's base URL lives in NVS**, with a build-time default (`https://micro-ft8.kalikstein.com/app`), set with a token-guarded write (`bundle_host.c`, `/api/bundle-host`): a host move is a config change, not a reflash, and a settable host is the most attractive thing on the device for a LAN attacker to repoint.

## Firmware updates

The sidekick downloads firmware images itself, from the release host over plain HTTP, and refuses any image whose SHA-256 differs from the one the web app read over HTTPS and handed it behind the pairing token (the trust argument: [system.md](system.md), **The inversion**). Unlike the app bundle, the image never passes through the browser, and the update goes on with the page closed. It has no PSRAM, so an image is staged in flash, in its spare OTA slot: its own next image, or a main board's, which it then sends down Port A (**A main board's image**, below; the main board's side is [main_board.md](main_board.md), **Firmware updates**). One image is staged at a time, so two boards are updated one after the other.

Every decision is in `fw_policy.c`, host-tested (`host_test_fw_policy`), the transfer to a main board included, which the test runs against the main board's own receiver over a link that loses frames. `fw_update.c` is the download, the flash writes and the restart.

* **`POST /api/fw/start`** (token required). The body is one `key=value` per line: `board` (`sidekick` or `main`), `url`, `size`, `sha256` (64 lowercase hex) and `version`, each once, as the manifest's `ota` entry gives them ([RELEASE_PROCESS.md](../RELEASE_PROCESS.md), **Public Cloudflare mirror**). **A body may hold two images,** separated by a line reading `next`, which the sidekick carries out in order with no page needed in between: each board once, and its own image last, since installing it restarts the sidekick (`fw_plan_parse()`). A malformed field is a 400 naming it, and a plan that breaks those rules a 400 `plan`. A request that cannot start is a 409 with `{"ok":false,"why":...}`: `busy` (one is running), `confirming` (the running image is still on trial, and the spare slot holds the image to go back to), `offline` (not joined to a WiFi network: on its own access point it has no internet), `size` (larger than the slot), or `no_host` (a main board's image and no main board answering). Otherwise it answers at once and a task does the rest.
* **The URL is plain HTTP only,** to any host: the hash is what is trusted, and whoever holds the pairing token could already do anything. `fw_url_ok()` refuses anything else at the API, and the client is ESP-IDF's `esp_http_client`, built with `CONFIG_ESP_HTTP_CLIENT_ENABLE_HTTPS` off so it cannot open an HTTPS URL either. The library links its TLS code all the same, 91 KB of the image that nothing calls (1,102,368 bytes against 1,011,232 with a client of our own over a socket, measured 2026-11-10): a proven client was judged worth more than the flash, and linked code costs no heap. The rule is about what the sidekick calls, not what is in its image (**Why the sidekick has no TLS**).
* **Download, then four checks, then restart.** The image is written to the spare slot as it arrives (`esp_ota_begin()` with sequential erase). It is refused, and the running image left as it was, unless: the byte count is `size`; the SHA-256 is `sha256`; ESP-IDF accepts it as an app image for this chip (`esp_ota_end()`); and the project name and version built into it are this project's and the requested `version`. Only then is it made the boot image, and the sidekick restarts 2.5 s later.
* **`GET /api/fw/status`** (open) is the progress, held on the sidekick, so any phone sees the same: `state` (`idle`, `downloading`, `verifying`, `transferring`, `restarting`, `done`, `failed`), `plan` (each image's `board`, `version` and `size`, in order) and `step` (which is in hand); that image's `board`, `version`, `got` and `size` in bytes (downloaded, or sent to the main board); `why`, `at` (the state it failed in) and `detail` for a failure; `running` (the sidekick's version now), `host` and `host_linked` (the main board's version, from its HELLO, and whether one came in the last 16 s) and `online`. A failure's `why` is `connect` (no DNS answer or no route: most often a network with no internet), `download`, `http` (the status in `detail`), `size`, `hash`, `image`, `version`, `flash` or `cancelled`, or, from a main board's update, `link`, `no_slot`, `host_restarted`, `host_flash`, `host`, `rolled_back` or `no_host`. **`POST /api/fw/cancel`** (token required) stops an update until the image is fully handed over.
* **A new image runs on trial, and must earn its place.** The bootloader goes back to the image before it at the next restart unless the new one is marked valid (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`). It is marked valid once it has sent three Port A beacons and is reachable: joined to the WiFi network again, or, on its own access point, having answered a `GET /api/fw/status`. Together those show it can take the next update. Joining is enough, with no client heard from, because the phone that started the update may be locked by then. One that is not reachable within 300 s restarts itself, which is the roll back (`fw_confirm_decide()`). So an image that boots but cannot get on the network undoes itself, with no cable, and one that crashes at boot is rolled back by the bootloader at once. An image written over USB is never on trial.
* **What came of it survives the restart.** Before restarting, the sidekick stores the target version and the one it came from in NVS (`fw_last`); after, `/api/fw/status` carries `last`: `board`, `version`, `from` and `result` (`confirming`, `ok`, or `rolled_back` when what is running is not the target).
* **From a workstation,** `python3 webapp/tools/install_firmware.py` installs a local build the same way: it serves `sidekick/build/sidekick.bin` on the LAN, posts the request with the cached pairing token and follows the status to the result. It is how a build that is not on `main` is installed over the air, a deliberately broken one included.
* **An update stops transmission first, and nothing checks for a radio.** On an accepted start the sidekick tells the main board an update is running (`host_link_update_mode(true)`, the `UPDATE_MODE` action) before it fetches a byte, says so again every 20 s while it runs (`fw_hold_refresh_due()`), and says it is over when it fails or is cancelled; the main board holds transmit off in between ([main_board.md](main_board.md), **Firmware updates**). A sidekick that has just started says "over" once, at the main board's first HELLO, which ends the hold of its own update and of one it lost power in. The message is sent and not waited on: a lost "on" is said again, and a lost "off" is covered by the main board's own 90 s timeout. This holds for every update, the sidekick's own included, though only a main board's restarts the board that keys the radio: an operator sees one update, and it behaves one way (maintainer, 2026-11-12). The operator is still asked to switch the radio off, by the app's review.
* **`POST /api/fw/hold`** (token required), body `on` or `off`: the page takes the hold before its own step of an update, the app's install, and gives it back when no firmware follows ([webapp.md](webapp.md), **Settings › Software update**). "Off" does nothing while an update is running, whose hold ends with it (`fw_page_hold_applies()`). A page that goes away mid-step strands nothing: the main board ends a hold nobody refreshes.

### A main board's image

* **Staged as plain bytes.** `esp_ota_end()` refuses an image built for another chip, so a main board's image is written to the spare slot with the partition calls, each sector erased as the write reaches it. The size and hash are checked as for the sidekick's own, and the version is read from the image's app description (`fw_image_version()`). The main board checks the rest when it has the image.
* **Sent a chunk and its answer at a time** (`fw_transfer_run()`): `FW_BEGIN` with the size, the SHA-256 and the version; `FW_CHUNK`s of 240 bytes, each answered with the next offset wanted; `FW_END`, on which the main board checks the image, makes it the boot image and restarts (`porta_proto.h`, **Firmware update**). A message with no answer in 3 s (10 s for `FW_BEGIN`, 30 s for `FW_END`, which reads the whole image back) is sent again, five times for a chunk, and then the update fails with `link`. **Before a message is sent again the sidekick sends filler,** 259 zero bytes (`PORTA_PROTO_RESYNC_LEN`, `host_link_resync()`), which no decoder can take for a frame's start and which is longer than any frame one can be in the middle of. Without it a retry can be lost the way the first try was: on the bench (2026-11-10) the sidekick's HELLO lost bytes on its way to a main board that was writing flash, the decoder took the next chunk for the rest of that frame, then found a sync byte in the image's own bytes, and five tries in a row went unanswered ("stopped answering during the transfer", 308,400 bytes in). `host_test_fw_policy` reproduces that with the real decoder and an image that is the worst case, and shows the filler getting the first retry through.
* **An interrupted transfer goes on from where it stopped.** Every answer says where the main board is, so a lost frame costs one resend. A `FW_BEGIN` for the image the main board already holds part of is answered with the bytes it has: after a failure, starting the same update again downloads the image again and sends only the rest. A main board that restarted has forgotten the transfer and it starts from 0. Seen on the bench (2026-11-10): the sidekick lost power 199,680 bytes in, and the next run sent the rest and the image booted.
* **While a transfer runs, replies are read as they arrive.** `uart_read_bytes()` waits out its timeout unless its whole buffer fills, which would add 50 ms to each chunk's 9-byte answer, so the receive task waits for one byte and takes what came with it (`host_link_fw_active()`).
* **Done means the new version reported in and was kept.** After `FW_END` the state is `restarting` until the main board's HELLO carries the requested version and the main board says it has kept the image: the sidekick asks with an `FW_END` abort, which with nothing to abort is answered OK, or `TRIAL` while the image is still on trial ([main_board.md](main_board.md), **Firmware updates**). Normally that is within 5 s of the restart. The version alone is not enough: on the bench an image that never counted the sidekick as heard said HELLO for 120 s and then went back (2026-11-10). A HELLO with another version, later than 4 s after `FW_END` (its old image is still running for the first moments), is `rolled_back`; neither in 240 s is `no_host` (`fw_host_result()`).
* **Transfer time: 74.4 s for an 872,384-byte image** (2026-11-10, P4 and sidekick at `7fdc14c`), about 11.7 KB/s or 20 ms a chunk, with no chunk refused or resent and no CRC errors; a whole update of the main board took 98 s. Stop-and-wait at `PORTA_BAUD`; the main board answers from its 10 ms loop. The sidekick logs each run to its console and the app's log (`SK firmware transfer: <sent> of <size> bytes in <s>`; less than the image is sent when the main board already held part of it).
* **From a workstation:** `python3 webapp/tools/install_firmware.py --board main` sends `poe_p4/build/poe_p4.bin` the same way, and `--both` posts both images in one request, as the app does.

## Why the sidekick has no TLS

"TLS on the sidekick" is two questions with different answers.

**As a client — the sidekick calling out over HTTPS: not needed, and not free.**

* **Nothing needs it.** The phone reaches every internet service ([system.md](system.md), **The inversion**). The one thing the sidekick will fetch, firmware, is checked against a SHA-256 the browser read over HTTPS, which proves integrity as well as TLS would; TLS would add only confidentiality, for a public file.
* **Its costs, weighed honestly.** Some are weaker than they first looked:
  * **Flash:** ~116 KB, measured on this target. Affordable: the image is under 1 MB in a 3 MB slot.
  * **CA bundle:** it must track root-certificate rotation. Weak, since the device updates itself; only a device offline for years falls behind.
  * **Clock:** checking certificate dates needs the right time. Weak: ESP-IDF's mbedTLS skips the date check by default.
  * **RAM:** a handshake needs tens of KB of heap on a board with no PSRAM that is already running WiFi and the HTTP server. **Unmeasured**, and the one cost that could decide it outright.
* **The cost that holds is architectural.** Once the device can speak HTTPS, the easy path for every new online feature becomes "have the sidekick call it". That erodes the inversion, and those features would then fail in AP mode, where the sidekick has no uplink, while the phone often still has cellular.

**As a server — the browser reaching the sidekick over HTTPS: it would fix our one real security limit, but it cannot be done properly.**

* **What it would fix.** The pairing token and all control traffic cross the LAN in clear ([system.md](system.md), **Who may key the transmitter**). HTTPS would close that, and would also make the app a secure context again: geolocation, a service worker, an offline cache ([webapp.md](webapp.md), **A non-secure origin**).
* **Why it can't be done properly.** Browsers trust a certificate only for a name a public CA can verify, and `micro-ft8.local` resolves on one LAN.
  * A **self-signed** certificate means a full-page warning to click through on every new phone and browser.
  * A **private CA** means installing a root certificate on every phone.
  * The scheme that works — a public domain name that resolves to the device's LAN address, with a CA-issued certificate — puts the private key on the device and needs renewal every few months. Renewal needs internet and a correct clock, exactly what a summit in AP mode lacks.
* **So the limit is accepted and scoped**: a nuisance control, on WPA2/WPA3 networks.

**Reopen TLS as a client** if the release host stops serving plain HTTP, or a feature needs the sidekick itself to reach an HTTPS-only service with no phone present. Measure the handshake's heap first. **Reopen TLS as a server** if a way appears to give a LAN device a browser-trusted certificate without renewal or a clock, or if the station will be operated on networks its owner does not trust.

## The access point

With no WiFi credentials, after a sustained loss of its network, or when the operator picks AP mode, the sidekick runs its own network at `192.168.4.1`, answering to `micro-ft8.local` over mDNS (`wifi_prov.c`, `start_ap()`). Two clients at most.

* **Name and password are the operator's to set** (Settings > Network, `POST /ap-config`, token required). The default is the open SSID `micro-ft8.local`; a password makes it WPA2-PSK (8 to 63 characters). Both live in NVS (`ap_ssid`, `ap_pass`) and no route returns the password. Saving in AP mode answers, then restarts the AP; in station mode it only saves. **Why:** an open AP is what a phone with no internet offers to join, and on 2026-10-09 at a park that drew people to it. **Why not a hidden SSID:** a phone must then be told the name by hand, and with a password it adds nothing. **Recovery:** holding the sidekick button for about ten seconds erases both and restarts (`button_check_hold()` in `main.c`), so a forgotten password needs no WiFi to undo. The seconds held ride on every `GET /api/events` reply as `hold`, and the page shows a card from the second second (`updateResetHold()` in `app.html`); the total is `WIFI_PROV_AP_RESET_HOLD_SECS`, sent as `hold_of`; the restart waits 1.5 s after the last second so the card can say it is resetting; a factory reset does the same. The press at the start of a hold also opens the pairing-token window, as any press does. **Not yet verified on a phone:** TEST_PLAN, the AP name and password row.

* **The lease is address-only: no router, no DNS server** (`ap_lease_local_only()`). The sidekick has no uplink, so an offered router is a default route to nowhere that the phone may try before cellular: on the 2026-10-09 activation, with a lease offering both, the phone had internet only some of the time, while with WiFi off it had it throughout ([system.md](system.md), **Connectivity**). Without a route out, the AP is a local link and internet can only go over cellular. Field-checked 2026-10-10 (sidekick `2e3e323-dirty`, iPhone): the lease showed no router, and over 30 minutes on the AP every internet use worked. `CONFIG_LWIP_DHCPS_ADD_DNS=n` (`sdkconfig.defaults`) is part of it: with it on, IDF offers its own address as DNS whatever the code asks, so `wifi_prov.c` refuses to build with it on.
* **Why not a captive portal:** it cannot coexist with an address-only lease. iOS raises the portal sheet only when its probe goes out over the WiFi, which needs an offered router and a DNS server answering every name with `192.168.4.1`. The sheet reaches "Done" only when that probe gets Apple's success page, and from then on iOS treats the WiFi as its internet. Tried with DHCP option 114, 2026-09-20/21: the sheet never reliably reached "Done", iOS kept re-intercepting page loads in Safari, and the captive state fought cellular. Option 114's standard API (RFC 8908) needs an HTTPS URL, which the sidekick cannot serve (**Why the sidekick has no TLS**). Instead, the SSID names the address to open, and the setup sheet's QR codes open it.

## The name `micro-ft8.local`

* **The sidekick answers `micro-ft8.local` over mDNS in both modes** (`mdns_bring_up()`, `wifi_prov.c`; `espressif/mdns` 1.14.1), and advertises `_http._tcp`. It has no IPv6 address, so AAAA questions go unanswered and a phone uses the A record.
* **On a home network, a failed lookup is usually WiFi multicast loss, not the responder.** Measured 2026-11-01 in station mode, from a laptop on the same WiFi: 17% of mDNS questions sent to the multicast group went unanswered, while the same question sent unicast to the sidekick's address was answered 59 times in 60, and ping lost under 3%. An access point sends multicast with no acknowledgement or retry, so a phone's lookup can fail while the sidekick is up and serving. mDNS 1.8.2 and 1.14.1 missed at similar rates with the WiFi dropped every two minutes (13% and 18%), so the library version does not change it. The lever is the access point's multicast handling (a multicast-to-unicast option, where it has one), not our firmware.

## First install

USB-C is the only wire flash path: the ROM bootloader listens only on UART0's default pins, never on Grove ([`sidekick/README.md`](../../sidekick/README.md)). A new unit is flashed with the merged `0x0` image (`tools/merge_sidekick_bin.sh`, or the downloads page); after that it updates over WiFi (**Firmware updates**). Until the app bundle is installed it serves only the setup pages.

## Port A: the link to the main board

Everything the app needs crosses Port A: decodes at slot cadence, TX control, config reads and writes, and the log. The message set is defined in `components/porta_proto/include/porta_proto.h`, which is the source of truth (host-tested by `host_test_porta_proto`); the sidekick side is `host_link.c`, the main-board side `components/porta`.

* **Framed messages over a byte pipe**, with framing that assumes no stream, so the transport could change without touching the app or the API.
* **Board-agnostic**: specified against the application, never against board hardware, so a second main board could be added without a per-board build or `#if` in the sidekick.
* **Versioned** (`PORTA_PROTO_VERSION`, carried in HELLO), for the same reason the bundle manifest pairs app and API. A mismatch is logged, not refused, so both ends must be flashed together when it changes. **Both ends send HELLO** every 5 s, with the protocol version and the build's version; the sidekick serves the main board's in `/api/config` as `host_fw_version` and `host_proto`, beside its own `sk_fw_version` and `sk_proto`. **Frozen from v15 (2026-11-10):** the frame, HELLO, ACK and NAK, the `UPDATE_MODE` action and the `FW_BEGIN`, `FW_CHUNK` and `FW_END` messages never change layout, so any two builds from v15 on can carry a firmware update between them, whatever else differs; `host_test_porta_proto` pins their bytes. v16 and v17 (2026-11-10) kept those bytes: `UPDATE_MODE` is now only ACKed, for the sidekicks of v15 and v16 that still ask it before their own update, and a v17 sidekick does not send it. That an update from `62e1c70` (v15) to `1e55290` (v16) carried both boards across is the rule working. v2 (2026-09-28) added each DECODE's slot index and length and the dial frequency at the middle of its signal, which the main board takes from `components/dial_history` (the frequency the radio reports is noted there, `radio_control_dial_tick()`: [radio.md](radio.md), **The dial a decode was heard on**); the sidekick relays them in `/api/events` as `si`, `sl` and `fq`. v4 (2026-09-30) added the SWR sweep ([radio.md](radio.md), **The SWR sweep on the main board**): the `SWEEP_START` action, which `POST /api/swr/start` (token required, body `lo-hi-step,lo-hi-step` in kHz, at most 12 ranges) sends, and the `SWEEP` event, served in `/api/events` as a row with `"d":6` and `k` (0 point, 1 band skipped, 2 done, 3 aborted), `r` (the range), `hz`, `swr` (hundredths, -1 none) and `why` (0 cancelled, 1 CAT lost, 2 stalled). Stopping is the existing `/api/tx/cancel`. The sidekick only relays: the host validates the ranges and its own state and answers with `{"ok":false,"why":...}`. v10 (2026-10-24) added the `RADIO_STATE` event ([webapp.md](webapp.md), **The radio bar**), served as a row with `"d":7`, `hz`, `tx`, `md` (the MD digit) and `sp`. v11 (2026-10-27) added the `ACTIVITY` event ([decode.md](decode.md), **Band activity**), about one a second while receiving; v12 gave it a frequency mask per block. It is served as a row with `"d":8`, `si`, `bm`, `b`, `lo`, `hi`, `v` and `m`. The event ring holds 128 rows, so a page that polls about once a second keeps up with a sweep (about 1.3 points a second) but one that sleeps through it does not; the page marks what it never received as missing ([webapp.md](webapp.md), **The SWR sweep**).
* **Port A rests at 2500000** (`PORTA_BAUD`). Both main boards held 14 MB both ways at that rate with no drops or CRC errors (2026-10-01), and decodes reached the app with the link opened there. 4000000 did not. With the receiver on during a link test at 2500000, no extra hiss was audible. The frame stays 255. A firmware update waits on one answer per 240-byte chunk (**A main board's image**); a window on `FW_CHUNK` would be the fix if its measured time is too long ([ota-updates.md](../roadmap/ota-updates.md), **Later**).
* **What held that rate.** The UART FIFO is 128 bytes. Both boards' UART interrupts are in IRAM so a flash access cannot stall them (`CONFIG_UART_ISR_IN_IRAM`; the main board's since 2026-11-10, when its own flash writes during a firmware update were seen to cost frames), and its receive buffer is 8192 bytes, large enough for one fill of the peer's 4096-byte transmit ring. The P4 receive buffer is 4096, with a separate reader. The decoder does not rescan after a lost byte.
* **The stress test stays in the page, hidden.** `#linkTest` in `webapp/app/app.html` has the `hidden` attribute. Remove it to show Bytes, Baud, Run, and Stop. `POST /api/link-test` with `rx`, `rx <bytes> <baud>`, or `stop` is unchanged (token required); `GET /api/link-test` is the live counters. Bare `rx` is 14 MB at `PORTA_BAUD`. The sidekick is the coordinator. A rate other than the resting rate is one switch, then both ends return to `PORTA_BAUD`. The run does not key the radio. Protocol version 6. The codec is `host_mock`-tested.

* **The sidekick's build identity** is its exact git SHA plus a dirty flag, from `tools/git_version.cmake`. CI pins `MICROFT8_GIT_SHA`, because a pull request builds a synthesized merge commit that is not the SHA anyone can check out.
* **Asymmetric traffic**: commands are rare and want low latency; decodes arrive every 15 s and tolerate hundreds of milliseconds. A full slot of decodes is about 3 KB, so sustained load is a couple of hundred bytes per second.
* **An events or state reply is sent a few KB at a time** (`batch_add()`, `host_link.c`): its rows are written into one 4 KB buffer, sent as a chunk when full. One chunk per row was six small socket writes an event, each held back by TCP until the last was acknowledged, so a full ring took 1 to 2.5 s to send and every other request waited behind it, and a reader that fell behind asked for more next time. Batched, a whole-ring reply (19 KB) took 99 ms median and 226 ms at worst, against 265 ms and 2.6 s (2026-11-08, sidekick on USB power, `tools/sidekick_latency.py`).
* **The browser polls** `GET /api/events?since=<seq>`; the sidekick keeps a ring of the last 128 events (`RING_LEN`, `host_link.c`) so a client can catch up after a short gap. That is about 55 s on a quiet band and 26 s on a busy one with FT8 and FT4, where decodes, state and activity come to about 5 events a second; at 64 a stalled server lost events in under a minute (2026-11-07, `sk_ring_gaps`). An event is 180 bytes and the S3FN8 has no PSRAM, so the ring is internal RAM; larger waits for `sk_heap_min` to show room. A client that falls behind skips to the oldest event the ring holds; repairing that is row [p8yv](../ROADMAP.md#p8yv)'s. Config is `GET /api/config` (open) and `PUT /api/config` (token-guarded).
* **A page that has just loaded reads `GET /api/state?slots=<n>` first** (open): the station as it is now, in `/api/events`' shape, and then polls from its `seq`. The sidekick builds it from the same events, in the same critical section as the ring (`event_state.c`, host-tested by `host_test_event_state`): the newest `n` decode slots (the page sends its `DECODE_SLOTS_MAX`; at most `EVENT_STATE_SLOTS_CAP`, 4), every live queue entry, and the last slot state, TX HUD, USB status and radio state. Log lines, sweep progress and band activity are not state. **Why:** the ring cannot do it. The main board re-sends every live queue entry each second, so on a busy band the ring holds less than a slot, and a reload replayed it over the browser's own cache, which could be hours old. **Queue entries** leave on IDLE, or when not re-sent for 4 s (a lost IDLE, a main-board restart). After a sidekick restart the snapshot is empty until the main board next sends; the page shows that rather than its cache. **Memory:** about 19 KB of static RAM, room for four full slots (`RX_MAX_DECODES` each) and `AUTOSEQ_MAX_QUEUE` entries.
* **Ring entries are the Port A structs themselves** (`event_t`): a frame is parsed straight into one, so every field it carries reaches the browser. A field-by-field copy once dropped the TX HUD's `not_keyed`.
* **The sidekick answers for itself without the main board.** Every `GET /api/config` reply carries its own facts (`sk_*`: firmware version, WiFi mode, network, IP, uptime, its link counters, and its internal heap now, lowest since boot and largest free block: `sk_heap_free`, `sk_heap_min`, `sk_heap_largest`), built at reply time (`send_config_reply()` in `host_link.c`), including the `{"ok":false,...}` reply when the main board does not answer. **`host_linked`** among them says whether a main board is there at all: `1` while its HELLO, sent every 5 s, is under 16 s old (`HOST_LINK_HELLO_FRESH_MS`, the same test a firmware update's start uses). The app's **Main board not connected** state reads it ([webapp.md](webapp.md), **The radio bar**). The web app shows them only from a live reply, never from its browser cache.

## Tasks and cores

Nothing of ours is pinned to a core: FreeRTOS places our tasks, and ESP-IDF pins some of its own to CPU0 by configuration (`sidekick/sdkconfig`). As of 2026-09-25:

| Task | Created by | Priority | Core | Stack | Job |
|---|---|---|---|---|---|
| main loop | `app_main` (`main.c`) | 1 | CPU0 | 3.5 KB | Once a second: Port A HELLO, marking a new image valid, the pairing-button disclosure; every 5 s an `alive` line on the USB-C console with the link's health (`host_link_health()`: `heap` free, `min` since boot, `big` largest block, the ring's `seq` and `gaps`, Port A's `rx_ok` and `crc`), out of band so it still reports while the web server is stalled |
| `porta_rx` | `host_link.c` | 5 | any | 6 KB | Reads Port A, parses frames, fills the event ring, the state snapshot and the reply state, and pumps the link test |
| `httpd` | `wifi_prov.c` (`httpd_start`) | 5 | any | 8 KB | Every HTTP handler; control requests wait on `porta_rx` for the main board's reply |
| `scan_fresh` | `wifi_prov.c` | 3 | any | 3 KB | AP mode only: keeps the WiFi scan list fresh for provisioning |
| WiFi driver, mDNS, `esp_timer` | ESP-IDF | IDF defaults (mDNS 1) | CPU0 | — | |
| lwIP `tcpip` | ESP-IDF | 18 | any | — | |

* **The action reply** (verb, OK, reason) is one slot under `s_lock`, the same mutex as the event ring and the state snapshot. `porta_rx` stores OK and the reason before the verb, and a CONFIG_GET retry resets its gather buffer under that lock, so a handler that sees its verb has this reply's OK and reason.
* **One request at a time.** `httpd` runs every handler in turn, and a control request waits on `porta_rx` for the main board (`wait_reply()`, `host_link.c`): up to 1 s for an action, 3 s for CONNECT, 5 s for a config read or a log read, with one config resend halfway. So while the main board is slow to answer, every request waits behind the one in hand, `/api/events` and the page included; the app reports it as "No contact with the station". A request slower than 500 ms (`HOST_LINK_SLOW_MS`) writes `SK slow <method> <uri> <ms> ms` into the event ring (`dispatch()`, `pairing_http.c`), and a Port A wait that slow writes `SK wait 0x<verb> <ms> ms`, with ` no ACK` when the main board never answered, so `/api/events` and the app's log show each stall. Answering config without waiting is **not yet built: row [dlu3](../ROADMAP.md#dlu3)**.
