# Main board

The main board decodes, transmits, runs autoseq, keeps the log, and hosts the radio over USB. The **P4** is the only one: the daily, headless station. (The Cardputer ADV was dropped 2026-10-02; `git log --diff-filter=D -- main/main.cpp` finds its last tree.) How it fits with the sidekick and the phone: [system.md](system.md). Radio control: [radio.md](radio.md).

Both boards run the same decode, autoseq, TX and Port A code from shared components; how the source is shared between them is a rule in [STYLE.md](../STYLE.md) (**Two boards, one source**).

## P4 (M5Stack Unit PoE-P4, U213)

The daily station. Headless is the only mode: the module has no display, touch or keyboard.

* **ESP32-P4, revision v1.3.** ESP-IDF treats pre-v3 P4 silicon as a separate hardware branch and defaults to v3+, whose bootloader refuses to boot on this board; `poe_p4/sdkconfig.defaults` selects `CONFIG_ESP32P4_SELECTS_REV_LESS_V3`. Newer P4 improvements (400 MHz, better PIE) do not apply to it.
* **16 MB flash. 32 MB PSRAM** (`CONFIG_SPIRAM`, caps-only so `malloc` stays internal). The waterfall, the decode working sets and the capture path (ingest ring, FFT buffers) live there as `EXT_RAM_BSS` ([memory.md](memory.md)); DMA buffers stay in internal RAM.
* **Internal RAM** holds the statics, the heap and some code, and the static part is budgeted at build time: [memory.md](memory.md).
* **No WiFi and no BLE.** The board pairs the P4 with an Ethernet PHY and 802.3at PoE. Ethernet is used only when the radio is an HL2 (**Ethernet**, below); PoE is not used. The phone reaches the station only through the sidekick ([system.md](system.md)).
* **No RTC chip, battery gauge or GPS.** `external_rtc_stub.cpp` and `board_power_stub.cpp` report them absent. The clock is unset at every boot until the web app sets it from the phone's clock over Port A ([time.md](time.md)).
* **Grove** `G53`/`G54` to the sidekick. A `porta_rx` task blocks in the UART read and decodes the byte stream there (`components/porta/porta.cpp`). Link-test bulk frames are checked in that task. Every other frame is queued for the main loop, which still owns autoseq and the radio. The loop's old 128-byte read every 10 ms was about 12.8 kB/s: clean at 115200, and CRC errors plus sequence drops at 230400 (measured on the P4, 2026-10-01). The task is not pinned.
* **Tasks.** The main loop (`app_main`, core 0, a pass every 10 ms) owns autoseq, the slot cycle and the armed TX, the radio, the decode ids a Port A reply names, the dial history, and the recently-worked and heard-grid tables. None of them is locked, so no other task may call into them.
  * **Capture** runs in `decode_audio`, pinned to core 1 at priority 4 (`poe_p4/main/main.cpp`): `ft8_audio_pipeline_run()` drains the ingest ring into each channel's waterfall and, at the decode trigger, queues the slot for decode.
  * **Decode** runs in `ft8_decode`, pinned to core 1 at priority 3, below capture, created by the first `ft8_audio_pipeline_run()` and kept (`components/ft8_audio_pipeline`; [decode.md](decode.md), **Channels**). It decodes and steps the clock, then hands each slot's decodes to the main loop: a one-slot hand-off under a mutex, as Port A's frames are, which `decode_pipeline_apply()` (`components/decode_pipeline`) takes on the main loop's next pass. That call does the rest: the two tables, the sort, `autoseq_on_decodes()`, arming, the decode ids and the DECODE events. The TX trigger waits until the main loop has applied the previous slot, not just until it is decoded ([autoseq.md](autoseq.md), **The slot cycle**).
  * **The decode helper** runs in `decode_helper`, a pthread pinned to core 0 at priority 1, the main loop's, so it takes only the time the main loop, USB, ingest and Port A leave (`decode_helper_start()`, `components/decode_pipeline/decode_workers.c`). It decodes the candidate after the one `ft8_decode` is decoding, and touches nothing else ([decode.md](decode.md), **Channels**).
  * **Ingest** runs in `audio_ingest`, created by `ft8_audio_pipeline_run()`, pinned to core 0 at priority 5 (above `decode_audio`'s 4, level with `usb_lib` and `uac_lib`, which are also on core 0). It calls the radio's read, which includes the receive front end ([decode.md](decode.md), **I/Q front end**), and fills the sample ring the capture task drains. A USB read must never wait out a decode, and the front end must not add its time to one, so it is not on decode's core. **Why pinned, not just unpinned:** ESP-IDF pins a task to the core it first uses the FPU on (the FPU's registers are saved lazily and cannot move between cores; IDF FreeRTOS, *Floating Point Usage*, `vPortTaskPinToCore()` in `portable/riscv/port.c`), and the ingest task runs float code from its first read, so left unpinned it would end up on whichever core that read ran on. The ring (`ft8_sample_ring.c`) is a single-producer single-consumer queue with acquire/release atomics, so the two cores share it without a lock.
  * **Logged:** a slot applied 250 ms or more after its decode (`DECODE slot <n> applied <ms> ms late`), and one never applied because the next slot's decode came first (`DECODE slot <n> dropped, never applied`). Both mean the main loop stalled, and both go to the console and the sidekick's log.
  * **Why not a lock around autoseq.** A QSO's ADIF flash write would run under it, autoseq's callbacks call back into the board, and the armed TX would need the same lock.
  * **The station call** is the main loop's (`g_call`). The decode task tests decodes against its own copy, which the main loop sets whenever the call changes (`decode_pipeline_set_my_call()`, under a mutex), never against `g_call` itself.
  * **The soft clock** is one atomic value, safe from any task ([time.md](time.md)). The decode task steps it; the main loop sets it from the phone.
  * **Still shared, unlocked:** the `decode_tx_state` flags, the designed hand-shake between the two tasks (one writer per field, none wider than one 32-bit write); and the callsign hash table, which decode fills and TX encoding reads, kept apart only because the TX trigger waits for the decode.
* **Flash layout** (`poe_p4/partitions.csv`, 16 MB): `nvs`, `otadata`, `phy_init`, two 4 MB app slots (`ota_0` at `0x20000`, `ota_1`), and a 3 MB LittleFS `storage` partition, which holds `Station.txt` and the daily `.adi` files. There is no factory slot: a flash over USB writes `ota_0` and resets `otadata` to boot it, and an update over Port A writes whichever slot is not running (**Firmware updates**). The table is written only over USB.

### Firmware updates

After its first flash over USB, the main board takes a new image from the sidekick over Port A; the sidekick's side, and what starts an update, is [sidekick.md](sidekick.md), **Firmware updates**. The code is `components/porta`, so any main board shares it.

* **HELLO.** The main board sends HELLO every 5 s, as the sidekick does: `PORTA_PROTO_VERSION` and its build's version (`PROJECT_VER`, the commit; [RELEASE_PROCESS.md](../RELEASE_PROCESS.md)). It is how the app shows the main board's version and how an update is confirmed.
* **The radio must be off.** A firmware update, of either board, needs no USB device on the Host port: a QMX switched off or unplugged (`porta_host_radio_attached()`, from the USB host's own device list, `qmx_usb_device_listed()`). With no radio there is nothing to stop first and nothing to resume after, and the restart that ends a main-board update cannot wedge the QMX (below). The sidekick asks before it starts (`PORTA_ACT_UPDATE_MODE`, which the board ACKs or NAKs with `radio attached` and which changes nothing), `FW_BEGIN` is refused with one attached, and so is the `FW_END` that would restart the board, the transfer kept so the same `FW_END` works once the radio is off. An earlier build stopped a running station for an update and held it stopped until the operator resumed; on the bench the restart then wedged the QMX both times, so the radio was power-cycled anyway (2026-11-10). **Two things the check does not see:** a QMX whose USB is already wedged is not on the device list, and an HL2, on Ethernet, is not checked at all; it is receive-only today, so there is nothing to stop.
* **The receiver** (`porta_fw_rx.c`, host-tested by `host_test_porta_fw_rx`; the flash calls behind it are `porta.cpp`'s). `FW_BEGIN` is refused with a radio attached, on a board with no second app slot (`NO_SLOT`), and for an image larger than the slot. Chunks are written to the inactive slot in order as they arrive (`esp_ota_write()`, each sector erased when reached), and each answer carries the next offset wanted, which is also the answer to a chunk that came twice or out of order. A `FW_BEGIN` repeating the transfer in progress is answered with the bytes already written.
* **`FW_END` installs only what checks out:** every byte arrived; the SHA-256 of the slot, read back from flash, is `FW_BEGIN`'s; ESP-IDF accepts it as an app image for this chip (`esp_ota_end()`); its project name is this board's; and the version built into it is `FW_BEGIN`'s. Then it is made the boot image, the answer goes out, and the board restarts 1.5 s later. Any failure leaves the running image as it was.
* **A new image runs on trial.** With rollback enabled in the bootloader (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`), an image installed this way is kept once the sidekick's HELLO has arrived, which is what the next update needs of it; with none in 120 s the board restarts itself and the bootloader goes back to the image before (`porta_fw_confirm_decide()`). One that crashes at boot is rolled back at once. Until it is kept, the board answers an `FW_END` abort that has nothing to abort with `TRIAL` instead of OK, which is how the sidekick knows an update held and not only that the new version is talking. All three were run on the bench (2026-11-10): kept 1 s after the sidekick's HELLO, back after 120 s without one, and back at once after a crash at boot.
* **Why the radio is off: the restart would wedge the QMX.** Installing an image restarts the P4, and a P4 reset with the QMX attached and streaming leaves the QMX's USB unanswering until the QMX itself restarts (**Two USB-C ports**). It did on both update restarts where the QMX was connected beforehand (2026-11-10, QMX 1_04_010). With the QMX off for the update there is no such reset. That a QMX switched on afterwards connects cleanly is the assumption the rule rests on, and is owed a bench count ([TEST_PLAN.md](../TEST_PLAN.md), Pending).

### Ethernet

Used only when Station's radio is the HL2 (`radio=HL2`, stored as 6), receive only so far ([hl2.md](hl2.md)). Settings › Radio switches between the QMX and the HL2 live ([radio.md](radio.md), **How it works**). Ethernet comes up the first time the HL2 is chosen and stays up; the USB host, the first time the QMX is. While the HL2 is chosen, the QMX's audio does not feed decode and nothing is under CAT control.

* **The PHY:** an IP101 at address 1, reset on GPIO 51, MDC 31, MDIO 52, RMII on ESP-IDF's ESP32-P4 defaults (the 50 MHz clock in on GPIO 50; TX_EN 49, TXD0 34, TXD1 35, CRS_DV 28, RXD0 29, RXD1 30).
* **Our address** is static link-local from our MAC, as the HL2 derives its own: no DHCP client, no server, no conflict probe ([hl2.md](hl2.md), **The link**, which says why). If it equals the HL2's, the P4 does not stream and says why.
* **`poe_p4/main/hl2_transport.cpp`**, a task on core 0, active only while the HL2 is chosen: discovery broadcast to 169.254.255.255 until a stopped HL2 answers (one already streaming to another client is left alone), then one receiver at 48 kHz on the station's dial, and one downstream control packet for each upstream packet, so the HL2's watchdog is fed exactly while we receive. One second with no packet, or the link dropping, sends stop and goes back to discovery; choosing another radio sends stop and waits. After a cable pull the HL2 answers as still running until its watchdog clears it, about 43 s after our last packet, and the P4 waits for that rather than take the stream. Every packet is built by `components/hl2_proto`, which cannot set MOX or write a transmit register.
* **The front end of the radio:** the N2ADR's low-pass for the dial's band, re-chosen on every band change (its relays click), and its receive high-pass (about 2.5 MHz) left in line except on 160 m, where it would cost 17 dB (`hl2_n2adr_receive_filters()`); the low-passes are in the receive path too, and on 40 m at night the low-pass was what stopped the clipping, and the LNA starting at +20 dB and stepping down 3 dB a second while the ADC clips, to −12 dB, never back up within a stream. With no filter chosen the ADC clipped all the time on 40 m ([hl2.md](hl2.md), **Receive**).
* **What it tells the app** (`hl2=` in the live status, `hl2_transport_state_name()`): `nolink` (no Ethernet link), `silent` (link up, nothing answers), `busy` (it answers discovery as streaming to another client, or answers ARP but not discovery: before each probe of the address it was found at, the P4 clears its ARP cache, so an entry afterwards is fresh), `found`, `streaming`, `lost` (it streamed and stopped, kept until it is found again or known busy), `off` (not the chosen radio); and `hl2_overload=1` while the ADC clipped with the LNA at its floor in the last 15 s. The link's speed and duplex are logged at link up, and a half-duplex link goes to the sidekick's log too.
* **Logged** every 15 s on the console: packets, sequence gaps, packets lost, late packets, ADC clips and the HL2's temperature; to the sidekick's log only when there are gaps or clips, and on finding, losing and failing to start.
* **Decoded:** each packet's I/Q goes into a half-second ring in PSRAM, read by the decode pipeline's ingest task through the HL2's own I/Q front end ([decode.md](decode.md), **I/Q front end**). A sequence gap is written as that many packets of zeros, so a slot's timeline holds; a packet the ring has no room for is dropped and logged as `ring_drops`. A band change retunes the receiver's NCO and notes the dial, so each decode carries its dial. **Not yet built: row [abkw](../roadmap/hl2-support.md#abkw):** transmit, and the HL2's own `radio_control` backend.
* **RAM:** Ethernet, lwIP and the transport add 2,688 bytes of static DRAM (63,740 against 61,052, 2026-11-03), and the decode path 72 more; the packet buffers, the 192 KB ring and the front end are in PSRAM. The EMAC's DMA buffers, 20 receive and 10 transmit of 512 bytes, are allocated only when the HL2 path starts. The UDP mailbox is raised to 32 packets (`sdkconfig.defaults`).

### Two USB-C ports

* **Host** — the QMX: CAT (USB CDC) and audio (UAC) run as two USB host clients in `poe_p4/main/qmx_transport.cpp`. The QMX takes about 11 s to enumerate after it is plugged in (a QMX-side fact, measured 2026-09-20). **A P4 reset or flash while the QMX streams can wedge the QMX's USB:** the boot logs `ENUM: Unexpected (8) device response length (expected 16)` and `CHECK_SHORT_DEV_DESC FAILED` once (the QMX acknowledges `GET_DESCRIPTOR` and sends no bytes), then CDC open fails until the QMX restarts. Three resets out of three wedged it on 2026-10-31, QMX 1_04_003; a reboot on 2026-09-28 recovered on its own. Only the QMX can clear it: switching the QMX off and on does, and on this unit so does unplugging its USB, which restarts it. The P4 cannot. The Host port's 5 V runs through an AW32901 switch whose enable is tied to ground (schematic `SCH_StickPoE_SCH_Main_V0.2`, `U8`), so no GPIO cuts it, and cycling the root port (`usb_host_lib_set_root_port_power()`) re-enumerated the QMX into the same empty descriptor (2026-10-31). qmx-panadapter reports the same wedge on QMX 1_03_002 and 1_04_004, also proof against an 8 s VBUS cut and an orderly close before the reset ([its report](https://github.com/SteffenLav/qmx-panadapter/blob/main/docs/qmx-usb-wedge-report-for-hans.md)); a firmware update's restart, the one restart our firmware starts itself, avoids it by needing the radio off first (**Firmware updates**). Do not run UAC open/start on the task that pumps USB host events: that crashed the P4 on 2026-09-18 ([README.md](../README.md), **Operating notes**).
* **PROG**, next to the RJ45 — flashing, the serial console, and 5 V power in, all at once. Confirmed in daily use (operator, 2026-09-25): the QMX streams on Host while the console runs on PROG. First install and recovery are the merged image over PROG, from the downloads page's Web Serial flasher (desktop Chrome or Edge; no phone browser has Web Serial) or `esptool.py`.

### USB host stack

* **Versions.** `espressif/usb` 1.6.0 under `usb_host_cdc_acm` 2.4.1 (CAT) and `usb_host_uac` 1.5.0 (audio), all pinned exact in `poe_p4/main/idf_component.yml`. The two class drivers come from the component registry. Twenty QMX power cycles on this set (2026-11-01) reconnected CAT and decoding every time.
* **`espressif/usb` is vendored** in `components/usb` (Apache-2.0) to carry one patch. It is listed in `EXTRA_COMPONENT_DIRS` (`poe_p4/CMakeLists.txt`), not in the manifest: a component named `usb` takes the place of ESP-IDF's own, which the CDC and UAC drivers require on IDF 5.x, and nothing reaches `dependencies.lock`. An `override_path` entry would write the vendoring machine's absolute path into the lock, which broke the CI build (2026-11-02). The patch: `_intr_hdlr_chan()` in `src/hcd_dwc.c` drops a channel-error interrupt that arrives with no buffer executing, logging `Channel error with no buffer executing, ignored`. Without it, such an error completes a buffer that is not running and asserts in `_buffer_parse()` (`buffer_to_parse->urb != NULL`), which rebooted the P4 on 1 power-off in 7 on usb 1.1.0. On 1.6.0 the warning has not yet been seen (0 in 20 power-offs), so the patch is unproven on hardware; it stays because the unguarded path is still in upstream's code, offered there as [espressif/esp-usb#635](https://github.com/espressif/esp-usb/pull/635). Drop the patch when a release carries that fix or another for the same path.
* **Upgrading `espressif/usb`:** replace `components/usb` with the new release's files (keep the directory name), re-apply the patch (`git log -p --follow -- components/usb/src/hcd_dwc.c` shows it), and set the version in `tools/dep_watch.py`'s `VENDORED`, and drop it if upstream has fixed the path.
* **Every disconnect logs USB errors.** The UAC driver's close suspends the streaming interface with a SET_INTERFACE request to a device that is already gone, so `Submit CTRL URB error: ESP_ERR_INVALID_STATE` and `Suspend Interface 3-0 Failed` appear on each QMX power-off. They are expected; the close still completes.

### Field power

Confirmed by the operator, 2026-09-25: **one laptop power bank runs the whole station.** The QMX takes 12 V from the bank through a USB-C PD trigger cable; the P4 takes straight USB-C from the bank into PROG; the sidekick takes 5 V from the P4 over Grove. The P4 also runs from an iPhone 17 Pro's USB-C port. The sidekick is powered over Grove in every setup.

### On the bench

What a session with a P4 and a QMX runs into, observed 2026-10-24 with QMX firmware 1_04_003. These are facts about the hardware, so nothing here is a procedure to follow.

* **The QMX has to be power-cycled after the P4 resets or flashes.** The USB host reads a short device descriptor (`ENUM: CHECK_SHORT_DEV_DESC FAILED`) and never retries, so `QMX CDC open attempt N failed` repeats until the radio is powered off and on (row `qdcm`). A cable replug while the QMX stays powered fails the same way; a QMX power cycle enumerates in about 10 to 15 s. Plan for one power cycle after every flash.
* **The PROG console link can drop when the QMX keys.** Once, on Tune, the serial console went silent and the P4 stopped answering the flasher (`Failed to connect to ESP32-P4: No serial data received`) while the station kept working, until the PROG cable was unplugged and replugged. Cause unconfirmed; RF on the cable is the suspect. A log capture that stops mid-transmission is this, not a P4 hang.
* **When the console is silent, the sidekick still has the P4's `debug_log_line` lines**, in `/api/events` as `d:0` rows (for example `DECODE pipeline could not start`). Only one program can hold the serial port at a time, so a monitor has to be stopped before flashing.
* **`VN;` answers with the release and the model run together** (`VN1_04_003QMX;`), and `SR;` needs 1_04_004 or later, so the SWR-protection recovery does nothing on 1_04_003 ([radio.md](radio.md)).
