# Micro-FT8 roadmap (kb2slo fork)

Living plan for this fork. How to use it, and the rest of `docs/`, is in [README.md](README.md).

Architecture details stay in `AUTOSEQ_ARCHITECTURE.md` and `AUTOSEQ_INACTIVE_QUEUE.md`. Extract/style/boundaries: [RFC 0002](rfcs/0002-extract-and-boundaries.md). Companion: [RFC 0001](rfcs/0001-ble-companion.md) (Nano UART; phone path not locked, I19). [RFC 0003](rfcs/0003-m32-pocket-port-and-ble-time.md) (Pocket+CTS bundle) is **rejected**. B15 CTS is ROADMAP-only; I17 gets its own RFC if sequenced. Long features get an RFC; this file only points at them.

Ship on `origin/main`. Talk through changes before a local commit (see [README.md](README.md)). No `upstream` remote exists; never push or open a PR to Wei's `wcheng95/Mini-FT8` unless explicitly asked.

| B76 | Fall back to AP mode on a mid-session WiFi loss, not just a failed initial join | **Built 2026-09-21, operator-requested, unverified on hardware.** Boot-time fallback already existed (`wifi_prov_start()` falls through to `start_ap()` if stored credentials fail to join) — the gap was everything after that: once joined, a sustained loss (router reboot, moved out of range) retried `JOIN_MAX_RETRY` (5) times and then just stopped. `BIT_JOIN_FAIL` got set, but nothing was still waiting on it — that wait belongs to `try_join()`'s one call at boot, long since returned — so the device went permanently offline with no AP fallback until a manual power cycle. Fixed with a new `s_was_online` flag (set once on the first successful `IP_EVENT_STA_GOT_IP`, never reset) that lets `on_wifi_event()`'s disconnect handler tell the two cases apart: still doing the initial join (existing behavior, unchanged) vs. was up and running (new — calls `wifi_prov_enter_ap_and_restart()` directly, the same restart-with-`force_ap`-flag path Forget WiFi/Switch-to-AP already use, credentials kept). Also widened the retry budget for the reconnect case specifically: a new `RECONNECT_MAX_RETRY` (20, not measured against a real router reboot's timing — a reasonable guess, not a tuned number) replaces `JOIN_MAX_RETRY` (5) once `s_was_online`, since nobody is standing there watching a mid-session outage the way an operator typically is for an initial join, and a router reboot can easily take a minute or two. `idf.py build` clean, `-Werror`. **Unverified, and says so plainly:** calling `esp_restart()` (inside `wifi_prov_enter_ap_and_restart()`) from within the WiFi driver's own event-callback context, rather than from an HTTP handler task the way the existing callers do, has not been checked for reentrancy issues on real hardware — this is category 3 per `docs/README.md`'s verifiability tiers (field-only, no host-test substitute), and the field check below is what actually proves it rather than the build. Done-when: join a real network, let it establish, then kill that network's WiFi (power off the router, or take the sidekick out of range) and confirm the sidekick's own AP comes back up within `RECONNECT_MAX_RETRY` attempts' worth of time, with no manual power cycle, and that a real router *reboot* (not a permanent kill) inside that same retry window reconnects to the original network instead of needlessly falling back. |

| B70 | Sidekick: deliberate dual-core task placement (currently none) | **Intake 2026-09-20**, raised by the operator stepping back from this session's MVP-era sidekick work to ask whether/how the two ESP32-S3 cores are actually being used. Mapped from code, not assumed: **nothing today is a deliberate dual-core architecture.** Pinned: `app_main()` itself (`CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0`) — and it never returns; after synchronous setup (`porta_beacon_init()`, `host_link_start()`, `wifi_prov_start()`, `button_init()`) it becomes an infinite loop doing the beacon send, heartbeat log, and button-press check, forever, on CPU0 — plus mDNS (also CPU0) and the WiFi driver's own internal task (CPU0, ESP-IDF's standard default). No mutex, no semaphore. This is already a latent, scheduler-luck-dependent race today, since nothing stops the two tasks from landing on different cores right now — deliberately pinning them to *always* differ would turn an occasional risk into a guaranteed one on every request, unless fixed first. The fix is not invented: `s_lock`, a real `SemaphoreHandle_t` mutex, already exists in this exact file and already protects the ring buffer (`s_ring`) a few functions away — the reply-gathering state needs the same protection extended to it, not a new mechanism. **Done-when:** `s_lock` (or an equivalent) covers every read/write of the reply-gathering state; `app_main`'s loop and `porta_rx_task` are explicitly pinned to one core and HTTP/DNS/scan explicitly pinned to the other; a full bench session (config polling, a real QSO logged, a file list/read, AP mode active) shows no new `no ACK`/timeout symptoms and no crash, ideally with the existing `no ACK` rate compared before/after to see whether CPU0 contention was actually a contributor or a red herring. |

| B67 | poe_p4: root-cause "initial QMX USB connection takes several seconds" | **Intake 2026-09-19**, field-found while bench-testing this session's `PORTA_EVT_USB_STATUS` banner (I28d follow-on) on the P4 board — the banner itself works, and in doing so made a pre-existing, previously-invisible delay perceptible for the first time. **Already ruled out**: `try_open_uac()`'s settle-retry loop (`kUacStartSettleMs`=400 × `kUacStartMaxAttempts`=8) — one bench log shows CDC open to UAC streaming in 410ms, one clean attempt, no retry warnings. **Prime remaining suspect, now instrumented but not yet measured**: `try_open()` (CDC) polls `cdc_acm_host_open()` at ~1 Hz with a completely silent failure path — no log, no attempt count, no error code — so there was no way to see how many 1s-spaced attempts preceded the one that succeeded.
